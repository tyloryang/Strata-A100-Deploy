## 1. 架构与准备

### 1.1 组件与端口链

```
浏览器 / SDK
   │  http://<公网IP>:13270
   ▼
平台端口转发（控制台配置，只能转发有限端口）
   │  13270 → VM:8800
   ▼
VM 宿主 0.0.0.0:8800
   │  docker publish
   ▼
容器 strata 0.0.0.0:8080
   │
   └─ engine-cuda12/strata（层拆分：layers 0-23 在 GPU0，24-47 在 GPU1）
```

三层链路任何一层错都表现为"页面打不开"，排查必须**从内往外**：先容器内 `curl 127.0.0.1:8080/health`，再 VM `curl 127.0.0.1:8800/health`，最后公网。

> 推理引擎日志里的 `ready: http://127.0.0.1:8080/v1` 和 `LAN: http://172.x.x.x:8080` **不是**对外访问地址：前者在 `host=0.0.0.0` 时被硬编码成 127.0.0.1，后者枚举的是容器自己的网卡。只能用上面的端口链。

### 1.2 基线与要求

| 项 | 要求 | 本次实测机 |
| --- | --- | --- |
| GPU | 2 × A100，compute capability **sm80** | 2 × A100-SXM4-40GB |
| 显存 | 单卡 40GB（80GB 单卡可用 `--gpu 0`） | 40 + 40 GB |
| 驱动 | ≥ 525（CUDA 12 minor version compatibility）；535 / 550 均可 | 550.78 |
| 内存 | ≥ 94GB（专家 40 + PLE 表 29 + KV） | 94 GB + 8GB swap |
| 磁盘 | `/data` 至少 400GB | 985GB |
| 系统 | x86_64 Linux，内核 ≥ 4.x | CentOS 7 / 4.19 |
| Docker | 20.10+，带 nvidia runtime | 20.10.17 |
| compose | v2 独立二进制（**离线机需预置**） | v2.29.7 |

内存预算公式（决定 `parallel` 上限，务必先算）：

```
常驻 = 专家 arena 40 GB + 引擎权重/缓冲 ~6 GB = 46 GB
     + PLE n-gram 表 26.8 GB × 模式系数
         --ple-io ram  ：系数 1.0，mlock 钉死不可回收  → 常驻 ≈ 73 GB
         --ple-io mmap ：走页缓存，压力下可让出        → 常驻 ≈ 46 GB + 可回收页缓存

每并发请求 KV ≈ 2.8 GB（200K 上下文、int8、--kv-resident 流式落内存）

安全上限（mmap 模式）：46 + 并发 × 2.8 ≤ 总内存 × 0.75
安全上限（ram  模式）：73 + 并发 × 2.8 ≤ 总内存 × 0.90
```

**94 GB 的机器上应该用 `mmap`**（`ram` 是按 560 GB 内存的前提写的）。实测对照：`ram` 时 `Mlocked 28.1 GiB`、`MemAvailable 18.5 GB`；`mmap` 时 `Mlocked 0`、`MemAvailable 32.4 GB`。详见《压测文档》§6.1。

## 2. 部署前检查

```bash
# GPU 与驱动
nvidia-smi -L                                  # 必须列出两张 A100
nvidia-smi --query-gpu=name,compute_cap,memory.total,driver_version --format=csv

# 内存与磁盘
free -h
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINT
df -h /data

# docker 与 nvidia runtime
docker --version
docker info | grep -E 'Runtimes|Default Runtime'      # Runtimes 里必须有 nvidia

# 端口占用
ss -ltnp | grep -E ':8800|:8080' || echo 端口空闲
```

判据：

- `compute_cap` 必须是 **8.0**（镜像只带 sm80 内核表）
- `driver_version` ≥ 525
- `docker info` 的 Runtimes 含 `nvidia`，否则装 `nvidia-container-toolkit`
- `/data` 剩余 ≥ 400GB

`setup.sh` 全程**不访问网络**（实测 49 秒），可以完全断网执行。

install -d -m 700 /etc/strata
head -c 24 /dev/urandom | xxd -p -c 48 > /etc/strata/api_key
chmod 600 /etc/strata/api_key

docker run --rm --gpus '"device=0,1"' -e KEY="$(cat /etc/strata/api_key)" \
  --security-opt label=disable --ulimit memlock=-1:-1 -v /data/qwen-strata:/data \

## 6. 阶段 4：启动

### 6.1 首选：docker-compose

若机器上没有 compose，先装官方 v2 独立二进制（**内网机必须提前放进交付包**）：

```bash
curl -fL -o /usr/local/bin/docker-compose \
  https://github.com/docker/compose/releases/download/v2.29.7/docker-compose-linux-x86_64
chmod +x /usr/local/bin/docker-compose
```

`/data/compose/strata/docker-compose.yml`：

```yaml
services:
  strata:
    image: strata-qwen38:cuda12-1.0
    container_name: strata
    restart: unless-stopped
    init: true
    command: ['/data/Strata/run-iq3_xxs.sh']
    ports:
      - '${BIND_IP}:8800:8080'
    volumes:
      - '${BASE}:/data'
    shm_size: 2g
    ulimits:
      memlock: {soft: -1, hard: -1}
    stop_grace_period: 120s
    security_opt: [label=disable]
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              device_ids: ['0', '1']
              capabilities: [gpu]
    healthcheck:
      test: ['CMD-SHELL', 'curl -fsS http://127.0.0.1:8080/health | grep -Eq loaded.:.true']
      interval: 30s
      timeout: 10s
      retries: 5
      start_period: 300s
```

`.env`（**必须同目录**）：

```
BASE=/data/qwen-strata
BIND_IP=0.0.0.0
```

启动与耗时：

```bash
cd /data/compose/strata
docker-compose config >/dev/null && echo 语法 OK
docker-compose up -d        # 4 秒返回
# 首次 healthy 65 秒
docker-compose ps           # 应显示 (healthy)
```

> **改名迁移**：原来用 `docker run` 起的同名容器必须先删掉，否则名字冲突。

### 6.2 兜底：docker run

compose 不可用时（保留的 `start_strata.sh`）：

```bash
docker run -d --name strata --gpus '"device=0,1"' --restart unless-stopped \
  --security-opt label=disable --ulimit memlock=-1:-1 \
  -p 0.0.0.0:8800:8080 -v /data/qwen-strata:/data \
  strata-qwen38:cuda12-1.0 /data/Strata/run-iq3_xxs.sh
# 70 秒到 ready
```

### 6.3 启动日志（正常的样子）

```
[strata] layer split across GPUs [0, 1] (auto)
[strata] loading the experts into RAM (about 47 GB) ...
[strata] experts loaded: 39.97 GiB at 2.69 GiB/s (43 s so far)
[strata] filling the GPU's expert cache (12288 experts, 17.72 GiB of VRAM) ...
[strata] almost ready ...
ready: http://127.0.0.1:8080/v1  (context 262144 tokens, API key required)
```

看到 `ready:` 后显存应稳定在 **28.9 / 35.0 GiB** 附近（两卡各 40 GB）。具体数值随三个参数变化，不是固定值：

| 参数 | 影响 |
|---|---|
| `parallel`（→ `--batch N`） | 每槽约 0.51 GiB × 2 卡；`parallel=4` 比 `1` 多用约 4 GB |
| `--prefill` 块大小 | `auto:32768` 的缓冲会挤占 VRAM，**并触发层拆分重新平衡**：CUDA0 从 28.9 涨到 37.8 GB（仅剩 3.2 GB） |
| `--kv-resident` | 决定 KV 在显存的窗口 |

启动后建议确认 `nvidia-smi` 与日志里的 `expert cache … slots`；**CUDA0 余量小于 2 GB 就要考虑退回 `--prefill auto`**（见《引擎参数速查》§3、§5）。

## 9. 故障处理

### 9.1 `docker rm -f` 卡在 "zombie" 或 "did not receive an exit event"

**现象**：删容器时卡住，服务中断，容器停在中间态。

**根因**：引擎占着两张卡的 CUDA 上下文，SIGKILL 后要拆 GPU 上下文，这期间进程不可中断；docker 20.10 只等 10 秒。`init: true` 只回收孤儿进程，**不解决 CUDA 收尾**。

**正确处理**：

```bash
docker-compose stop     # SIGTERM，python 自己收掉引擎，13 秒
docker-compose down
docker-compose up -d
```

已经卡住的，等它自己变 `Exited (137)`（约 5 分钟），或 `systemctl restart docker`。

### 9.2 页面打不开

按端口链从内往外查：

```bash
docker exec strata curl -s 127.0.0.1:8080/health      # 容器内
curl -s 127.0.0.1:8800/health                          # VM 内
docker port strata                                      # 8080/tcp -> 0.0.0.0:8800
ss -ltnp | grep 8800
```

最后一层是平台控制台的端口转发规则（`13270 → 8800`），改完必须回控制台确认。

### 9.3 `/health` 从 127.0.0.1 访问不到

如果 compose 里写的是 `'${BIND_IP}:8800:8080'` 且 `BIND_IP=<内网IP>`，宿主 `127.0.0.1:8800` 不监听，要用 `<内网IP>:8800` 或容器内访问。默认 `BIND_IP=0.0.0.0` 时两者都通。

### 9.4 内存打爆导致整机假死

**现象**：SSH 只有 TCP 握手、拿不到 banner；API 无响应；`sshd` 起不来。

**根因**：`parallel` 设得过高 + 长上下文并发，`69GB + 并发×2.8GB` 超过物理内存，进 swap 后系统饿死。

**处置**：从控制台/带外重启，先把 `parallel` 降到 4 或 1 再启动。预防见 1.2 的预算公式，或部署《看门狗》脚本（health 非 200 / 可用内存 <6GB / swap >1GB 即杀压测）。

### 9.5 恢复后 API 返回 401 或脚本报 `FileNotFoundError: /etc/strata/api_key`

系统重装只清了系统盘，`/data` 还在，但 `/etc/strata/api_key` 丢了。从配置里恢复：

```bash
install -d -m 700 /etc/strata
python3 -c "
import json
c = json.load(open('/data/qwen-strata/Strata/strata-iq3_xxs.json'))
open('/etc/strata/api_key','w').write(c['api_key'])"
chmod 600 /etc/strata/api_key
```

### 9.6 上下文超限

返回 **400**，不截断：

```
request exceeds the context window: prompt (270902 tokens) + max tokens (96)
exceeds the context (262144); requests are never truncated.
```

- 提示 + `max_tokens` 超窗 → 配 `"fit_max_tokens": true` 可把**输出上限**缩到剩余空间
- 提示本身超窗 → 无论怎么配都 400，客户端必须自己裁剪历史

## 10. 重装与迁移恢复

### 10.1 判断数据还在不在

```bash
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT
blkid /dev/vdb
```

`vdb` 在且 `blkid` 显示 `TYPE="ext4"` + UUID → 数据盘没被格式化，挂上就能用；`blkid` 为空 → 被格过，走数据恢复；设备不存在 → 只能重传。

### 10.2 挂载并持久化

```bash
mkdir -p /data && mount /dev/vdb /data
df -h /data && ls /data                       # 用量与重装前一致 = 数据完整
echo 'UUID=<磁盘UUID> /data ext4 defaults,noatime,nofail 0 0' >> /etc/fstab
mount -a && findmnt /data
```

用 UUID 不用 `/dev/vdb`：设备名会变，UUID 不会。

### 10.3 重建系统盘上丢失的内容

| 丢失项 | 恢复方式 |
| --- | --- |
| docker 镜像 | `docker load -i /data/strata-qwen38-cuda12-1.0.tar`（41 秒） |
| compose 二进制 | 重新下载 v2.29.7（见 6.1） |
| `/etc/strata/api_key` | 见 9.5 |
| `/etc/fstab` 的 /data | 见 10.2 |

然后 `cd /data/compose/strata && docker-compose up -d`，68 秒 healthy。

### 10.4 恢复后必须验三件事

```bash
curl -s http://127.0.0.1:8800/health
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $(cat /etc/strata/api_key)" http://127.0.0.1:8800/v1/models   # 200
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8800/v1/models                                                        # 401
```

**只看容器状态不够**——曾出现容器 healthy 但 Key 丢失、所有脚本静默失败的情况。

## 11. 与官方手册的差异

| # | 手册 | 实测 | 处理 |
| --- | --- | --- | --- |
| 1 | 容器内 Python 3.12.16 | **3.10.12** | 门禁改为 3.10.12，不影响运行 |
| 2 | `curl 127.0.0.1:8080/health` | 绑 `<内网IP>` 时不监听 | 用 `<内网IP>:8080` 或容器内 curl |
| 3 | A100-PCIE-40GB + 535.104.12 | SXM4-40GB + 550.78 | 535 的 CUDA 12.4 兼容风险在 550 上不存在 |
| 4 | 专家全放内存（按 560GB 写） | 94GB 机器走"显存专家缓存 12288 个/17.72GiB" | 内存小的机器按显存缓存策略 |
| 5 | 局域网另一台机器可访问 | 本机是 libvirt NAT | 需平台端口转发，非离线包问题 |
| 6 | — | 运行中 `docker rm -f` 会卡死 | 一律用 `docker-compose down/up` |
| 7 | 手册称 `--parallel N` 是 setup 参数 | **引擎根本没有 `--parallel`**；只有 `--batch`/`--slots`，配置顶层 `parallel` 由 `server.py` 翻译 | 改 `parallel` 后用 `/slots` 验证槽位数 |
| 8 | 手册按 560 GB 内存推荐 `--ple-io ram` | 本机 94 GB，`ram` 会 mlock 26.8 GiB 导致 `MemAvailable` 只剩 18.5 GB | 改 `--ple-io mmap`，可用内存回到 32 GB |
| 9 | 手册说 ESP 载入后默认对所有请求生效 | `--serve` 下由请求的 `cvec` 决定；配置无 `sampling.experimental_speed_projection` 就不带该参数 | ESP 的 A/B 目前记为"未验证" |

## 12. 附录

### A. 引擎参数速查

完整含义、取舍与坑位见 **[引擎参数速查](引擎参数速查.md)**（含引擎 `--help` 原文）。这里只放最容易出错、最常被问到的几条，并修正早期版本的几处错误说法：

| 参数 | 当前值 | 作用 | ⚠️ 注意 |
| --- | --- | --- | --- |
| `--pack` | `packs/iq3_xxs` | 预转换权重包（专家布局） | |
| `--native` | 第 1 个 GGUF | 原生量化路径的权重来源 | |
| `--ple-gguf` | 第 2 个 GGUF | **必需**：PLE / n-gram 表分片 | 不给会**静默跳过第 1 层 PLE**，不报错 |
| `--expert-profile` | `expert-profile.bin` | 专家热度排序，决定哪 12288 个进显存 | |
| `--expert-cache` | `auto` | 显存里的专家块数 | 与 `--layer-split` **不互斥**（互斥的是 `--peer-device`） |
| `--prefill` | `auto:32768` | 提示分块批处理；`auto` 上限 8192 | 块越大越快，但挤占 VRAM 会改变层拆分 |
| `--spec` / `--spec-min-p` | `4` / `0.5` | MTP 投机解码窗口与置信门限 | 收益取决于接受率，随机文本下等于没开 |
| `--mtp` | `mtp/rt` | MTP 草稿头（占 835 MiB 显存） | |
| `--max-context` | `262144` | KV 容量 | **默认只有 4096** |
| `--kv` | `int8` | KV 量化 | 还有 `q4_0`（再省一半）、`k8v4`（816 B/cell） |
| `--kv-resident` | `32768` | 留在显存的 KV 格数，整份 K/V 放 pinned RAM | **256K 上下文能进 40 GB 卡的关键**；实测只占 1.55 GiB |
| `--ple-io` | `mmap` | n-gram 表读取方式 | `ram` 会 mlock 26.8 GiB（**94 GB 机器上别用**）；`direct` 每 token 读盘 |
| `parallel`（JSON） | `4` | 并发槽位数，**上限 8** | **引擎没有 `--parallel`**，它被翻译成 `--batch N`；`1` = 单槽位 |
| `fit_max_tokens`（JSON） | `true` | 输出上限自适应，不裁提示 | 早期文档写 `false` 是错的 |
