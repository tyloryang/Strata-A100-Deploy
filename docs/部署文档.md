## 1. 架构与准备

### 1.1 组件与端口链

```
浏览器 / SDK
   │  http://<公网IP>:13270
   ▼
平台端口转发（控制台配置，只能转发有限端口）
   │  13270 → VM:8800
   ▼
VM 宿主 0.0.0.0:8800
   │  docker publish
   ▼
容器 strata 0.0.0.0:8080
   │
   └─ engine-cuda12/strata（层拆分：layers 0-23 在 GPU0，24-47 在 GPU1）
```

三层链路任何一层错都表现为"页面打不开"，排查必须**从内往外**：先容器内 `curl 127.0.0.1:8080/health`，再 VM `curl 127.0.0.1:8800/health`，最后公网。

> 推理引擎日志里的 `ready: http://127.0.0.1:8080/v1` 和 `LAN: http://172.x.x.x:8080` **不是**对外访问地址：前者在 `host=0.0.0.0` 时被硬编码成 127.0.0.1，后者枚举的是容器自己的网卡。只能用上面的端口链。

### 1.2 基线与要求

| 项 | 要求 | 本次实测机 |
| --- | --- | --- |
| GPU | 2 × A100，compute capability **sm80** | 2 × A100-SXM4-40GB |
| 显存 | 单卡 40GB（80GB 单卡可用 `--gpu 0`） | 40 + 40 GB |
| 驱动 | ≥ 525（CUDA 12 minor version compatibility）；535 / 550 均可 | 550.78 |
| 内存 | ≥ 94GB（专家 40 + PLE 表 29 + KV） | 94 GB + 8GB swap |
| 磁盘 | `/data` 至少 400GB | 985GB |
| 系统 | x86_64 Linux，内核 ≥ 4.x | CentOS 7 / 4.19 |
| Docker | 20.10+，带 nvidia runtime | 20.10.17 |
| compose | v2 独立二进制（**离线机需预置**） | v2.29.7 |

内存预算公式（决定 `parallel` 上限，务必先算）：

```
常驻 = 专家 40 GB × 映射模式 + 引擎权重/缓冲 ~6 GB
     + PLE n-gram 表 26.8 GB × 模式系数
         --ple-io ram                      ：mlock 钉死，不可回收 → 总量 ≈ 73 GB
         --ple-io mmap                     ：可回收页缓存       → 总量 ≈ 46 GB + 可回收
         --ple-io mmap + --resident-experts：再加 12.65 GiB 钉页，其余可回收

会话缓存 = --conversation-cache-mib（当前 12288 MiB，最多 4 个会话）
每并发请求 KV ≈ 2.8 GB（200K 上下文、int8、--kv-resident 流式落内存）

安全上限（当前配置）：46 + 12（会话缓存）+ 并发 × 2.8 ≤ 总内存 × 0.75
```

**实测三档对照（同一台 94 GiB 机器）**

| | `ram` | `mmap` | `mmap + --resident-experts`（当前） |
|---|---|---|---|
| `Mlocked` | 28.1 GiB | 0 | 0 |
| `MemAvailable` | 18.5 GB | 32.4 GB | **57.1 GB** |
| 引擎 RSS | 76.8 GB | 65.2 GB | **39.3 GB** |

**94 GB 的机器上应该用 `mmap`，并且加 `--resident-experts`**（`ram` 是按 560 GB 内存的前提写的）。详见《压测文档》§6.1、《引擎参数速查》§4、§12、§14。

### 6.1 首选：docker-compose

若机器上没有 compose，先装官方 v2 独立二进制（**内网机必须提前放进交付包**）：


```yaml
services:

    command: ['/data/Strata/run-iq3_xxs.sh']

        reservations:
          devices:
            - driver: nvidia
              device_ids: ['0', '1']
              capabilities: [gpu]
    healthcheck:
      test: ['CMD-SHELL', 'curl -fsS http://127.0.0.1:8080/health | grep -Eq loaded.:.true']
      interval: 30s
      timeout: 10s
      retries: 5
```

`.env`（**必须同目录**）：

```

```

```bash

docker-compose up -d        # 4 秒返回
# 首次 healthy 65 秒
docker-compose ps           # 应显示 (healthy)
```

> **改名迁移**：原来用 `docker run` 起的同名容器必须先删掉，否则名字冲突。

### 6.2 兜底：docker run

compose 不可用时（保留的 `start_strata.sh`）：

### 6.3 启动日志（正常的样子）

```
[strata] layer split across GPUs [0, 1] (auto)
[strata] loading the experts into RAM (about 47 GB) ...
[strata] experts loaded: 39.97 GiB at 2.69 GiB/s (43 s so far)
[strata] filling the GPU's expert cache (12288 experts, 17.72 GiB of VRAM) ...
[strata] almost ready ...
ready: http://127.0.0.1:8080/v1  (context 262144 tokens, API key required)
```

看到 `ready:` 后显存应稳定在 **37.8 / 31.2 GiB** 附近（CUDA0 / CUDA1，各 40 GB）。具体数值随以下参数变化，**不是固定值**：

| 参数 | 影响 |
|---|---|
| `--prefill` 块大小 | `auto:32768` 的缓冲挤占 VRAM，**并触发层拆分重新平衡**：CUDA0 从 28.9 涨到 37.8 GB（仅剩 3.2 GB），CUDA1 从 35.0 降到 31.2 GB |
| `parallel`（→ `--batch N`） | 每槽约 0.51 GiB × 2 卡；`parallel=4` 比 `1` 多用约 4 GB |
| `--kv-resident` | 决定 KV 在显存的窗口（当前 32768 格） |
| `--resident-experts` | **不影响显存**，只改主机内存（专家走文件映射） |

启动后建议确认 `nvidia-smi` 与日志里的 `expert cache … slots`；**CUDA0 余量小于 2 GB 就要考虑退回 `--prefill auto`**（见《引擎参数速查》§3、§5）。

## 9. 故障处理

### 9.1 `docker rm -f` 卡在 "zombie" 或 "did not receive an exit event"

**现象**：删容器时卡住，服务中断，容器停在中间态。

**根因**：引擎占着两张卡的 CUDA 上下文，SIGKILL 后要拆 GPU 上下文，这期间进程不可中断；docker 20.10 只等 10 秒。`init: true` 只回收孤儿进程，**不解决 CUDA 收尾**。

**正确处理**：

```bash
docker-compose stop     # SIGTERM，python 自己收掉引擎，13 秒
docker-compose down
docker-compose up -d
```

已经卡住的，等它自己变 `Exited (137)`（约 5 分钟），或 `systemctl restart docker`。

### 9.2 页面打不开

按端口链从内往外查：

```bash
docker exec strata curl -s 127.0.0.1:8080/health      # 容器内
curl -s 127.0.0.1:8800/health                          # VM 内
docker port strata                                      # 8080/tcp -> 0.0.0.0:8800
ss -ltnp | grep 8800
```

最后一层是平台控制台的端口转发规则（`13270 → 8800`），改完必须回控制台确认。

### 9.3 `/health` 从 127.0.0.1 访问不到

如果 compose 里写的是 `'${BIND_IP}:8800:8080'` 且 `BIND_IP=<内网IP>`，宿主 `127.0.0.1:8800` 不监听，要用 `<内网IP>:8800` 或容器内访问。默认 `BIND_IP=0.0.0.0` 时两者都通。

### 9.4 内存打爆导致整机假死

**现象**：SSH 只有 TCP 握手、拿不到 banner；API 无响应；`sshd` 起不来。

**根因**：`parallel` 设得过高 + 长上下文并发，`69GB + 并发×2.8GB` 超过物理内存，进 swap 后系统饿死。

**处置**：从控制台/带外重启，先把 `parallel` 降到 4 或 1 再启动。预防见 1.2 的预算公式，或部署《看门狗》脚本（health 非 200 / 可用内存 <6GB / swap >1GB 即杀压测）。

### 9.5 恢复后 API 返回 401 或脚本报 `FileNotFoundError: /etc/strata/api_key`

系统重装只清了系统盘，`/data` 还在，但 `/etc/strata/api_key` 丢了。从配置里恢复：

```bash
install -d -m 700 /etc/strata
python3 -c "
import json
c = json.load(open('/data/qwen-strata/Strata/strata-iq3_xxs.json'))
open('/etc/strata/api_key','w').write(c['api_key'])"
chmod 600 /etc/strata/api_key
```

### 9.6 上下文超限

返回 **400**，不截断：

```
request exceeds the context window: prompt (270902 tokens) + max tokens (96)
exceeds the context (262144); requests are never truncated.
```

- 提示 + `max_tokens` 超窗 → 配 `"fit_max_tokens": true` 可把**输出上限**缩到剩余空间
- 提示本身超窗 → 无论怎么配都 400，客户端必须自己裁剪历史

### 12.6 有数据支撑的结论

按证据强度分档。**A 档**是差异远超测量噪声、可放心使用的；**B 档**在噪声范围内，只能作倾向性参考。

**A 档（可信）**

1. **单请求解码速度与并发数强负相关，且没有免费扩容。** 单流约 105~111 tok/s（TPOT 9.0ms）。开 4 槽后并发 8 时单流只剩约 22 tok/s，开 8 槽只剩约 10.6 tok/s。聚合吞吐最多提高约 15%，代价是单流延迟恶化 2~5 倍。
2. **4 槽在长提示下全面优于 8 槽。** v6 的 TPOT 在并发 8 时是 45.9ms，v5（8 槽）是 94.7ms——差 2 倍以上。聚合也更高。
3. **串行窗口 + `batch-mtp` 是最差组合。** v7/v8 比 v6 低 16~20%，TPOT 差 2.9~3.0 倍。引擎自己在启动警告里给的方向（4 路并发时流水线比串行快 25~30%）在本机得到同向验证。
4. **`--kv-resident 32768` 不能去掉。** 去掉后每槽 session 从 0.51 GiB 涨到 1.86 GiB，8 槽吃掉 14.9 GiB 显存，专家缓存从 12288 降到 9203（87% 驻留），并发 8 时聚合从 55.9 崩到 36.5、TPOT 从 94.4 涨到 157.0。这个参数用 1.55 GiB pinned RAM 换来 10.8 GiB 显存，是整份配置里性价比最高的一项。
5. **`--ple-io ram` 与 `mmap` 性能无差异。** v9（ram）与 v5（mmap）在同槽位同分组下：并发 8 聚合 55.9 vs 56.4，TPOT 94.41 vs 94.71。**但 `ram` 会锁死 26.8 GiB 不可回收内存**，期间 `MemAvailable` 掉到 652 MiB、会话缓存开始拒绝停放。稳定性上 `mmap` 更优。
6. **短提示下 8 槽才划算。** B 轮 v5（8 槽）在并发 6/8 是 83.7/89.3，v6（4 槽）是 78.3/80.7。原因：短提示预填占比低，多槽才能真正把解码并行度换成吞吐。

**B 档（噪声内，仅作倾向）**

7. `layer_split` 从 24 抬到 28 未见收益（v13 vs v9 的 B 轮差 1~2%），但也未见害处。
8. `ROUTE_TAIL_SKIP` 从 0 改到 7 **没有复现官方标称的 +13~16%**。但 v12/v13 同时改了会话缓存和拆分点，属于多变量改动，**不能据此判定该参数无效**——这一项始终没有做到干净的单变量测试。

### 12.7 三个测量方法学缺陷（做下一轮前必须先修）

这台机器上跑出来的数字，如果不控制下面三点，**10~15% 的差异全部不可解释**。

**缺陷一：冷启动污染低并发点。**
引擎启动后单请求解码速度会在 32~155 tok/s 之间乱跳，稳定后才固定在 84 tok/s（引擎自报）。v13 在启动后 2 分钟开测，A 轮 c1 测出 TPOT 15.73ms，而正常值是 9.0ms；同一次运行里晚 40 分钟的 B 轮 c1 恢复到 9.4ms。
**对策**：开测前跑 20~30 个预热请求，确认引擎自报解码速度稳定在 84 tok/s 附近再记录。

**缺陷二：同配置重复跑的差异可达 14%，个别点崩到 56%。**
v5 与 v11 是**完全相同**的配置：c1/c2 差 +3.0%/+2.5%（可接受），c3 差 **−56.1%**，c4/c6/c8 差 −11.6%/−7.8%/−13.8%。
**对策**：每个配置至少跑两遍取中位数；并发 3 这个点尤其不稳定，必要时重复或剔除。

**缺陷三：会话缓存跨轮次累积。**
每跑一轮压测就多停放几个会话。v5 那轮缓存基本是空的，到 v11 已 `parked=8 / 13.3 GB` 全满，引擎 RSS 涨到 85.4 GiB、`MemFree` 只剩 694 MB、kswapd0 开始回收。后跑的轮次天然吃亏——这解释了 v5→v9→v11 聚合吞吐的单调下滑（56.4→55.9→48.7）。
更关键的是：**会话缓存在这类单轮负载上复用率≈0**（每行都是 `reused_kv_bytes=0`，UI 上"复用"列全为 0），纯属占 10~13 GB 内存的空转。
**对策**：压测期间彻底关掉会话缓存（删掉三个 `--conversation-cache-*` 参数或把 slots 设 0，注意 `mib 0` 无效），并记录每轮的 RSS / MemAvailable 作为状态一致性的证据。

另一个旁证：Web UI 上同一批 8 个并发请求，输入完全相同（1960 token / 输出 100），解码速度却是 **14.7 / 14.8 / 18.8 / 18.9 / 26.1 / 26.3 / 30.0 / 41.5 / 42.2 / 50.6 / 60.8 tok/s**，耗时 5.9~10.4 秒。**离散度是请求级的，不只是跨轮次的。**

### 12.8 三次事故

**① `setup.sh --calibrate` 清空了 venv（21:36）。**
`setup.sh` 有一段守卫：`.venv/bin/python` 存在但 `pip --version` 失败时执行 `rm -rf .venv`，然后 `pip install -r requirements.txt`。这台机器无外网，装不回来，留下只有 pip/setuptools 的空 venv。当时服务没立刻挂——旧进程把模块载在内存里——但**任何一次重启都会失败**。
恢复：从 `/data/strata-src.tar` 里解出 `Strata/.venv`（该 tar 内含完整原始 venv，8193 个条目）覆盖回去。
**结论：这台离线机器上不要运行 `setup.sh` 的任何会重建 venv 的命令。`/data/strata-src.tar` 是唯一一份可用 venv 的副本，不能删。**

**② 配置被写成非法值，引擎拒绝启动（23:14）。**
`--conversation-cache-mib` 的参数值被拼成了 `327683276832768`（`32768` 重复三次），引擎报 `needs a nonnegative integer within range`，退出码 2，容器进入重启循环（重启 7 次）。
修复：把该参数改回单个合法值（现为 `32768`），重启后 `loaded: true`，端到端 HTTP 200 通过。

**③ 去掉 `kv-resident` 把显存推到 99%（22:25）。**
v10 实测：CUDA0 39.8/40 GB、CUDA1 40.5/40 GB，余量只剩约 600 MB。这种状态下任何长上下文请求都可能触发 CUDA OOM。
**结论：显存占用超过 90% 就不该上线。`--kv-resident` 是安全阀，不是可选项。**

补充一条观察（非事故）：容器被 `docker stop` 时（退出码 0），正在跑的请求会返回 `I/O operation on closed file`，并在日志里留下 `the engine stopped unexpectedly (exit code 0)`。这**不是崩溃**，是被主动停止，排查时不要误判。

### 12.9 最终推荐配置

按两种业务形态给，均基于 2×A100-40G + 94 GiB 内存、262144 上下文、int8 KV：

**长提示 / 文档分析（默认推荐，对应 v6）**

```
parallel            4
--batch 4（流水线 2×2，不启用 batch-mtp）
--ple-io            mmap          # ram 不更快，但会锁死 26.8 GiB
--kv-resident       32768         # 必留，用 1.55 GiB RAM 换 10.8 GiB 显存
--resident-experts  启用          # 专家全驻留主机内存
--prefill           auto:32768
--conversation-cache-mib 16384 / slots 4 / min-tokens 4096 / park-gain 2048
--spec 4 / --spec-min-p 0.5 / --mtp   # 保留无害，但在流水线批量下不生效
layer_split         auto（24）
STRATA_ROUTE_TAIL_SKIP=0   # 未验证 7 的收益，保守取 0
```

实测：A 轮 c8 聚合 59.5 tok/s、TPOT 45.9ms；B 轮 c8 聚合 80.7 tok/s。这是所有 14 个版本里综合最优的一版。

**短提示 / 高并发问答（对应 v5）**

```
parallel            8
--batch 8（流水线 2×4）
其余同上
```

实测：A 轮 c8 聚合 56.4、B 轮 c8 聚合 89.3。

**不要用的组合**：串行窗口 + `batch-mtp`（v7/v8，低 16~20%）；去掉 `kv-resident`（v10，显存 99%、并发 8 崩 35%）；`--ple-io ram`（性能同 mmap 但锁死内存）。

### 12.10 未完成的事项

- **`STRATA_ROUTE_TAIL_SKIP` 0 → 7 的单变量测试没做成。** 官方 changelog 标称 CUDA 上 +13~16% 解码，本机始终是和其他改动混在一起测的。
- **IQ3_S 没跑起来。** 权重已在 `/data/Strata-data/models/IQ3_S/`（52 GB + 27 GB 两个分片），但 `packs/` 下只有 `iq3_xxs`。pack 与量化强绑定——`experts.bin`（40 GB）是从 IQ3_XXS 分片里按字节偏移抠出来的，`experts.bin.src.json` 和 `native_experts.txt` 里钉着 IQ3_XXS 的分片名、大小和偏移，**不能复用**。必须用 `tools/iq_pack.py` 重新生成：

  ```bash
  /data/Strata/.venv/bin/python /data/Strata/tools/iq_pack.py \
    --gguf /data/Strata-data/models/IQ3_S/Qwen3.8-Flash-Next-GSQ-RCO-IQ3_S-00001-of-00002.gguf \
    --out  /data/Strata-data/packs/iq3_s
  ```

  **注意不要加 `--experts-bin`**：不加时 pack 只含 index + tokenizer + dense（约 1.5 GB，几分钟完成），引擎直接从 GGUF 读专家；加了才生成那个 40 GB 的 `experts.bin`（几十分钟）。生成后把配置里的 `--pack` / `--native` / `--ple-gguf` / `tokenizer` 换成 IQ3_S 对应路径即可。
  IQ3_S 总量 79 GB（IQ3_XXS 是 71 GB），内存与显存占用都要重新核；PLE 分片同样是 27 GB。

### A. 引擎参数速查

完整含义、取舍与坑位见 **[引擎参数速查](引擎参数速查.md)**（含引擎 `--help` 原文）。这里只放最容易出错、最常被问到的几条，并修正早期版本的几处错误说法：

| 参数 | 当前值 | 作用 | ⚠️ 注意 |
| --- | --- | --- | --- |
| `--pack` | `packs/iq3_xxs` | 预转换权重包（专家布局） | |
| `--native` | 第 1 个 GGUF | 原生量化路径的权重来源 | |
| `--ple-gguf` | 第 2 个 GGUF | **必需**：PLE / n-gram 表分片 | 不给会**静默跳过第 1 层 PLE**，不报错 |
| `--expert-profile` | `expert-profile.bin` | 专家热度排序，决定哪 12288 个进显存 | |
| `--expert-cache` | `auto` | 显存里的专家块数 | 与 `--layer-split` **不互斥**（互斥的是 `--peer-device`） |
| `--prefill` | `auto:32768` | 提示分块批处理；`auto` 上限 8192 | 块越大越快，但挤占 VRAM 会改变层拆分 |
| `--spec` / `--spec-min-p` | `4` / `0.5` | MTP 投机解码窗口与置信门限 | 收益取决于接受率，随机文本下等于没开 |
| `--mtp` | `mtp/rt` | MTP 草稿头（占 835 MiB 显存） | |
| `--max-context` | `262144` | KV 容量 | **默认只有 4096** |
| `--kv` | `int8` | KV 量化 | 还有 `q4_0`（再省一半）、`k8v4`（816 B/cell） |
| `--kv-resident` | `32768` | 留在显存的 KV 格数，整份 K/V 放 pinned RAM | **256K 上下文能进 40 GB 卡的关键**；实测只占 1.55 GiB |
| `--ple-io` | `mmap` | n-gram 表读取方式 | `ram` 会 mlock 26.8 GiB（**94 GB 机器上别用**）；`direct` 每 token 读盘 |
| `parallel`（JSON） | `4` | 并发槽位数，**上限 8** | **引擎没有 `--parallel`**，它被翻译成 `--batch N`；`1` = 单槽位 |
| `fit_max_tokens`（JSON） | `true` | 输出上限自适应，不裁提示 | 早期文档写 `false` 是错的 |
