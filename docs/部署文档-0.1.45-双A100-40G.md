# Strata 0.1.45 + Qwen3.8-Flash-Next IQ3_XXS 部署文档（2 × A100 40GB）

> **状态**：步骤整理自历史 SXM4 测试机（2026-11-02，CentOS 7 / 550.78）和 AutoDL PCIe 机（2026-11-14）上实际跑通的 0.1.45 部署。**还没有在麒麟 V10 / 535 驱动的目标机上完整执行过。** 第一次在目标机上做时，每一步都要把输出和本文的"通过标准"对一遍，对不上就停下，不要往下走。
>
> 适用：2 × A100 40GB（PCIe 或 SXM4，sm80），离线或内网机器，Docker 部署。
> 不适用：0.2.20（引擎 0.1.66），那一版的镜像、目录和启动方式都不同，见 [离线迁移部署 0.2.20](离线迁移部署-0.2.20.md)。
> 相关文档：[部署文档](部署文档.md)（历史全过程）、[参数详解](参数详解.md)、[目标机迁移清单](目标机迁移清单.md)、[运维卡片](运维卡片.md)。

## 0. 先读这一节

### 0.1 每一步怎么读

每一步都按同样的四段写：

- **命令**：照抄执行。`<...>` 是占位符，换成实际值。
- **为什么**：这一步解决什么问题，不做会怎样。
- **来源**：用到的文件或程序从哪里来。
- **通过标准**：看到什么结果才进入下一步；没看到时怎么处理。

### 0.2 整体流程

```
联网准备机                          目标机（内网 / 离线）
────────────                        ──────────────────────
§3 拿到交付包（137 GB）             §2 部署前检查
   下载 compose 二进制        ──→   §4 传输与校验
   （可选）重新下载模型并核对        §5 解包、导入镜像、驱动兼容自检
                                    §6 系统设置
                                    §7 生成 Key 和配置
                                    §8 启动
                                    §9 日志与接口验收
                                    §10 性能基线
```

### 0.3 统一的目录约定

本文只用一种布局，和仓库里的 `deploy/docker-compose.yml`、`deploy/.env.example`、`deploy/strata-iq3_xxs.recommended.json`、`scripts/setup_offline.sh` 一致：

| 宿主机路径 | 容器内路径 | 内容 |
|---|---|---|
| `/data/`（交付包所在） | — | 6 个 tar 和校验清单 |
| `/data/qwen-strata/` | `/data/` | `BASE`，整个挂进容器 |
| `/data/qwen-strata/Strata/` | `/data/Strata/` | 源码、引擎、`.venv`、`setup.sh`、配置、引擎日志 |
| `/data/qwen-strata/Strata-data/` | `/data/Strata-data/` | 模型 GGUF、`packs/`、`mtp/` |
| `/data/compose/strata/` | — | `docker-compose.yml` 和 `.env` |
| `/etc/strata/api_key` | — | API Key，权限 600 |

**配置 JSON 里写的都是容器内路径**（`/data/Strata/...`）。宿主机上看同一个文件要加前缀 `/data/qwen-strata`。这是最容易搞混的地方。

> 2026-11-14 AutoDL 机器和 0.2.20 阶段宿主机直接用了 `/data/Strata`，不经过 `qwen-strata`。本文不用那种布局，两种不要混用。

### 0.4 三条红线

1. **离线机上不要跑 `setup.sh --calibrate`，也不要跑任何会重建 venv 的命令。** 它会 `rm -rf .venv` 再联网重装，离线装不回来。`/data/strata-src.tar` 是唯一一份完整 venv 的副本，部署完也不要删。
2. **不要对运行中的容器 `docker rm -f` / `docker kill`。** 引擎占着两张卡的 CUDA 上下文，强杀后容器会卡在 zombie 状态。一律用 `docker-compose stop` / `down`，或 `docker stop -t 120`。
3. **真实 Key 只放在 `/etc/strata/api_key` 和配置 JSON 里，两个文件都是 600。** 不写进命令行参数、文档、聊天记录、git。

## 2. 目标机部署前检查

### 2.1 GPU 与驱动

**命令**

```bash
nvidia-smi -L
nvidia-smi --query-gpu=index,name,compute_cap,memory.total,driver_version,power.limit --format=csv
```

**为什么**：引擎只编了 sm80（`BUILD.json` 里 `archs [80]`），不是 A100 就跑不了；驱动版本决定 CUDA 12.4 引擎能不能直接跑（§5.4）。

**来源**：系统自带的 NVIDIA 驱动。

**通过标准**

- 列出两张卡，名字是 `A100-PCIE-40GB` 或 `A100-SXM4-40GB`，`compute_cap` 是 `8.0`，显存 40960 MiB 左右。
- `driver_version` 记下来。≥ 550 直接继续；535（目标机是 535.104.12）也继续，但 §5.4 一定要做；< 525 先升驱动。
- `nvidia-smi` 报错或只看到一张卡：先解决驱动/硬件问题，不要往下走。

### 2.2 内存、磁盘、CPU

**命令**

```bash
free -h
swapon --show
lscpu | grep -E 'Model name|Socket|NUMA node'
lsblk -d -o NAME,ROTA,SIZE
df -h /data
```

**为什么**：0.1.45 推荐配置在 94 GiB 内存的机器上跑通过，内存比这小就要降槽位；`/data` 要同时放交付包（137 GB）和解开后的内容（约 120 GB）。

**来源**：系统命令。

**通过标准**

- 内存 ≥ 94 GiB。
- `/data` 可用 ≥ 400 GB。不够就把交付包放在另一块盘上，解包时 `-C` 指到 `/data/qwen-strata`。
- 没有 swap、双路 CPU、双 NUMA 不影响继续，§6 会处理。

### 2.3 Docker 与 nvidia runtime

**命令**

```bash
docker --version
docker info 2>/dev/null | grep -E 'Runtimes|Default Runtime|Storage Driver'
docker-compose version || docker compose version
getenforce 2>/dev/null || echo 'no selinux'
```

**为什么**：服务跑在容器里，GPU 靠 nvidia runtime 传进去；compose 用来管理起停和健康检查。

**来源**：系统已装的 Docker。没装时离线安装包来源见 §1.2，在麒麟 V10 上的离线安装步骤**未验证**，不在本文范围。

**通过标准**

- Docker ≥ 20.10，`Runtimes` 里有 `nvidia`。没有 `nvidia` 就先装 nvidia-container-toolkit。
- compose 有 v2 就记下版本；没有就在 §3.3 准备二进制。
- SELinux 是 `Enforcing` 也能继续，compose 和所有 `docker run` 都带了 `label=disable`。

### 2.4 端口

**命令**

```bash
ss -ltnp | grep -E ':8800|:8080' || echo '8800/8080 空闲'
docker ps -a --format '{{.Names}}\t{{.Status}}' | grep -w strata || echo '没有名为 strata 的容器'
```

**为什么**：compose 把宿主 8800 发布到容器 8080，容器名固定为 `strata`，端口或名字被占都会启动失败。

**通过标准**：两条都显示"空闲"/"没有"。8800 被占就在 §8 改 compose 的宿主端口；已有 `strata` 容器先确认能不能停，停用 `docker stop -t 120 strata`。

> 也可以直接跑仓库的 `scripts/preflight.sh`，它把上面几项一次打出来，并写到 `/root/offline_check/preflight.log`。

## 3. 联网准备机上的工作

### 3.1 取交付包

**命令**

```bash
mkdir -p /staging/strata-0145 && cd /staging/strata-0145
# 从 <交付包位置> 拷贝 6 个 tar + SHA256SUMS-tars.txt + gguf_done.tar
ls -l
sha256sum -c SHA256SUMS-tars.txt
```

**为什么**：镜像和 0.1.45 引擎只存在于交付包里；在准备机上先校验一次，可以把"源头就坏了"和"传输时坏了"分开。

**来源**：`<交付包位置>`（见 §1.1）。

**通过标准**

- 每个文件字节数和 §1.1 表格逐字一致。
- `sha256sum -c` 每一行都是 `OK`（中文系统显示"确定"），退出码 0。历史实测 57 秒。
- 有任何一行 `FAILED`：重新拷那个文件，不要带着坏文件去目标机。

### 3.2 （可选）重新下载模型并核对

只在交付包里的模型 tar 坏了、或者想独立核对模型时做。

**命令**

```bash
pip install modelscope        # 准备机上，不进目标机
modelscope download --model ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-GGUF --revision master \
  --include 'IQ3_XXS/*.gguf' --local_dir /staging/models
sha256sum /staging/models/IQ3_XXS/*.gguf
```

**为什么**：ModelScope 在国内比 Hugging Face 快；用 CLI 能断点续传。

**来源**：ModelScope `ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-GGUF`，备用 Hugging Face 同名仓库（§1.2）。

**通过标准**：两个 sha256 和 §1.2 的固定值**逐字一致**。不一致说明上游换了文件，**不要用**：packs 和 MTP 是按旧文件生成的，换了模型就要重新生成，这条路在离线机上走不通。

下载核对通过后重新打成和交付包同名的 tar：

```bash
cd /staging/models/IQ3_XXS && tar -cf /staging/strata-0145/Qwen3.8-Flash-Next-GSQ-RCO-IQ3_XXS-00002-of-00002.tar *.gguf
```

### 3.3 下载 compose 二进制

目标机已有 compose v2 就跳过。

**命令**

```bash
cd /staging/strata-0145
curl -fLO https://github.com/docker/compose/releases/download/v2.29.7/docker-compose-linux-x86_64
curl -fLO https://github.com/docker/compose/releases/download/v2.29.7/docker-compose-linux-x86_64.sha256
sha256sum -c docker-compose-linux-x86_64.sha256
```

**为什么**：内网机下载不了；v2.29.7 是测试机上验证过的版本（60.8 MB）。compose 的 `restart`、`healthcheck`、`stop_grace_period` 比手写 `docker run` 好管。

**来源**：Docker Compose 官方 GitHub Release。

**通过标准**：`docker-compose-linux-x86_64: OK`。

### 3.4 （仅在交付包丢失时）重编引擎

**这条路线没有完整记录，需要确认后才能用。** 已知的只有：

- 0.1.45 是在云主机的 Ubuntu 22.04 + CUDA 12.4 容器里编的，`engine-cuda12/BUILD.json` 为 version 0.1.45 / archs [80] / toolkit 12，2026-11-14 那次构建的 source fingerprint 是 `b95137167bd9b751`。
- 上游 `https://github.com/Niko1221/Strata` **没找到 v0.1.45 的 release tag**；仓库里也没有当时的 Dockerfile 和编译命令。
- 上游编 CUDA 引擎的通用方式（见 [引擎升级 0.1.45→0.2.10](../待实施-其他模型/引擎升级-0.1.45到0.2.10.md) §3）：`cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DSTRATA_ENABLE_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=80`，`CMAKE_CUDA_ARCHITECTURES` 必须写 80；官方打包逻辑在 `packaging/build_cuda_linux.sh`、`packaging/package_engine.py`。

如果交付包真的丢了，更现实的做法是直接部署 0.2.20 官方预编译包（[离线迁移部署 0.2.20](离线迁移部署-0.2.20.md)），而不是重造 0.1.45。

### 3.5 打包准备机的产物

**命令**

```bash
cd /staging/strata-0145
cp <仓库>/deploy/docker-compose.yml <仓库>/deploy/.env.example \
   <仓库>/deploy/strata-iq3_xxs.recommended.json <仓库>/deploy/strata-iq3_xxs.0.1.45-8slot-split26.json \
   <仓库>/scripts/setup_offline.sh <仓库>/scripts/accept.sh <仓库>/scripts/preflight.sh .
sha256sum docker-compose-linux-x86_64 *.json *.yml .env.example *.sh > SHA256SUMS-extra.txt
```

**为什么**：目标机上用到的所有东西一次带齐，并且都有校验值。

**通过标准**：`/staging/strata-0145` 下有 6 个 tar、`gguf_done.tar`、`SHA256SUMS-tars.txt`、`SHA256SUMS-extra.txt`、compose 二进制、配置和脚本。

## 4. 传输到目标机并校验

### 4.1 传输

**命令**（以 rsync 为例，任意支持断点续传的方式都可以）

```bash
rsync -av --partial --progress /staging/strata-0145/ root@<内网IP>:/data/
```

**为什么**：单个文件最大 75.8 GB，断点续传能避免从头再来。移动硬盘如果是 FAT32（单文件上限 4 GB），要先格式化成 exFAT 或 ext4。

**来源**：§3 的准备机目录。

**通过标准**：目标机 `/data/` 下没有 `.filepart`、`.tmp`、`.~tmp~` 之类的残留。

### 4.2 校验

**命令**

```bash
cd /data
ls -l *.tar
sha256sum -c SHA256SUMS-tars.txt
sha256sum -c SHA256SUMS-extra.txt
```

**为什么**：137 GB 走网络或硬盘，任何一位翻转都会在很后面才以奇怪的方式暴露出来（加载崩溃、乱码输出），先校验最省事。

**通过标准**：字节数和 §1.1 一致，两份清单每一行都 `OK`/`确定`。失败的文件重传，不要"先解开看看"。

## 5. 解包、导入镜像、驱动兼容自检

### 5.1 解包

**命令**

```bash
B=/data/qwen-strata
mkdir -p $B/Strata-data/models/IQ3_XXS
cd /data
tar -xf strata-src.tar -C $B
tar -xf tools.tar     -C $B
tar -xf data-packs.tar -C $B/Strata-data      # 实测约 100 秒
tar -xf data-mtp.tar   -C $B/Strata-data
tar -xf Qwen3.8-Flash-Next-GSQ-RCO-IQ3_XXS-00002-of-00002.tar -C $B/Strata-data/models/IQ3_XXS
tar -xf gguf_done.tar  -C $B/Strata-data/models/IQ3_XXS
```

**为什么**：目录要和 §0.3 的约定完全一致，配置里的路径是写死的。`.gguf.done` 标记让 setup 认为模型已下载完，不去联网。

**来源**：交付包。

**通过标准**

```bash
cat $B/Strata/engine-cuda12/BUILD.json              # version 0.1.45，archs 含 80，toolkit 12
ls  $B/Strata/.venv/bin/python $B/Strata/setup.sh
ls  $B/Strata/data/expert-profile.bin
ls  $B/Strata/data/experimental-speed-projection/   # 有 Qwen3.8-Flash-Next-experimental-speed-projection.gguf
ls  $B/Strata-data/packs/iq3_xxs/                    # experts.bin dense.bin tokenizer index.txt ...
ls  $B/Strata-data/mtp/rt | head
ls -la $B/Strata-data/models/IQ3_XXS/                # 两个 .gguf + 两个 .gguf.done
du -sh $B/Strata-data/packs/iq3_xxs $B/Strata-data/models/IQ3_XXS   # 约 42G / 75G
```

全部存在继续。ESP 向量缺失就按 §1.2 的固定 commit 地址补，放回原路径；`expert-profile.bin` 缺失同理。

### 5.2 核对模型哈希

**命令**

```bash
sha256sum /data/qwen-strata/Strata-data/models/IQ3_XXS/*.gguf
```

**为什么**：tar 校验只证明 tar 完整，这一步证明解出来的就是 packs 对应的那两片模型。

**通过标准**：和 §1.2 的两个值逐字一致。

### 5.3 导入镜像

**命令**

```bash
docker load -i /data/strata-qwen38-cuda12-1.0.tar     # 实测 41–55 秒
docker image ls strata-qwen38
```

**为什么**：镜像里有 CUDA 12.4 运行库、Python 3.10.12 和 curl（健康检查要用），引擎依赖它们。

**来源**：交付包。

**通过标准**：看到 `strata-qwen38   cuda12-1.0   84d6b339d752   ...   7.61GB`。ID 不对说明拿错了镜像，比如 0.2.20 用的 `strata-qwen38:0.1.45-cuda12`（ID `23b13e03d0dd`，2.47 GB）不能代替它。

### 5.4 驱动兼容自检（535 驱动必做）

**命令**

```bash
B=/data/qwen-strata
I=strata-qwen38:cuda12-1.0
# 1) 容器里能看到两张卡
docker run --rm --gpus '"device=0,1"' $I nvidia-smi -L
# 2) 引擎的动态库都能找到

  bash -c 'ldd /data/Strata/engine-cuda12/strata | grep -c "not found"'
# 3) venv 能用
docker run --rm --security-opt label=disable -v $B:/data $I \
  /data/Strata/.venv/bin/python -c 'import sys; print(sys.version)'
```

**为什么**：引擎用 CUDA 12.4 工具链编，目标机驱动是 535（原生对应 CUDA 12.2），只能靠 CUDA 12 的小版本兼容运行。**这个组合没有测过。** 测试机是 550.78。

**来源**：镜像 + `strata-src.tar`。

**通过标准**

- 第 1 条列出两张 A100。
- 第 2 条输出 `0`。不是 0 就是缺 `libcudart.so.12` / `libcublas.so.12`，检查是不是挂错了目录或拿错了镜像。
- 第 3 条输出 `3.10.12`。
- 第 1 条报 `requirement error: unsatisfied condition: cuda>=12.4` 一类的错误：这是镜像自带的 `NVIDIA_REQUIRE_CUDA` 检查。加 `-e NVIDIA_DISABLE_REQUIRE=true` 再试；通过的话，§7.1 的 setup 和 §8 的启动都要带上这个变量。它只绕过检查，引擎能不能真正跑，要看 §9.1 的日志里有没有 CUDA 报错。
- §9.1 引擎报 `CUDA driver version is insufficient` 或找不到符号：535 跑不了这个引擎。两条退路：升驱动到 ≥ 550（离线 `.run` 包，需要重启，要排运维窗口）；或在准备机上用 CUDA 12.2 工具链重编（§3.4，未记录）。

## 6. 系统设置

这几项测试机都没做，是针对目标机（双路双 NUMA、565 GiB、无 swap）补的，理由见 [目标机迁移清单 §三](目标机迁移清单.md)。效果**未在目标机实测**。

### 6.1 内核参数

**命令**

```bash
cat > /etc/sysctl.d/99-strata.conf <<'EOF'
kernel.numa_balancing = 0
vm.max_map_count = 262144
vm.swappiness = 10
vm.nr_hugepages = 0
EOF
sysctl -p /etc/sysctl.d/99-strata.conf
```

**为什么**

- `numa_balancing = 0`：自动 NUMA 迁移会在后台搬页，双路机器上会拖慢预填（llama.cpp 有明确警告）。
- `max_map_count = 262144`：引擎大量 mmap 模型文件和 PLE 表，默认 65530 个映射区可能不够。
- `swappiness = 10`：配合 §6.2 的 swap，只在真不够时才换出。
- `nr_hugepages = 0`：推荐配置带 `--resident-experts`，这块内存引擎显式不用大页，预留的 hugetlb 页会白白占掉内存。原因详见 [离线迁移部署 0.2.20 §8.1](离线迁移部署-0.2.20.md#81-大页内存按当前配置不用预留)。

**通过标准**：`sysctl kernel.numa_balancing vm.max_map_count vm.swappiness vm.nr_hugepages` 显示 `0 / 262144 / 10 / 0`。

### 6.2 swap

**命令**

```bash
fallocate -l 32G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
swapon --show
```

**为什么**：没有 swap 时内存一超，内核直接 OOM 杀引擎。swap 不是用来跑的，是给你留出发现问题、降参数的时间。

**通过标准**：`swapon --show` 里有 `/swapfile 32G`。已经有 16 GB 以上 swap 就跳过。

### 6.3 文件句柄、persistence mode

**命令**

```bash
printf '* soft nofile 65535\n* hard nofile 65535\n' > /etc/security/limits.d/99-strata.conf
nvidia-smi -pm 1
```

**为什么**：句柄数给 HTTP 并发和 mmap 留余量；persistence mode 让驱动常驻，避免每次启动容器重新初始化 GPU。

**通过标准**：`nvidia-smi -q | grep -i 'Persistence Mode'` 两张卡都是 `Enabled`。`-pm 1` 重启后失效，需要的话加到开机脚本或启用 `nvidia-persistenced` 服务。

### 6.4 防火墙（需要内网其他机器访问时）

**命令**

```bash
firewall-cmd --state && firewall-cmd --permanent --add-port=8800/tcp && firewall-cmd --reload
```

**为什么**：麒麟 V10 默认可能开着 firewalld，宿主机本地能访问、内网其他机器访问不了，多半是这里。

**通过标准**：`firewall-cmd --list-ports` 含 `8800/tcp`；firewalld 没运行就跳过。

## 7. 生成 API Key 和配置

### 7.1 生成 Key

**命令**

```bash
install -d -m 700 /etc/strata
head -c 24 /dev/urandom | xxd -p -c 48 > /etc/strata/api_key
chmod 600 /etc/strata/api_key
wc -c /etc/strata/api_key       # 49（48 位十六进制 + 换行）
```

**为什么**：服务对外提供接口，不带 Key 必须 401。Key 存文件，后面所有命令都从文件读，不出现在命令行和历史记录里。

**来源**：系统随机数。没有 `xxd` 就用 `openssl rand -hex 24 > /etc/strata/api_key`。

**通过标准**：`wc -c` 输出 49，`ls -l` 显示 `-rw-------`。

### 7.2 断网跑一次 setup

**命令**

```bash
B=/data/qwen-strata
docker run --rm --gpus '"device=0,1"' -e KEY="$(cat /etc/strata/api_key)" \
  --security-opt label=disable --ulimit memlock=-1:-1 -v $B:/data \
  strata-qwen38:cuda12-1.0 bash -c 'cd /data/Strata && ./setup.sh --setup --no-start --yes \
  --cuda 12 --model IQ3_XXS --gpus 0,1 --vision no --context 262144 --no-browser \
  --host 0.0.0.0 --api-key "$KEY" --data-dir /data/Strata-data --models-dir /data/Strata-data/models' \
  2>&1 | tee /root/setup-offline.log
```

（和仓库 `scripts/setup_offline.sh` 是同一条命令，脚本会把日志写到 `/root/offline_check/`。§5.4 需要 `NVIDIA_DISABLE_REQUIRE` 的话，在 `docker run` 后加 `-e NVIDIA_DISABLE_REQUIRE=true`。）

**为什么**：setup 按本机的 GPU、内存、磁盘检测一遍，生成启动脚本 `run-iq3_xxs.sh`（compose 的 `command` 就是它）和一份基础配置。它全程不联网，历史实测 49 秒。**不加 `--build`**（沿用已编好的引擎），**不加 `--calibrate`**（会重建 venv，见 §0.4）。

**来源**：`strata-src.tar` 里的 `setup.sh`。

**通过标准**：输出里每一行都是 `[ok]`，至少要有：

```
[ok] GPUs: GPU 0 (A100-..., 40 GB) + GPU 1 (... 40 GB) together (layers split)
[ok] GPU: ... compute capability 8.0, driver 535.104.12
[ok] engine already built for this PC
[ok] two GGUFs already downloaded
[ok] model prepared: /data/Strata-data/packs/iq3_xxs
[ok] MTP draft layer: /data/Strata-data/mtp/rt
[ok] layer split across GPUs [0, 1] (auto)
```

然后确认：

```bash
ls -l /data/qwen-strata/Strata/run-iq3_xxs.sh /data/qwen-strata/Strata/strata-iq3_xxs.json
```

- 出现 `[!!]`、`[x]`，或开始下载东西（说明 `.gguf.done` 标记没放对）：Ctrl+C 停掉，回 §5.1 检查目录。
- 出现 `building the engine`：说明它认为引擎不匹配，停掉，检查 `BUILD.json` 和镜像是否对得上。

### 7.3 换成推荐配置

setup 生成的配置是 `--ple-io ram`、`parallel 1`、`--prefill auto`，是通用默认值，不是这台机器调出来的值。换成仓库里的推荐配置。

**命令**（4 槽推荐配置；要 8 槽就把文件名换成 `strata-iq3_xxs.0.1.45-8slot-split26.json`）

```bash
C=/data/qwen-strata/Strata/strata-iq3_xxs.json
cp $C $C.setup-generated
cp /data/strata-iq3_xxs.recommended.json $C
python3 - "$C" <<'EOF'
import json, sys
p = sys.argv[1]
c = json.load(open(p))
c['api_key'] = open('/etc/strata/api_key').read().strip()
json.dump(c, open(p, 'w'), ensure_ascii=False, indent=2)
EOF
chmod 600 $C $C.setup-generated
```

**为什么**

| 项 | setup 默认 | 推荐配置 | 原因 |
|---|---|---|---|
| `parallel` / `--batch` | 1 | 4 | 4 槽是长提示场景实测最优（v6）；两处必须一致 |
| `--ple-io` | ram | mmap | 性能没差别，`ram` 会锁死 26.8 GiB 内存 |
| `--resident-experts` | 无 | 有 | 引擎内存占用 61.7 → 39.3 GiB，显存不变 |
| `--prefill` | auto | auto:32768 | 层拆分下实际生效的块大小以日志为准（2026-11-14 PCIe 机日志是 8192） |
| 会话缓存 | 无 | 16384 MiB / 4 槽 | 多轮对话的前缀复用 |
| `--kv-resident` | 32768 | 32768 | **必须保留**，去掉后显存 99%、并发 8 崩 35% |

两份配置怎么选：

| | 4 槽 `recommended.json` | 8 槽 `0.1.45-8slot-split26.json` |
|---|---|---|
| 场景 | 长提示、文档分析 | 短提示、高并发问答 |
| 层拆分 | auto（解析为 24） | 固定 26 |
| 并发 8 聚合（长提示 in=2000） | 59.5 tok/s，TPOT 45.9 ms | 8 槽另一套（v5）：56.4 tok/s，TPOT 94.7 ms |
| 说明 | 历史 SXM4 实测 v6 | 和 0.2.20 测试用的是同一套参数，只改了路径；`STRATA_RESIDENT_HEADROOM_GIB` 文件里是 2，A/B 实测用的是 12，用 2 的性能**未实测** |

565 GiB 的目标机内存不是瓶颈，`--ple-io ram` 也可以用，但实测没收益，保持 `mmap`。

**来源**：仓库 `deploy/`。

**通过标准**

```bash
python3 -c "import json;c=json.load(open('$C'));print(c['parallel'], c['exe']); a=c['args']; print(a[a.index('--batch')+1]); print(len(c['api_key']))"
grep -oE '"/data/[^"]+"' $C | sort -u
ls -l $C
```

- 第一条输出 `4 /data/Strata/engine-cuda12/strata`、`4`、`48`（8 槽配置是 `8`、`8`、`48`）。
- 列出的路径都以 `/data/Strata/` 或 `/data/Strata-data/` 开头（容器内路径），**不能**出现 `/data/qwen-strata/` 或 `/data/Strata-0.2.20/`。
- 权限 `-rw-------`。

## 9. 验收

### 9.1 引擎日志

**命令**

```bash
L=/data/qwen-strata/Strata/strata-iq3_xxs.log
grep -nE 'compute capability|layer split|experts resident|of 24576|of its 12288|VRAM free|batch-groups|kv-resident|cells per|ready:' $L
grep -niE 'error|fail|out of memory|insufficient' $L | head
```

**为什么**：接口能通不代表配置生效。专家有没有全进显存、层拆分是不是生效，只有日志能证明，直接决定速度。

**通过标准**

| 看什么 | 应该看到 |
|---|---|
| 卡型号 | `compute capability 8.0`，名字是 `A100-PCIE-40GB` 或 `A100-SXM4-40GB` |
| 层拆分 | `layer split`，4 槽配置为 auto（历史解析为 24），8 槽配置为 `split 26` |
| 专家全在显存 | `every expert is in the GPU caches (24576 of 24576)`，或每卡 `12288 of its 12288` / `100% of the experts resident` |
| 显存余量 | `VRAM free with everything loaded` 两张卡都 ≥ 1 GB |
| 就绪 | `ready: http://127.0.0.1:8080/v1  (context 262144 tokens, API key required)`（8 槽配置是 229376） |
| 错误 | 第二条 grep 没有 CUDA 相关报错 |

- 专家数不是 24576：显存不够，有专家落到了内存，速度会明显下降。先看 CUDA0 余量，小于 2 GB 就把 `--prefill auto:32768` 改回 `auto`。
- `ready:` 里的 `127.0.0.1:8080` 是容器内地址，不是访问地址，访问走宿主 8800。

### 9.2 接口

**命令**（也可以直接跑 `scripts/accept.sh`，它做的是同样的检查）

```bash
KEY=$(cat /etc/strata/api_key)
curl -s http://127.0.0.1:8800/health; echo
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8800/v1/models
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $KEY" http://127.0.0.1:8800/v1/models
curl -s http://127.0.0.1:8800/v1/chat/completions -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"model":"x","max_tokens":64,"temperature":0,"reasoning_effort":"none","messages":[{"role":"user","content":"计算 37 × 43，只给结果"}]}'; echo
curl -s -H "Authorization: Bearer $KEY" http://127.0.0.1:8800/slots | python3 -c 'import json,sys; print(len(json.load(sys.stdin)))'
nvidia-smi --query-gpu=index,memory.used,memory.total --format=csv
```

**为什么**：分别证明服务加载完成、鉴权生效、推理正确、槽位数和配置一致、两张卡都在干活。

**通过标准**

| # | 检查 | 期望 |
|---|---|---|
| 1 | `/health` | `loaded: true`、`api_key: true`、`max_context: 262144`（8 槽配置 229376） |
| 2 | 不带 Key | `401` |
| 3 | 带 Key | `200` |
| 4 | 推理 | 回答里有 `1591`，`finish_reason` 为 `stop` |
| 5 | `/slots` 条数 | 等于 `parallel`（4 或 8） |
| 6 | 显存 | 两张卡都有明显占用（历史 4 槽：约 37.8 / 31.2 GB） |

- 第 4 条回答是空的：多半是没带 `reasoning_effort: "none"`，`max_tokens` 被思考占满了。
- 宿主机能通、内网其他机器不通：查 §6.4 防火墙和 `.env` 的 `BIND_IP`。

### 10.1 单路解码（估算）

## 11. 运维与故障

### 11.1 起停

```bash
cd /data/compose/strata
docker-compose ps          # 巡检，看 (healthy)
docker-compose restart     # 历史 77 秒到 healthy
docker-compose stop        # 约 13 秒，显存回到 1 MiB
docker-compose start
docker-compose down        # 不动 /data
docker-compose up -d
```

### 11.5 常见故障

| 现象 | 先查 | 处理 |
|---|---|---|
| 容器一启动就退出，报 CUDA 版本 | §5.4 | `NVIDIA_DISABLE_REQUIRE=true`；不行就升驱动或重编 |
| `Permission denied` 读不到挂载目录 | SELinux | 确认 compose 里 `label=disable` 还在 |
| 一直 `unhealthy` | 引擎日志末尾 | 冷启动慢就继续等；有报错按报错处理 |
| 专家不是 `24576 of 24576` | 显存余量 | `--prefill` 改回 `auto`，或降槽位 |
| 进程消失，`dmesg` 有 `oom-kill` | `free -h`、并发数 | 降 `parallel`；确认 §6.2 swap 已开；长上下文（200K）并发不超过 4 |
| 401 | `/etc/strata/api_key` 和配置里的 Key 是否一致 | 以配置里的为准写回文件 |
| 400 `exceeds the context window` | 提示长度 | 客户端裁剪历史；`fit_max_tokens: true` 只能缩输出上限 |
| 本机通、内网不通 | `BIND_IP`、firewalld | §6.4、§8.2 |

更多故障和重装恢复见 [部署文档 §9、§10](部署文档.md)。
