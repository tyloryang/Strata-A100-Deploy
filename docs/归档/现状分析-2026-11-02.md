### 4.2 三个必须修的方法学问题

**① 全部使用 `--dataset random`** —— 手册 §12.1 明确警告过这条。随机 token 的 next-token 近似均匀分布，MTP 草稿几乎必被拒：实测接受率 2–5%、每次只出 1.01 个 token，等于投机采样完全失效。同时随机前缀不可能命中 prefix cache（KV 命中率恒 0）。
→ **现有全部绝对吞吐都是地板值，不能当交付基线。** 换成自然中文后，接受率通常会跳到 40–70%，单流解码有希望显著提升。

**② 服务端 `parallel=1`，只有一个槽位。**
引擎没有 `--parallel`（`strata --help` 里 0 处匹配）。真正的开关是 `--batch N / --slots N`，由 `server.py` 从配置的 `parallel` 键翻译：

```python
PARALLEL_MAX = 8
def parallel_args(cfg, args):
    if n <= 1: return []          # parallel=1 → 不传 --batch
    ...
    return ["--batch", str(n)]
```

所以所有"并发 2/4/6/8"的用例，实际测的都是 **1 个槽位前的排队**，不是批处理吞吐。这解释了为什么聚合吞吐在所有并发档位都卡在 ~50–110 tok/s。

副作用：早期 `parallel=4` 那批（0948–1001）反而让 TPOT 从 8.05 ms 恶化到 13.25 ms，聚合只涨 16% —— 与官方文档记录的"专家多在 CPU 时，批处理会让每个请求慢 11–24%"完全吻合。

**③ ESP 的 A/B 无效。**
控制向量本身已加载（日志有 `control vector mode = project, dir = per-layer, layers 4..44 (41 steered)`），但 `--serve` 模式下**每个请求各自开关**：

```python
# server.py:1236
on = sampling.get("experimental_speed_projection")
return f" cvec={int(on)}" if isinstance(on, bool) else ""
```

配置里没有 `sampling.experimental_speed_projection`，所以请求不带 `cvec`，走引擎默认值。实测开/关两轮差异在 ±5%（噪声级），**不能作为 ESP 有/无效的证据**，需要先正确开启再重测。

```
总显存   2 × 40 GiB = 80 GiB

│  ├ PLE n-gram 表    ~27 GiB  ← 3.2 亿行 × 90 B，被 --ple-io ram 整表锁内存
│  └ 权重/KV/缓冲      ~6 GiB
```

### 5.2 逐参数

| 参数 | 现值 | 含义 | 为什么这样 | 判断 |
|---|---|---|---|---|
| `--layer-split auto` | auto | 按各卡空闲显存自动分层 | 双卡同型号，auto 合理 | ✓ 结果 K=24，均匀 |

| `--native` | shard1 | 启用全套原生 CUDA 路径 | 性能路径 | ✓ |
| `--spec 4` / `--spec-min-p 0.5` | 4 / 0.5 | MTP 草稿每次验 4 个 token；草稿层置信度 ≥0.5 才继续外扩 | setup 默认值 | △ 参数本身合理，但**被测语料废掉了它** |

## 6. 调优方向（按收益/风险排序）

### 6.1 A 级：必做，否则后面的数字都不可信

**A1. 换自然中文语料重测。**
准备 ≥32 条 500–2000 字的中文运维类问答，用 `--dataset openqa` 或自定义 jsonl。这一步决定投机采样能否从 2% 接受率恢复到正常水平，是所有吞吐基线的前提。

**A2. 确认 ESP 到底要不要。**
先在配置里写 `"sampling": {"experimental_speed_projection": true}` 让请求带 `cvec=1`，再重跑 A/B。否则 ESP 那 9 个参数只是增加了每 token 0.2–0.4% 的开销。

### 6.2 B 级：高确定性收益

**B1. `--ple-io ram` → `--ple-io mmap`**（已于 15:08 实施，实测确认）
PLE 表 26.8 GiB（320001536 行 × 90 B）。`ram` 用 mlock 整表钉内存，`mmap` 靠页缓存按需装入、可回收。实测差异：

| 指标 | `ram`（14:38） | `mmap`（15:08） |
|---|---|---|
| `Mlocked` | 28.1 GiB | **0** |
| `MemAvailable` | 18.5 GB | **32.4 GB**（+13.9 GB） |
| 引擎 RSS | 76.8 GB | 65.2 GB |
| 启动额外耗时 | +2.5~6 s | 0（懒加载） |

注意：同一次重启里还加了 `--batch 4`，两者混在一起，所以这组数字只能证明内存结构变好了，**不能证明 PLE 读性能的变化**。`mmap` 的代价是内存压力下页会被回收、退回 SSD 读，因此热启动后要先预热再压测（见 §13 手册的 `cat` 预热法）。

**B2. `--prefill auto` → `--prefill auto:32768`**
引擎源码 `setup.py` 里写死了这个档位判断：

```python
PREFILL_BIG_RAM_GB = 96   # bench #433 #440 #834 #669:
                          # --prefill auto:32768 +21-35% at 96 GB, ~3x slower at 32 GB
PREFILL_RISK_RAM_GB = 64
```

本机内存正好 **96 GB**，是官方标定的最优点。当前 prefill 只有 4.2–5.2k tok/s，这是最直接的一刀。
前提：先做 B1 腾内存，否则 18.5 GB 可用内存撑不住 32768 的缓冲。

**B3. 让专家缓存用上第二张卡**
现状：末级 CUDA1 有 33.10 GiB 可给专家，24576 全量需 ~40–44 GiB，**装不下**，所以停在 12288（50%）。而 CUDA0 跑完层 0–23 后还空着约 35 GiB。
引擎提供了 `--expert-cache-device1 N|auto`（"fill CUDA1 with N experts or as many as fit"）。
注意：`--peer-device` 的帮助明确写了与 layer-split 互斥，但 `--expert-cache-device1..3` **没有**这条限制 —— 需要实验验证它与 layer-split 的组合行为，不要直接上生产。

### 6.3 C 级：值得实验

| 项目 | 现值 | 试什么 | 依据 |
|---|---|---|---|
| KV 位宽 | int8（1056 B/cell） | `--kv k8v4`（816 B/cell，K 保持 int8 精确） | 省 23% KV，长上下文友好 |
| KV 显存格数 | 32768 | `--kv-resident 20480`（最小值） | 再腾一点显存给专家 |
| 双卡 decode 重叠 | 默认关 | `--pipeline-windows 2` | 帮助写明仅 AMD gfx12 默认开，NVIDIA 上 2 stage 有重叠空间 |
| 专家缓存策略 | 共享计数器 | `--expert-cache-per-layer` | 帮助实测：默认策略 vs per-layer，命中率 2.97% → 21.4% |
| 草稿扩展 | `--suffix-draft 3` | `--lookup-chain 16` | 提示词查找草稿，默认 0=关；对重复性文本有效 |
| 引擎自调优 | 未跑 | `--calibrate`（15–30 min，占满 GPU） | 会为本机标定 `--spec-min-p` |
| 批处理 | 1 | `parallel` 2 或 4 | **但**官方文档明确：专家多在 CPU 时批处理会让每个请求慢 11–24%、合计反而降。必须先解决 B3 让专家全进显存，再谈批处理 |
| CUDA0 负载 | 26.6 GiB | 试 `--layer-split 26` 手动调 | 现在 32.7 vs 26.6 不均，auto 按空闲显存分，未按每层 0.48 ms 的成本均衡 |

## 7. 压测参数方案

### 7.1 数据集（一票否决项）

```bash
# 推荐：真实问答
docker exec strata /data/tools/venv-evalscope/bin/evalscope perf \
  --dataset openqa ...

# 或自定义中文语料（每行 {"prompt": "..."}）
--dataset custom --dataset-path /data/Strata-data/prompts_zh.jsonl
```

`random` 只能用于**容量/拐点扫描**（长度可控、方差小），绝不能用于报吞吐。

### 7.2 三组业务形态 × 并发梯度

| 形态 | input | output | 对应场景 |
|---|---|---|---|
| 短问答 | 512 | 256 | 在线助手 |
| 典型运维 | 2000 | 100 | 本次"文章同款"口径，便于横向对比 |
| 长文阅读 | 8192 | 256 | RAG／文档问答 |
| 长上下文 | 65536–200000 | 64 | 已验证可跑，单独报 TTFT 与 prefill tok/s |

并发梯度：`--parallel 1 2 4 6 8`（客户端）× 每组 `-n` 取 4×并发，**每个配置至少重复 3 次取中位**。

### 7.3 必须抓的指标

`--stream` 必加，否则拿不到 TTFT/TPOT。

| 类别 | 字段 |
|---|---|
| 延迟 | TTFT p50/p95/p99、TPOT p50/p95/p99、ITL p99、E2EL p50/p95/p99 |
| 吞吐 | Output tok/s（最贴近成本）、Total tok/s、Req/s、**Goodput（SLO 内有效吞吐）** |
| 投机 | `Spec. Accept Rate`、`Avg Decoded Tok/Iter` ← 判断 MTP 是否工作 |
| 缓存 | `KV Cache Hit Rate (%)` ← 判断 prefix cache |
| 资源 | 两卡显存分别记、MemAvailable、swap used、`expert cache slots` |
| 服务端 | `/slots` 条目数（确认槽位真的变了） |

三个必看红线：
- **p99 涨而 p50 正常** = 排队/抢占，不是算力不足
- **专家缓存 slots 下降** = VRAM 被 KV 挤掉，解码会变慢
- **swap used 上升** = 内存不够，立刻停

### 7.4 建议的配置矩阵（重启次数最少）

`parallel` 只在重启时生效，所以按配置分组跑，别逐用例重启：

1. 基线：现状（parallel=1，不改）→ 重跑三组形态，拿到可信基线
2. 改 B1+B2（`ple-io mmap` + `prefill auto:32768`）→ 同矩阵复测
3. 改 B3（专家上双卡）→ 同矩阵复测
4. 在 3 的基础上开 `parallel 4` → 看批处理是否终于开始正收益

每组之间只改一项，其余不动。

## 8. 风险清单

| 风险 | 触发条件 | 处置 |
|---|---|---|
| OOM / 换页 | 可用内存 < 6 GB（watchdog 阈值） | 已有 watchdog，会杀压测；先做 B1 |
| 压测污染基线 | 用 random 数据集出交付数字 | 禁止 |
| ESP 悄悄开启 | 配置里 `sampling.experimental_speed_projection: true` 被遗忘 | 每次 A/B 后复位，并在报告里注明开关状态 |
| 端口暴露 | 8800 绑 0.0.0.0，公网 13270 直达 | 至少加 iptables 限制源网段 |
| API Key 明文 | 内网 HTTP 明文传输；Key 出现在 `ps` 输出里 | 已见 Key 出现在压测进程命令行，建议改用环境变量传参 |
| 服务重启抖动 | 每次改配置重启，加载约 3 min | 低峰期操作，一次改一项 |
