## 二、压测方法与口径

```bash
docker exec strata /data/tools/venv-evalscope/bin/evalscope perf \
  --model qwen3.8-flash-next-iq3_xxs \
  --url http://127.0.0.1:8080/v1/chat/completions \
  --api openai --api-key "$(cat /etc/strata/api_key)" \
  --tokenizer-path /data/Strata-data/tokenizer-qwen \
  --dataset random --min-prompt-length N --max-prompt-length N \
  --min-tokens M --max-tokens M \
  --parallel 2 4 6 8 -n 8 16 24 32 --stream \
  --outputs-dir /data/bench --name <name>
```

- 两个容易踩的点：evalscope 的 venv **只能在容器内**运行（shebang 指向 `/data/tools/...`）；随机文本生成必须给 `--tokenizer-path`，而 Strata 自带的 `tokenizer.json` 是自研格式（`{"model":"gpt2","pre":"qwen35",...}`），HF 的 `AutoTokenizer` 直接报 `KeyError: 'added_tokens'`。已额外拉 `Qwen/Qwen3.8-Flash-Next` 的 HF tokenizer 到 `Strata-data/tokenizer-qwen`（23MB）。
- 场景：输入 512/1024/4096/8192，输出 512/256/256/256；并发 2/4/6/8；每档请求数 8/16/24/32。全部 stream 模式，取 TTFT / TPOT / 吞吐。
- 两轮：`parallel=1`（默认）与 `parallel=4`（配置加 `"parallel": 4` 后重启，测完恢复）。

## 四、结论

1. **`parallel=1` 下并发毫无意义**：总输出吞吐是水平线（109→102、86→81、61→62、48→49），TTFT 随并发线性上涨（512 输入从 4.3s 到 28.0s）。所有请求排一条队，一个槽位依次解码。
2. **`parallel=4` 才把并发变成吞吐**：+19%~+64%，短提示收益最大、长提示最小——因为长提示的预填本身就吃满槽位，4 个槽位也顶不住 8 个 8K 提示同时预填。
3. **代价是单流变慢**：TPOT 从 8–10ms 涨到 13–54ms，即单请求解码从 100–125 tok/s 降到 18–75 tok/s。这是 4 个槽位分同一份算力的必然结果。
4. **槽位不是无限加**：并发 6/8 时 TTFT 重新变长（4 个槽位占满后照样排队）。
5. **显存代价很小**：`parallel=4` 只多用约 4GB（26.6/32.7 → 28.8/34.9 GB），专家缓存仍是 12288 个 / 17.72 GiB，没被挤掉——因为 KV 走的是 `--kv-resident 32768` + 内存流式。
6. **零失败**：32 组、448 个请求，全部成功，无超时、无 OOM。

## 五、建议
| 使用场景 | 建议配置 | 理由 |
| --- | --- | --- |
| 单人用 / 长文档分析 | `parallel=1` | TPOT 8–10ms，单流最快 |
| 3–5 人同时用 | `parallel=4` | 吞吐 +36~64%，TTFT@2 从 4s 降到 1s |
| ≥6 人同时用 | `parallel=6` 或 `8`（显存够，实测 4 槽位仅 +4GB） | 需再测一轮确认长提示下的退化幅度 |
| 长提示为主（>4K） | 优先看预填能力，槽位收益有限 | 8K 提示下 +19% 已是上限 |

## 六、长会话多轮与上下文上限（2026-11-02 10:20–10:30 补测）

脚本：`Strata-data/multiturn_test.py`（多轮）、`Strata-data/ctx_scale.py`（新鲜长上下文 / 并发长请求），用容器内 venv 跑。

### 6.1 先确认溢出行为

单请求构造 270,000 token：

```
HTTP 400（53 ms 内返回，没做任何计算）
{"error":{"type":"invalid_request_error","message":"request exceeds the context window:
 prompt (270017 tokens) + max tokens (32) exceeds the context (262144);
 requests are never truncated. Send a smaller max_tokens (at most 0 here),
 or add \"fit_max_tokens\": true to the model's strata-<model>.json to shorten it to the room left (#545)"}}
```

**不会静默截断，不会 OOM，不会崩服务**。错误信息还给了官方开关：`fit_max_tokens: true` 可让服务端自动缩短到剩余空间（本次未启用、未测）。

### 6.2 多轮 A：每轮 4K，12 轮

| 轮 | prompt_tokens | 新增 | TTFT | 解码 |
| --- | --- | --- | --- | --- |
| 1 | 4,123 | 4,123 | 1.95s | 107.5 tok/s |
| 3 | 12,421 | 4,123 | 1.67s | 127.6 |
| 6 | 24,871 | 4,121 | 1.70s | 169.1 |
| 9 | 37,321 | 4,123 | 1.74s | 159.8 |

**关键：每轮"新增 token"恒等于 4,123** —— 对话前缀被完整缓存，每轮只预填新说的话。所以 TTFT 不随轮数增长（1.95s → 1.77s），单轮墙钟稳定在 1.9 秒。多轮对话在这种模型上非常便宜。

预填吞吐稳定在 4.2–5.2K tok/s；**解码从 104.6 掉到 87.0（-17% @200K）**——这是长上下文唯一明显的性能衰减。

### 6.5 并发长请求（parallel=1）

| 场景 | 各请求 TTFT | 总墙钟 | 成功 |
| --- | --- | --- | --- |
| 4 × 64K | 14.4 / 28.8 / 42.9 / 57.2 s | 57.8s | 4/4 |
| 4 × 200K | 41.3 / 81.1 / 121.0 / 160.9 s | 161.9s | 4/4 |

严格串行：总墙钟 ≈ 4 × 单个耗时。**长上下文 + 并发 = 排队到分钟级**（最后一个 200K 请求等了 161 秒）。

### 6.6 结论

1. **不会"爆"**：超限一律 400，明确不截断、不静默丢弃、不 OOM；测试全程服务零错误（日志里只有两次预期内的 400）。
2. **多轮对话几乎不衰减**：前缀缓存命中，TTFT 只跟"本轮新增 token 数"相关，与历史长度无关。
3. **上限按轮数算**：24K/轮 只能 10 轮；4K/轮 可以 60 轮左右。客户端要自己管历史长度，或开 `fit_max_tokens`。
4. **参数衰减很小**：新鲜 200K 提示解码 -17%；多轮 B 的 TTFT +29%。都属可用范围。
5. **长上下文并发是硬伤**：`parallel=1` 下 4 个 200K 请求要 2.7 分钟。要支撑这类业务必须提高 `parallel`，但内存/显存要另算（KV 现在走内存流式，45G 已用）。

### 6.7 建议

| 场景 | 做法 |
| --- | --- |
| 多轮对话 | 客户端裁剪历史到 ~10 万 token 以内；或开 `fit_max_tokens: true` 让服务端自动缩短 |
| 超长单文档（200K） | 可用，39 秒预填；但并发时排队严重 |
| 长文 + 多人 | 提高 `parallel`（4 起），并监控内存（每请求 KV 约 2.8GB 走内存） |
| 客户端错误处理 | 必须处理 HTTP 400 的 `invalid_request_error`，不要当网络错误重试 |

### 7.6 ESP 的行为影响（需要业务确认）

ESP 的用途是削弱一个拒答方向，**输出会和平常不同**（更少拒答、措辞可能变化）。本次只测了性能，没有做质量评测。建议上线前用真实业务提示词做一次 A/B，确认内容风格可接受。它可以通过配置每会话关闭（`"sampling": {"experimental_speed_projection": false}`）。

## 八、内存安全边界与那次宕机（事故复盘）

### 8.1 内存预算公式

```
常驻 = 专家层（40 GB）+ PLE n-gram 表（--ple-io ram，29 GB）≈ 69 GB
每并发请求 KV ≈ 2.8 GB（200K 上下文，int8，流式落内存）
安全上限：69 + 并发 × 2.8 ≤ 85 GB   →   200K 场景最多并发 4；64K 场景（≈1 GB/请求）可到 8
```

### 8.2 事故

`parallel=8` + 8 个 200K 并发请求 → 69 + 22 = 91 GB，叠加页缓存后进入 swap，系统假死：
sshd 只有 TCP 握手、无 banner，模型服务不响应，持续约 50 分钟未自愈。逐级测试里 `parallel=2`×200K（83 秒，2/2 成功）与 `parallel=4`×64K 都正常，问题出在 6/8 档 × 200K。

**结论：这台 94GB 的机器上，长上下文并发不能超过 4**；且 `parallel` 的取值必须按上面公式算，不能照搬"短提示并发"的经验值。

### 8.3 看门狗（后续压测都用）

`/root/offline_check/watchdog.sh` 每 15 秒检查，满足任一条件即杀掉压测并保留现场：

- `/health` 非 200
- 可用内存 < 6 GB
- swap 使用 > 1 GB
- load average(1m) > 80

实测触发过一次（关 ESP 重启时 health 短暂 000），说明它对"计划内重启"会误报，正式压测时应先暂停它或放宽为连续 3 次失败。

## 九、系统重装后的恢复步骤（2026-11-02 13:39 实测）

### 9.1 判断数据还在不在

```bash
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT     # vdb 是否还是 ext4
blkid /dev/vdb                                  # 有没有文件系统签名
```

判据：`vdb` 存在且 `blkid` 有 `TYPE="ext4"` + UUID → 数据盘没被格式化，只差挂载；`blkid` 为空 → 被格过，要走数据恢复；设备不存在 → 盘被删，只能重传。

### 9.2 挂载并持久化

```bash
mkdir -p /data && mount /dev/vdb /data
df -h /data && ls /data                         # 用量与重装前一致 = 数据完整
echo 'UUID=40b57a09-4530-4486-9d46-c5e717ad32c6 /data ext4 defaults,noatime,nofail 0 0' >> /etc/fstab
mount -a && findmnt /data                        # 验证 fstab 正确
```

用 UUID 而不是 `/dev/vdb`：设备名会变，UUID 不会，避免把别的盘挂到 /data。

### 9.3 重建系统盘上丢失的东西

| 丢失项 | 恢复方式 |
| --- | --- |
| docker 镜像 | `docker load -i /data/strata-qwen38-cuda12-1.0.tar`（41 秒，**没删离线包 tar 是关键**） |
| compose 二进制 | 重新下载 v2.29.7 单文件到 `/usr/local/bin/docker-compose` |
| `/etc/strata/api_key` | 从配置 JSON 的 `api_key` 字段重建（`chmod 600`） |
| `/root/offline_check/` 脚本 | 从仓库重新上传 |
| `/etc/fstab` 的 /data | 9.2 已补 |

然后 `cd /data/compose/strata && docker-compose up -d`，68 秒 healthy。

### 9.4 恢复后必须验证的三件事

```bash
curl -s http://127.0.0.1:8800/health                      # loaded/api_key 都要 true
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $(cat /etc/strata/api_key)" \
     http://127.0.0.1:8800/v1/models                      # 200
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8800/v1/models   # 401
```

这次就是漏了第 2/3 步：`/etc/strata/api_key` 没恢复，第一次重跑压测 4 秒就因 `FileNotFoundError` 退出，却没有任何报错提示。**恢复完成后立刻做一次带 Key 的请求**，比看容器状态可靠。
