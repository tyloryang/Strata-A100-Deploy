## 0. 参数分五层，改之前先确认在哪一层

| 层 | 写在哪里 | 谁读取 | 改完怎么生效 |
|---|---|---|---|
| **容器层** | `docker-compose.yml` + `.env` | docker compose | `docker-compose up -d`（会重建容器） |
| **服务层** | 配置 JSON 的顶层键（`args`、`env` 之外的） | `serve/server.py` | 重启容器 |
| **引擎层** | 配置 JSON 的 `args` 数组和 `env` 对象 | `engine-cuda12/strata` | 重启容器 |
| **请求层** | 每个 API 请求的 JSON body | `server.py` 逐个请求处理 | 立即生效，只影响这一个请求 |
| **压测层** | evalscope 命令行、`scripts/` 里的脚本 | 压测工具 | 立即生效 |

服务层会替引擎补几个参数，所以**最终的引擎命令行比 `args` 多几项**。启动日志 `engine started:` 那一行就是最终版本，本机实测是在 `args` 之后追加了：

| 追加的参数 | 来自 | 说明 |
|---|---|---|
| `--serve` | server.py 固定加 | 以服务模式运行引擎（长驻、按请求处理） |
| `--layer-split auto` | 顶层 `layer_split` + `gpu` 有多张卡 | 见 §1 `layer_split` |
| `--batch N` | 顶层 `parallel` | **只有 `args` 里没写 `--batch` 时才追加**；推荐配置在 `args` 里已经显式写了 `--batch`，所以这里不会重复 |

| 键 | 本机值 | 是什么 | 为什么这么设 / 注意事项 | 状态 |
|---|---|---|---|---|
| `_说明` `_注意` `_代价` | 文字 | 本仓库加的说明字段 | 以 `_` 开头，server.py 不认识也不使用；setup 重跑时会保留它不管理的键 | ⚪ |
| `exe` | `/data/Strata/engine-cuda12/strata` | 引擎可执行文件（容器内路径） | `engine-cuda12/` 是 CUDA 12 构建版，官方称"experimental CUDA 12 engine"。A100（sm80）+ 驱动 550 用它 | ✅ |

| `log` | `/data/Strata/strata-iq3_xxs.log` | 引擎日志文件 | 比 `docker logs` 详细得多，**排障先看它**。改参数后用它确认引擎实际怎么理解的 | ✅ |
| `lib_dirs` | `/usr/local/cuda/bin`、`/usr/local/cuda/lib64` | 启动引擎前加到 `LD_LIBRARY_PATH` 最前面的目录 | 让引擎找到 `libcudart.so.12`、`libcublas.so.12`。server.py 只加实际存在的目录 | ✅ |
| `port` | `8080` | server 在**容器内**监听的端口 | 对外端口不在这里改：VM 的 8800 由 compose 决定，公网的 13270 由平台转发决定（见 §4） | ✅ |
| `host` | `0.0.0.0` | server 在容器内监听的地址 | 容器内必须是 `0.0.0.0`，docker 的端口映射才能连进来。日志里打印的 `127.0.0.1:8080` / `172.x.x.x:8080` 都**不是**对外地址 | ✅ |
| `cuda` | `12` | 声明这份配置用 CUDA 12 引擎 | setup 据此选择 `engine-cuda12/` 目录。真正决定跑哪个引擎的是 `exe`，单改这个值不会换引擎 | ✅ |
| `gpu` | `[0, 1]` | 用哪几张卡（按 `nvidia-smi` 编号） | 写多张卡就是**层拆分**（模型的层分到各卡上） | ✅ |
| `gpus_asked` | `true` | setup 的标记：已经问过"要不要多卡一起用" | 防止下次启动再问一遍，对运行没有影响 | ⚪ |
| `layer_split` | `"auto"` | 层拆分点 | `auto` 按各卡空闲显存自动分。也可以写数字，表示**后一张卡从第几层开始**（模型 48 层，`"24"` 就是均分），不是"每张卡几层"。本机 `auto` 解析为 24：CUDA0 跑第 0–23 层，CUDA1 跑第 24–47 层 + 输出头 + MTP 草稿层。v12–v14 实测改成 28 没有收益 | ✅ |
| `parallel` | `4` / `8` | 并发槽位数 | **引擎没有 `--parallel` 参数**，server 把它翻译成 `--batch N`（`PARALLEL_MAX = 8`）。写 1 或不写 = 一次只处理一个请求。`args` 里已经写了 `--batch` 时 server 不再翻译，**两处必须保持一致**。验证方法：数 `/slots` 返回几条 | ✅ |
| `api_key` | 占位符 | 鉴权密钥 | `/v1/*`、`/slots`、`/metrics` 都要带 `Authorization: Bearer <Key>`。可以写多个（逗号分隔或数组），方便单独吊销某个客户端。真实值放 `/etc/strata/api_key` 和配置文件，**两者权限都要 600，不要入库、不要贴到聊天里** | ✅ |
| `open_browser` | `false` | 启动后是否自动打开浏览器 | 容器里没有浏览器，必须是 `false` | ✅ |
| `reasoning_effort` | `"medium"` | 请求没指定时的默认思考强度 | 可选 `none` / `low` / `medium` / `high`，不设时模型默认 `high`。请求自己带的值优先 | ✅ |
| `reasoning_budget_tokens` | `4096` | 思考最多用多少 token | 到上限时 server 插入一句收尾语和 `</think>`，让模型开始作答；收尾语计入输出 token。⚠️ **请求的 `max_tokens` 小于这个值时，输出可能全部被思考占满、没有答案**（压测里 `max_tokens=100` 就出现过空回答） | ⚠️ |
| `reasoning_close_retry` | `true` | 兜底：回复结束时还在思考、既没答案也没工具调用，就补一个 `</think>` 再续写一次 | 官方默认关闭（issue #1053）。开着能减少"只想不答"的空回答 | ✅ |
| `fit_max_tokens` | `true` | 请求的 `max_tokens` 超出上下文剩余空间时，自动缩短到放得下 | 官方默认就是 `true`。**提示本身就超长时仍然返回 400**，引擎从不截断提示 | ✅ |
| `sampling.temperature` | `1.0` | 请求没给时的默认温度 | 1.0 / 0.95 / 20 是 Qwen 思考模式的推荐值。温度高会让结果不可复现，还会压低投机解码的接受率。**压测要在请求里显式固定**（见 §5） | ✅ |
| `sampling.top_p` | `0.95` | 默认 top-p | 同上 | ✅ |
| `sampling.top_k` | `20` | 默认 top-k | 引擎最多保留 64 个候选 | ✅ |
| `sampling.experimental_speed_projection` | `true` | 已加载 ESP 控制向量时，默认对请求开启 | 每个请求可以传 `"experimental_speed_projection": false` 关掉。**ESP 不是提速功能**，务必先读 §2.7 | ⚠️ |

## 2. 引擎层：`args` 数组

### 2.1 模型文件

| 参数 | 本机值 | 是什么 | 注意 | 状态 |
|---|---|---|---|---|
| `--pack` | `/data/Strata-data/packs/iq3_xxs` | 预转换包目录：`experts.bin`（42 GB 专家）、`dense.bin`（1.4 GB 稠密权重）、`tokenizer`、索引 | pack 和量化档绑定，**IQ3_S 不能复用 IQ3_XXS 的 pack**（见[待实施-其他模型](../待实施-其他模型/IQ3_S.md)） | ✅ |
| `--native` | 第 1 个 GGUF 分片（47 GB） | 原生量化路径，模型主体权重从这里读 | | ✅ |
| `--ple-gguf` | 第 2 个 GGUF 分片（28.8 GB） | PLE / n-gram 表（`per_layer_token_embd`，约 26.8 GiB） | 这是**按 token 查表的嵌入表，不是专家权重**。帮助原文：`WITHOUT IT LAYER 1's PLE IS SILENTLY SKIPPED`。**不给不会报错，但模型能力受损**，必须给。所有 GSQ-RCO 量化档共用同一个文件（sha256 `316b46f3…`） | ✅ |
| `--expert-profile` | `/data/Strata/data/expert-profile.bin` | 专家热度画像（24576 个按热度排序的"层-专家"对） | 启动时按它把专家预装进显存，不用等第一次用到才装 | ✅ |
| `--mtp` | `/data/Strata-data/mtp/rt` | MTP 草稿层（模型自带的多 token 预测头，用来做投机解码） | 约占 835 MiB 显存，放在最后一张卡（CUDA1）上 | ✅ |

### 2.2 专家放在哪里（决定解码速度的核心）

先说结论：**本机全部 24576 个专家都在显存里**（每张卡缓存自己那 24 层的 12288 个）。证据有三条：
- 日志：`layer split: CUDA1 runs layers 24-47, expert cache 12288 slots (22.24 GiB), 12288 of its 12288 profiled pairs`
- 日志：`layer split: 100% of the experts resident`。源码含义是"所有层-专家对都在某张卡的显存缓存里"
- Web 监控页："显存中的专家 24,576（40.0 GB）"

所以**显存没占满是正常的**：专家已经全部装下，剩余的显存没有东西可放。

> 早期文档写的"专家缓存只有 12288/24576（50%）""100% resident 指的是在主机内存里"**是误读**，已在本次整理中更正。
> v10 去掉 `--kv-resident` 时 CUDA1 的缓存降到 9203 个、总驻留率降到 87%，也反过来印证了平时是 100%。

| 参数 | 本机值 | 是什么 | 为什么这么设 / 实测 | 状态 |
|---|---|---|---|---|
| `--expert-cache` | `auto` | 显存里放多少个专家 | `auto` = 空闲显存减去预留（默认 700 MiB，`--vram-reserve-mib` 可改）能放多少就放多少，写完各槽位后会再检查一次，放不下就缩小。本机日志：`expert cache auto: 33.11 GiB free, 700 MiB reserved -> 12288 slots`（单卡） | ✅ |
| `--resident-experts` | 启用 | 低内存模式 = `--mmap-experts` + `--resident-cpu-experts`：专家从文件映射；**只把"显卡不持有的专家"和"读 prompt 时从显存借出去的那些槽位对应的专家"拷进内存**（尽量锁页），并给系统留 4 GiB 余量；放不下就退回纯 mmap | 不开时，引擎默认把**全部约 40 GiB 专家**拷进锁页内存。本机专家全在显存，需要的内存副本只有借出那部分（日志 `resident 12.65 GiB, pinned 12.65 GiB`）。实测：引擎内存占用（RSS）61.7 → 39.3 GiB，可用内存 30.6 → 57.1 GB，显存不变。帮助原文：同一放置下答案与 `--mmap-experts` 相同 | ✅ |

### 2.3 读 prompt（预填）

| 参数 | 本机值 | 是什么 | 为什么这么设 / 注意 | 状态 |
|---|---|---|---|---|
| `--prefill` | `auto:32768` | 读 prompt 时每块多少 token | `auto` 的上限是 8192，`auto:32768` 放宽到 32768（日志 `prompt chunk auto: 32768 tokens, a 96-slot ring`）。块越大，每层专家在一块里只读一次，长 prompt 越快。代价有三个：① 缓冲更大，要从专家缓存**借**显存槽位，借出的专家要在内存留副本（就是上面那 12.65 GiB）；② 层拆分会重新平衡，CUDA0 显存从 28.9 涨到 37.8 GB；③ **官方注明 CUDA 上块大于 8192 时结果不是逐位一致**（最后几位有差异）。setup.py 的注释是"96 GB 内存上 +21–35%，32 GB 上约慢 3 倍"。**本机没做 A/B** | ⚠️ |

### 2.4 投机解码（MTP）

| 参数 | 本机值 | 是什么 | 注意 | 状态 |
|---|---|---|---|---|
| `--spec` | `4` | MTP 草稿层每个验证窗口最多提议几个 token | 遇到上下文里的重复内容（suffix-draft）时窗口可以再 +2，上限 8。Web 页"关于"显示为"MTP 草稿最多 3 个 token" | 见下 |
| `--spec-min-p` | `0.5` | 草稿层置信度门槛，把握低于这个值就不再往窗口里加猜测 | 越低越激进、越容易猜错重算。`setup.sh --calibrate` 能为本机测这个值，但 ⚠️ **本机跑 `--calibrate` 清空过 venv**（离线装不回依赖），不要在这台机器上跑 | 见下 |

**这两个参数什么时候生效**：
- **一个请求独占时生效**。单请求解码约 105–111 tok/s，主要就来自它。
- **多个请求同时进 batch 槽位后不生效**。层拆分下槽位默认按卡分组做流水线，而流水线分组不跑槽位草稿，日志里槽位请求都是 `drafts accepted 0 of 0`。想在批量时也用草稿，见 §2.8 的 `--batch-mtp`。

### 2.5 上下文与 KV 缓存

| 参数 | 本机值 | 是什么 | 为什么这么设 / 实测 | 状态 |
|---|---|---|---|---|
| `--max-context` | `262144` | 每个会话最多多少 token | 引擎默认只有 4096。262144 是模型的训练长度。提示 + `max_tokens` 超过上限时返回 400，**从不截断**（实测 270K 提示 53 ms 内拒绝） | ✅ |
| `--kv` | `int8` | KV 缓存精度 | `int8`：每 64 个值共用一个 fp16 缩放，1056 字节/格，setup 的默认值。其他选项：`q4_0` 省一半内存，长文档精度略降（官方测得困惑度 +8–12%）；`k8v4`（K 用 int8、V 用 4 bit，816 字节/格）省 23%，比 `q4_0` 精确。本机没测其他选项 | ✅ |
| `--kv-resident` | `32768` | KV 流式：每个注意力（QSA）层只在显存留 32768 格，**完整 K/V 放在锁页内存**，腾出的显存给专家 | 上下文 ≤ N 时不流式；最小 20480；`0` = 全放显存。**内存代价**：官方约 13.7 KB/token，262144 上下文约 3.6 GB/会话（setup 也打印 `KV cache lives in RAM (3.6 GB)`），**每个 batch 槽位各有一份**。本机日志里显示的 1.55 GiB 推断是单张卡那一半。**实测不能去掉**：v10 去掉后每槽显存从 0.51 涨到 1.86 GiB，显存被推到 99%，专家驻留率降到 87%，并发 8 的聚合吞吐从 55.9 崩到 36.5 tok/s | ✅ 必留 |

> 如果确实想把 KV 搬回显存（减轻内存压力），必须**同时**把 `--max-context` 降下来，例如 65536。这个组合**没有测过**，列在[压测文档 §8](压测文档.md#8-下一轮实验计划)的待验证项里。

### 2.6 PLE / n-gram 表的读法

| 参数 | 本机值 | 是什么 | 为什么这么设 / 实测 | 状态 |
|---|---|---|---|---|
| `--ple-io` | `mmap` | 这张约 26.8 GiB 的表怎么读 | 三个选项：<br>• `direct`（引擎默认）：无缓冲直接读 SSD，表不进内存、不进页缓存<br>• `mmap`：映射文件，用到的行进系统页缓存，内存紧张时可以被回收<br>• `ram`：启动时整张表锁进内存（约 28 GiB，**不可回收**），读 prompt 时不碰磁盘<br><br>**本机实测**：`ram` 和 `mmap` 解码没有差异（v9 对 v5：55.9 对 56.4 tok/s），但 `ram` 让可用内存一度跌到 652 MiB、会话缓存开始拒绝停放。所以选 `mmap`。<br>setup 当初自动选了 `ram`，原因是它把虚拟盘 vdb 判成了"旋转盘"。官方在内存充裕的机器上测得 `ram` 读 prompt 快 16–30%，但前提是内存放得下 | ✅ |

### 2.7 ESP 控制向量（先读这一节）

| 参数 | 本机值 | 是什么 | 状态 |
|---|---|---|---|
| `--control-vector-scaled` | `…/Qwen3.8-Flash-Next-experimental-speed-projection.gguf:1.0` | 加载一个控制向量文件（llama.cpp 格式，约 480 KB），强度 1.0。`--serve` 下每个请求可以单独开关 | ⚠️ |
| `--control-vector-layer-range` | `4 44` | 作用在第 4–44 层（含两端，共 41 层；日志 `layers 4..44 (41 steered)`） | ⚠️ |
| `--cvec-mode` | `project` | 投影模式：`h -= s·(h·v)·v`，从隐藏状态里**去掉**向量 v 方向的分量。另一个选项 `add`（默认）是 `h += s·v` | ⚠️ |
| `--cvec-dir` | `per-layer` | 每一层用自己那层的方向向量。另一个选项 `single:L` 是所有层都用第 L 层的方向 | ⚠️ |

**它到底做了什么**（官方 `docs/DETAILS.md`「Experimental speed projection」一节）：
- 名字叫"实验性速度投影"，但官方说明里明确写了：这个向量是一个**拒答方向投影（refusal-direction projection）**。开启后模型**拒绝请求的情况大幅减少**，等于去掉了一层安全行为；官方写明开启时模型写出的内容由使用者负责。
- 它**不会让 token 变快**，反而每个 token 慢 0.2–0.4%，也会让普通回答有细微变化。
- 本机 ESP 开/关的 A/B 差异是 +1.1%，在噪声范围内，和这一点一致。
- 关掉时输出和原模型逐 token 一致；开关切换会清空一次会话缓存。

**怎么处理（需要你来定）**：
- **如果当初开它是为了提速**：应该关掉。有两种办法：
  - 把 `sampling.experimental_speed_projection` 改成 `false`：向量仍然加载，但默认不用，单个请求还能传 `true` 打开。
  - 直接删掉上面 4 个参数：根本不加载。
- **如果确实需要它**：保留，但**所有压测和对外报的数字都要标"ESP-on"**，不能当成原模型的成绩。Web 监控页会给每个请求打"ESP"或"stock"标记。
- 推荐配置**暂时保持开启**，因为 v6 的实测数据就是在开启状态下测的。改不改由你决定。

### 2.8 并发槽位（batch）

| 参数 | 本机值 | 是什么 | 为什么这么设 / 实测 | 状态 |
|---|---|---|---|---|
| `--batch` | `4`（推荐）/ `8` | 最多 N 个请求**一起**解码。每个槽位有独立会话状态，各占约 0.51 GiB 显存 × 2 张卡 | 层拆分下引擎默认把槽位按卡分组做流水线：4 槽是 2 组×2，8 槽是 2 组×4（日志 `--batch-groups auto: 2 groups of ...`）。**实测**：长提示（2000 token）下 4 槽每个并发点都最好，并发 8 时 TPOT 45.9 ms，8 槽是 94.7 ms；短提示（800 token）高并发时 8 槽聚合更高（89.3 对 80.7 tok/s），但单流延迟差一倍。**没有免费扩容**：开 4 槽后并发 8 时单流只剩约 22 tok/s，单槽时约 110 | ✅ |

**推荐配置故意没写的相关参数**：

| 参数 | 是什么 | 为什么不用 |
|---|---|---|
| `--batch-mtp` | 每个槽位每轮额外验证 1 个 MTP 草稿 | 层拆分 + 默认流水线时，引擎会打 `WARNING: --batch-mtp is off` 并自动关掉它。要生效必须加 `--batch-groups 1` 或 env `STRATA_BATCH_MTP_SERIAL=1`，改成串行窗口：两张卡轮流干活，而且每个槽位占 2 行，一个窗口最多只放得下 4 个槽。**实测串行 + batch-mtp 比流水线差 16–20%**（v7/v8），TPOT 差 2.9 倍 |
| `--batch-groups G` | 层拆分时把槽位分成 G 组做流水线 | 不写就是 `auto`（每张卡一组），本机就是这样跑的 |
| `STRATA_PIPED_MTP=1` | 流水线分组里**也跑**槽位草稿 | **0.2.7 才有，本机 0.1.45 没有**。见 §7 |

### 2.9 会话缓存

**作用**：多个长会话交替发请求时，把暂时不用的会话状态存进内存，下一轮接着用，不必把整段 prompt 重读一遍。存的是运行状态、检查点、已用的 K/V 页和草稿层 K/V，**只占主机内存，不占显存**。

| 参数 | 本机值 | 是什么 | 默认值 | 状态 |
|---|---|---|---|---|
| `--conversation-cache-mib` | `16384` | 停放会话的内存预算（MiB） | 0.1.45 帮助写的是"0 = off"；官方 main 是"不传则按空闲内存自动定、上限 8192，传 0 关闭"。⚠️ **本机 v12 设 0 后仍然停放了 7 个会话（8.6 GB）**，原因没查明，不要指望设 0 就能关掉 | ✅ |
| `--conversation-cache-slots` | `4` / `8` | 最多停放几个会话 | 4。建议和槽位数相同 | ✅ |
| `--conversation-cache-min-tokens` | `4096` | 少于这么多 token 的会话不停放，免得短请求挤掉长会话 | 0（全部停放） | ✅ |
| `--conversation-cache-park-gain` | `2048` | 同一会话比已存的那份副本再前进 2048 token，才重新存一次；避免每轮都写一份大快照、下一轮又丢掉 | 0（每轮都存） | ✅ |
| （未设）`--conversation-cache-min-free-mib` | 默认 2560 | 空闲内存低于这个值时跳过停放 | 2560 | — |

**要不要开**：
- **生产上的多轮对话、Claude Code / Codex 这类 agent**：开着有价值。它们每轮都带很长的系统提示和历史，按本机约 1.5K tok/s 的读速，一个 20K 上下文重读一次要十几秒。
- **压测**：要关掉。压测请求的 prompt 各不相同，复用率是 0（实测每条都是 `reused_kv_bytes=0`），而且停放的会话一轮轮累积，到 v11 已经占满 13.3 GB，把后跑的轮次拖慢（见[压测文档](压测文档.md)方法学缺陷三）。

## 3. 引擎层：`env` 环境变量

| 变量 | 本机值 | 是什么 | 本机情况 | 状态 |
|---|---|---|---|---|
| `STRATA_ROUTE_TAIL_SKIP` | `0` | 跳过"不在显存里、并且这一轮所有 token 都把它排在第 7 名或更靠后"的专家，既不拷贝也不计算。CUDA 上默认 7，0 = 关闭 | **在本机设 0 和设 7 结果完全一样，不需要再测**。原因：① 全部专家都在显存，根本没有"不在显存的专家"可以跳过（源码注释：every expert in VRAM 时"nothing to do"）；② 开了 `--batch` 时这个功能默认也关闭。官方说的 +10–20% 只出现在**专家装不下的 12–16 GB 小显存卡**上。v12/v13 改成 7 后没看到变化，和这一点一致。保留 0 无害：万一以后专家装不下显存，0 能保证答案不受跳过影响 | ⚪ |
| `STRATA_RESIDENT_HEADROOM_GIB` | `2` | `--resident-experts` 启动时给系统留多少 GiB 空闲**内存**（不是显存） | 默认 4。改小 = 允许往内存里多拷专家，但离内存耗尽更近。本机需要的内存副本只有 12.65 GiB，远用不到上限，2 和 4 在这里没有实质差别；内存紧张时可以改回 4 | ✅ |
| `MALLOC_MMAP_THRESHOLD_` | `16777216` | glibc 参数：≥16 MiB 的内存分配直接用 mmap，释放后立即还给系统；同时关闭 glibc 自动调整这个阈值 | 作用是减少预填缓冲、会话快照这类大块内存反复分配造成的碎片，避免进程内存只涨不降。**和 PLE 表的 mmap 无关**：那是文件映射，不经过 malloc。代价是大块分配多一些系统调用和缺页。没做过 A/B | ✅ |
| ~~`STRATA_ADAPT_OVERLAP`~~ | 已从推荐配置删除 | 让自适应专家层的换入拷贝和下一个验证窗口重叠进行 | **只在单卡生效**。本机日志明确写了 `STRATA_ADAPT_OVERLAP=1 is off: not on a layer split`。它和 `--adapt-async` **不是一回事**（两者互斥）。早期文档说它导致结果不可复现，是把它和 `--adapt-async` 混淆了 | ⚪ |
| ~~`STRATA_ADAPT_OVERLAP_RESIDENT`~~ | 已从推荐配置删除 | 上一项在 `--resident-experts` 模式下的放行开关 | 上一项不生效，这一项也就无从生效 | ⚪ |
| `STRATA_BATCH_MTP_SERIAL`（历史） | 推荐配置不设 | 层拆分下让 `--batch-mtp` 以串行窗口运行 | v7/v8 用过，比流水线差 16–20% | — |

## 6. 压测层：evalscope perf 参数（本仓库用法）

```bash
docker exec strata /data/tools/venv-evalscope/bin/evalscope perf \
  --model qwen3.8-flash-next-iq3_xxs \
  --url http://127.0.0.1:8080/v1/chat/completions \
  --api openai --api-key "$(cat /etc/strata/api_key)" \
  --tokenizer-path /data/Strata-data/tokenizer-qwen \
  --dataset random --min-prompt-length 2000 --max-prompt-length 2000 \
  --min-tokens 100 --max-tokens 100 \
  --parallel 1 2 3 4 6 8 -n 4 8 12 16 24 32 --stream \
  --outputs-dir /data/bench --name <名字>
```

| 参数 | 是什么 | 注意 |
|---|---|---|
| `docker exec strata …/venv-evalscope/bin/evalscope` | 在容器里运行 evalscope | 这个 venv 只能在容器里跑（解释器路径指向 `/data/tools/...`） |
| `--model` | 请求里的模型名 | |
| `--url` | 压测目标 | 在容器里跑，所以用容器内的 `127.0.0.1:8080`；从宿主机跑要用 `8800` |
| `--api openai` | 用 OpenAI Chat Completions 协议 | |
| `--api-key` | 鉴权密钥 | 从文件读，不要写死在命令里 |
| `--tokenizer-path` | 生成随机文本、统计 token 用的分词器 | 必须用 HF 格式（`Strata-data/tokenizer-qwen`），Strata 自带的分词器 HF 读不了 |
| `--dataset random` | 随机 token 语料 | ⚠️ 随机文本让 MTP 接受率只有 2–5%、前缀缓存命中率恒为 0。**只适合做容量扫描，报吞吐要用自然文本**（`--dataset openqa` 或自建中文 jsonl） |
| `--min/max-prompt-length` | 输入长度（两个相等就是固定长度） | |
| `--min/max-tokens` | 输出长度 | 100 太短，体现不出投机解码的作用；比较批量模式时要加长输出（500–1000）的一组 |
| `--parallel 1 2 …` | 并发数梯度 | 这是**客户端并发**，和服务端配置里的 `parallel`（槽位数）不是一回事 |
| `-n 4 8 …` | 每个并发档发多少个请求 | 和 `--parallel` 一一对应，取并发数的 4 倍 |
| `--stream` | 流式请求 | 必加 |
| `--outputs-dir` / `--name` | 结果存放目录和这一轮的名字 | |

本仓库 A 轮口径还在请求体里固定了 `reasoning_effort=none`、`temperature=0`、`seed=1234`。evalscope 每次都会提示"Warmup is disabled"，仓库原文建议加预热参数（`--warmup-num`，参数名以 `evalscope perf --help` 为准）。

## 8. 本机没用、但经常被问到的参数

| 参数 | 是什么 | 为什么本机不用 |
|---|---|---|
| `--expert-cache-device1/2/3` | 用 CUDA1/2/3 额外缓存专家（"helper"卡） | 专家已经 100% 在显存，没有可多放的；而且 helper 卡必须是没跑层的卡，两卡层拆分下没有空闲卡 |
| `--expert-cache-per-layer` | 每层单独分配缓存槽 | 同上，专家已全部在显存 |
| `--peer-device` | 第二张卡当专家缓存层 | 和层拆分互斥 |
| `--trim-stage-weights` | 每张卡只加载自己那几层的稠密权重，省下的显存给专家缓存 | 要求 `layer_split` 写成具体数字；专家已经全在显存，省出来的显存用不上 |
| `--pipeline-windows 2` | 层拆分下两卡的验证窗口重叠 | NVIDIA 上需手动开启，而且**有 batch 槽位时会自动关闭**。本机开着 `--batch`，开了也不起作用 |
| `--kv-grow` | KV 按实际用到的长度占显存 | 只支持单卡 |
| `--vram-reserve-mib N` | 专家缓存计算时额外预留的显存 | 默认 700 MiB。显存溢出时调大 |
| `--memory-limit-mib N` | 告诉引擎容器的真实内存上限 | 容器看不到自己的内存限制时才需要 |
| `--prompt-cache N` | 会话检查点个数（每个约 118 MB，默认 6）；`0` 同时关闭检查点和会话停放 | 默认值即可。设 0 会让多轮对话每轮都重读 prompt |
| `--prompt-cache-tail` | 在 prompt 末尾附近多存一个检查点 | 帮助注明 single GPU，双卡下是否生效存疑，推荐配置已不用 |
| `--pool-workers N` | CPU 专家计算线程数 | 专家全在显存，CPU 池基本不参与解码。（迁移清单里写的 `--cpu-threads` 是其他引擎的参数，Flash-Next 引擎用的是这个） |

B=/data/qwen-strata
