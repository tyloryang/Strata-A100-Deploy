# 最新压测结果：双 A100 PCIe 40GB，2026-11-14

本页记录 **2026-11-14 新一台 AutoDL 双 A100-PCIE-40GB** 的 Strata 0.1.45 / Qwen3.8-Flash-Next IQ3_XXS 实测。此前 2026-11-02 的 SXM4 机器数据仍作为历史记录保留，两台机器的配置、负载和指标口径不同。

**针对 32K 新输入 TTFT，最终选定固定 `--prefill 8192` 的组合。单并发 8/8 成功，平均 TTFT 8.148985 秒，未达到 2 秒目标。** 这表示本轮按筛选规则选中并复验的配置，不表示所有长度、并发和语料上的全局最优。

这份文件使用 AutoDL 的 `/data/Strata`、`/data/Strata-data` 路径，**不是旧 SXM4 Docker 路径的直接替换件**。需要先按目标机器调整路径，并从自己的私有文件填入 API Key。引擎版本仍是 0.1.45，没有升级到 0.2.10。

快照保留 `sampling.experimental_speed_projection=true` 和 `env.experimental_speed_projection=false` 的原值；实测引擎 argv 没有加载 `--control-vector` 参数。本报告不凭这两个字段认定 ESP 已生效或带来性能收益。旧 SXM4 推荐配置的 ESP 默认关闭规则保持独立。

## 4. 两轮对比：无缓存新输入

请求显式使用 `temperature=0`、`reasoning_effort=none`、流式响应，输出上限 64 tokens。TTFT 计到首个非空正文。生产配置的默认 `medium` 思考模式可能有不同的首正文等待时间。

| 标称输入 / 客户端并发 | 第一轮 / 第二轮请求数 | 第一轮平均 TTFT 秒 | 第二轮平均 TTFT 秒 | 第二轮平均 TPOT ms | 第二轮整场输出 tok/s | 第二轮实际输入 tokens |
|---|---:|---:|---:|---:|---:|---|
| 32K / 1 | 3 / 8 | 8.7493 | **8.1490** | 13.284 | 7.1215 | 33599–34592 |
| 32K / 4 | 4 / 4 | 22.8086 | **21.4083** | 241.216 | 6.9140 | 33404–34307 |
| 64K / 1 | 3 / 1 | 15.9358 | **14.3944** | 15.507 | 4.1634 | 68891 |
| 128K / 1 | 3 / 1 | **28.7373** | 29.9612 | 14.908 | 2.0711 | 136435 |

第二轮四组共 **14/14 请求成功，服务端缓存命中均为 0**。两轮样本数与 seed 不同，表格是已有实测对照，不是配对统计检验；不能据此推断稳定 P99 或长期差距。128K 的第一轮结果更快，第二轮配置不是所有场景都提升。

第一轮完整矩阵覆盖输入 32768 / 65536 / 131072，客户端并发 1 / 4 / 6 / 8 / 16 / 32，共 18 组、207 个成功请求。第二轮最终组合只做了本表四组复验，**没有把第一轮的 18 组算作第二轮已验证覆盖**。

标称输入来自客户端 tokenizer。随机 token 解码为文本后会由 Strata 重新分词，并加入聊天模板，因此实际输入以每组 `*-usage.jsonl` 为准。usage 的首行是独立短预热，应排除。本轮没有把引擎总上下文容量改成 32768；容量上限与 32K 输入压测是两个参数。

## 5. 为什么输出吞吐只有 7.12 tok/s

32K 单并发八条总输出 512 tokens，整组耗时 71.895285 秒，所以 vLLM 整场输出吞吐为 `512 / 71.895285 = 7.121468 tok/s`。每条只有 64 个输出 token，而平均 TTFT 已达 8.149 秒，绝大部分时间在处理长输入。

该组平均 TPOT 为 13.284423 ms/token，倒数折算约 75.28 tok/s；它描述首 token 后的间隔，不等于整场输出吞吐。四并发 TPOT 实测升到 241.216 ms/token，也存在并发下的实际生成变慢，不能全部用统计口径解释。

32K 四并发还有一个计数差异：vLLM 对返回文本计数合计 **250** 输出 tokens，服务端 usage 的 completion 合计 **251**。本页吞吐保留 vLLM 原字段 `250 / 36.158486 = 6.914006 tok/s`；CSV 中分别保留客户端与服务端计数，不强行改成相等。并发下 usage 到达顺序也不必等于客户端请求索引。

随机文本适合固定长度与参数筛选，不能代表自然业务语料的质量或吞吐。旧 SXM4 短提示的 105–111 tok/s 解码速度，不能直接与本轮 32K 输入、最多 64 输出的整场 7.12 tok/s 比较。

## 6. 2 秒目标与共享前缀

全新 32K 输入没有达到 TTFT < 2 秒。共享前缀实验两条都成功，实际输入均为 33622 tokens：

| 请求 | 缓存命中 tokens | TTFT 秒 |
|---|---:|---:|
| 首次输入 | 0 | 8.743067 |
| 相同前缀再次请求 | 33615 | **0.091794** |

第二条是缓存命中结果，不能用来宣称新输入达到 2 秒。原控制器按无缓存标准将整组标记为 `valid=false`，原因是 `cached_prompt_invalidates_cold_measurement`；两条实际请求成功、errors 均为空。见[原始结果](../benchmarks/2026-11-14-a100-pcie40g/results/identical-prefix-pair-32k-c1.json)。

## 7. 初筛更低的数字为什么没选

第二轮每个候选初筛 3 条，使用相同 seed 27001；只有中位 TTFT 相对已接受父配置严格改善超过 3%，才替换父配置。`promptcache0` 的均值 7.771725 秒、中位 7.562564 秒，数值低于 `chunk8192`，但中位改善约 2.85%，未过门槛，也未做最终八条复验。因此它是初筛更低的候选，不能冒充最终推荐成绩。

独立 `--max-context 40960` 容量试验八条平均 TTFT 8.885047 秒，没有体现速度优势，未部署为默认。`--prefill-head-alias` 在双 GPU 上被明确拒绝启动，没有对应压测数据。`--batch-mtp` 在多 GPU 流水线分组下被自动关闭，不能把这个试验解释为“启用后没有收益”。筛选摘要见[screening-summary.json](../benchmarks/2026-11-14-a100-pcie40g/screening-summary.json)。

## 8. 验收与复现

最终服务在验收时恢复至 8080，health `loaded=true`；有效 Key 的 models 返回 200，错误 Key 返回 401。短算术和两次约 32K 文档中部、尾部信息检索均通过，缓存均为 0。检索的 8.457 / 8.011 秒是端到端时间，不是 TTFT，也不构成全面精度评估。

在部署好同版本引擎、同模型、HF tokenizer 与客户端 Python 依赖的 A100 服务器执行：

```bash
bash scripts/benchmark_latest_a100.sh
```

脚本使用本仓库保存的同一份客户端、正式 8080、运行时读取的私有 Key，以及新的结果目录。历史实跑命令仍保留原测试端口 8081、原私有配置路径和 seed，见逐组启动证据；两种用途分别标注。重复相同 seed 可能命中缓存，脚本会拒绝将命中样本当作新输入，可用 `BENCH_SEED_OFFSET` 选择新的 seed。

本次 GitHub 更新只整理和发布已经完成的实测与复现文件，没有重新运行一套压测。历史验收不代表读者访问时服务器仍在线。
