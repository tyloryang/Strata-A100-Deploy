## 1. 方法与口径

### 1.1 工具与环境

```bash
docker exec strata /data/tools/venv-evalscope/bin/evalscope perf \
  --model qwen3.8-flash-next-iq3_xxs \
  --url http://127.0.0.1:8080/v1/chat/completions \
  --api openai --api-key "$(cat /etc/strata/api_key)" \
  --tokenizer-path /data/Strata-data/tokenizer-qwen \
  --dataset random --min-prompt-length N --max-prompt-length N \
  --min-tokens M --max-tokens M \
  --parallel 2 4 6 8 -n 8 16 24 32 --stream \
  --outputs-dir /data/bench --name <name>
```

三个必须注意的环境事实：

- evalscope 的 venv **只能在容器内跑**（shebang 指向 `/data/tools/...`）。
- 随机文本生成要 `--tokenizer-path`，而 Strata 自带的 `tokenizer.json` 是自研格式（`{"model":"gpt2","pre":"qwen35",...}`），HF `AutoTokenizer` 会报 `KeyError: 'added_tokens'`。已另拉 `Qwen/Qwen3.8-Flash-Next` 的 HF tokenizer 到 `Strata-data/tokenizer-qwen`（23 MB）。
- `--stream` 必加，否则拿不到 TTFT / TPOT。

### 1.2 指标定义

| 指标 | 定义 | 主要受什么影响 |
|---|---|---|
| **TTFT** | 请求发出 → 第一个 token，含排队 + 预填 | prompt 长度、排队深度、前缀缓存是否命中 |
| **TPOT** | 总解码时长 ÷ 输出 token 数，倒数即 tok/s | 显存带宽、专家是否命中显存、KV 读取 |
| **ITL** | 相邻 token 的实际间隔（不是均值） | 调度抖动、被长预填抢占 |
| **E2EL** | 全流程 = TTFT + 输出 token × 平均 TPOT | 上述之和 |

**TPOT 是均值、看整体快慢；ITL 是单次、看稳不稳。** 只报 p50 不报 p99 的结论无效——p99 暴涨而 p50 正常，说明是排队/抢占，不是算力不足。

evalscope 的 `Req Throughput (req/s)` 在闭环模式下等于 `并发 ÷ 最慢请求耗时`，**不是饱和吞吐**；真正的成本指标是 `Output Throughput (tok/s)` 和 `Goodput`。

### 1.3 语料：这一节决定全部结论的可信度

**当前 62 个用例 100% 使用 `--dataset random`。** 这是一个必须修掉的方法学错误，原因有三层：

1. **投机采样会失效。** 随机 token 的 next-token 分布近似均匀，MTP 草稿几乎必被拒。实测 `Spec. Accept Rate = 2%–5%`、`Avg Decoded Tok/Iter = 1.01–1.05`——意味着每个验证窗口只产出约 1 个 token，`--spec 4` 完全没起作用。
2. **前缀缓存恒不命中。** 随机前缀不可能重复，实测 `KV Cache Hit Rate = 0.0%`，多轮/共享 system prompt 的场景完全没被覆盖。
3. **MoE 路由失真。** 随机 token 的专家选择不具代表性，EvalScope 结果对真实业务分布无预测力。

⇒ **`random` 只适合"容量/拐点扫描"**（长度可控、方差小）；**报吞吐、报 SLO、做交付基线，必须用自然中文。**

| | 6 | 0 | 106.1s | 20.32s | 8.34ms | 105.5 |
| | 8 | 0 | 145.6s | 27.99s | 8.69ms | 101.8 |

### 3.6 上下文超限行为

返回 **400**，53ms 内拒绝（不做任何计算），**不截断、不 OOM、不崩服务**：

```
request exceeds the context window: prompt (270017 tokens) + max tokens (32)
exceeds the context (262144); requests are never truncated.
Send a smaller max_tokens (at most 0 here), or add "fit_max_tokens": true ...
```

- 提示本身超窗 → 无论怎么配都 400，客户端必须自己裁历史
- 提示放得下但 `max_tokens` 过大 → `"fit_max_tokens": true` 可自动缩到剩余空间（**当前已开启**）

## 4. 三个方法学缺陷（必须修，否则后续数据同样不可信）

### 4.1 语料全是随机 token

见 §1.3。修法：换 `--dataset openqa` 或自建中文语料。

### 4.2 "并发"测的是排队，不是批处理

引擎**没有 `--parallel` 这个参数**（`strata --help` 里 0 处匹配）。真正的开关是 `--batch N / --slots N`，由 `server.py` 从配置的 `parallel` 键翻译：

```python
PARALLEL_MAX = 8
def parallel_args(cfg, args):
    if "--batch" in args or "--slots" in args: return []
    if n <= 1: return []                       # parallel=1 → 不传 --batch
    return ["--batch", str(n)]
```

所以 `parallel=1` 时所有"并发 2/4/6/8"的用例都在测**单槽位前的排队**。这正是 §3.1 吞吐呈水平线的原因。

**当前配置已是 `parallel=4`（4 个槽位）**，但这是 15:08 之后才改的，**尚无对应压测数据**。

### 4.3 ESP 的 A/B 可能测了个空

控制向量确实加载了，引擎日志有：

```
strata generate: control vector mode = project, dir = per-layer, layers 4..44 (41 steered)
```

但 `--serve` 模式下**是否对某个请求生效，由该请求的 `cvec` 决定**：

```python
# serve/server.py:1236
on = sampling.get("experimental_speed_projection")
return f" cvec={int(on)}" if isinstance(on, bool) else ""
```

配置里没有 `sampling.experimental_speed_projection`，所以请求**不带 `cvec` 参数**，走引擎默认值。两轮实测零差异，与"默认值 = 0（未应用）"一致，但也无法排除"应用了但确实没区别"。

⇒ **要判定 ESP 的真实效果，必须先在配置加 `"sampling": {"experimental_speed_projection": true}` 让请求带 `cvec=1`，再重跑 A/B。** 在那之前，这一节只能记为"未验证"。

### 4.4 其他口径问题

- **无预热**：evalscope 每次警告 "Warmup is disabled, so the first N requests are released at once" —— 第一个 case 的 TTFT 含着冷启动突发，会污染 p95/p99。ESP 矩阵里 512 那组的 −6% 就是这个原因。应加 `--warmup-num`。
- **单次测量**：每个配置只跑一遍，没有重复取中位，噪声（±5%）和真实差异分不开。
- **配置漂移**：62 个用例横跨 `parallel=1/4/6`、`ple-io ram/mmap`、chunk `8192/32768`、ESP 开/关等多种状态，**跨批次比较必须核对当时的配置**（见 §2 表）。

### 4.5 新增的 `reasoning_*` 让"输出长度"失去原有语义

16:42 的配置加了 `reasoning_effort: "medium"`、`reasoning_budget_tokens: 4096`、`reasoning_close_retry: true`。模型现在**先输出思考 token，再给答案**。

之前的历史压测用 `--max-tokens 100`，当时的日志里已经反复出现：

```
the reply reached max tokens while still thinking, so it has no answer
```

含义是：100 个 token 全被思考吃掉，`finish_reason=length`，response 里根本没有答案。也就是说 **你测到的是"思考速度"，而不是"回答速度"**，而且每次请求的有效输出长度并不等于你设定的 `max_tokens`。

⇒ 开 reasoning 时，压测必须二选一：

| 口径 | 设置 | 用途 |
|---|---|---|
| 纯性能基线 | 请求体带 `reasoning_effort: "none"` | 与历史数据可比；TTFT/TPOT 反映纯解码能力 |
| 业务 SLO | 保持 `medium`，`--max-tokens ≥ 4096 + 期望答案长度` | 端到端真实体验；必须把"思考阶段"和"回答阶段"分开记指标 |

**两种口径的数字不能混着报。**

### 4.6 `temperature=1.0` 会压低投机收益且不可复现

`sampling` 现在是 `temperature 1.0 / top_p 0.95 / top_k 20`。两个后果：

1. **MTP 接受率下降。** 投机加速比上界约 `1/(1-α)`，输出越随机，草稿越难与目标模型对齐，α 越低。**temp 0 测出的 tok/s 一定高于 temp 1.0。**
2. **结果不可复现。** 叠加 `STRATA_ADAPT_OVERLAP=1`（官方注明 "Not bit-exact run to run"），同一请求两次运行可能不同。

⇒ 基线跑 **temp 0**；另跑一组 temp 1.0 专门量化投机损失。每组至少重复 3 次取中位。

## 5. 结论与配置建议

| 场景 | 建议 | 依据 |
|---|---|---|
| 单人 / 长文档分析 | `parallel=1` | TPOT 8–10ms，单流最快 |
| 3–5 人同时用 | `parallel=4` | 吞吐 +19~64%，TTFT@2 从 4s 降到 1s |
| 长提示为主（>4K） | 优先看预填能力，槽位收益有限 | 8K 提示下 +19% 已接近上限 |
| 200K 长上下文 | 可用但并发要 ≤4 | 见 §6 内存公式 |
| 多轮对话 | 客户端裁历史到 ~10 万 token，或依赖 `fit_max_tokens` | 24K/轮只能 10 轮 |

## 6. 安全边界与事故复盘

### 6.1 内存预算公式

```
常驻 = 专家 arena 40 GB
     + PLE n-gram 表（模式相关，见下）
     + 引擎权重/缓冲 ~6 GB
每并发请求 KV ≈ 2.8 GB（200K 上下文、int8、--kv-resident 流式落内存）

--ple-io ram  ：表 26.8 GB 被 mlock 钉死，不可回收 → 常驻 ≈ 69 GB
--ple-io mmap ：表走页缓存，可回收              → 常驻 ≈ 42 GB + 页缓存（压力下可让出）
```

实测对照（同一台机器）：

| | `--ple-io ram` | `--ple-io mmap` | `+ --resident-experts`（16:42） |
|---|---|---|---|
| `Mlocked` | 28.1 GiB | **0** | **0** |
| `MemAvailable` | 18.5 GB | **32.4 GB** | **57.1 GB** |
| 引擎 RSS | 76.8 GB | 65.2 GB | **39.3 GB** |

`--resident-experts` 把 40 GiB 专家从"常驻匿名内存"改成"文件映射 + 局部钉页"（日志：`100% of the experts resident`、`resident 12.65 GiB, pinned 12.65 GiB`），显存与专家缓存完全不变（37.8/31.2 GB、12288 槽）。**这是当前配置里对内存安全贡献最大的一项。**

⇒ **94 GB 的机器上 `ram` 是错误选择**（它是按 560 GB 内存的前提写的）。`mmap` 的代价是内存压力下页会被回收、退回 SSD 读，所以**每次重启后要先预热再压测**。`--resident-experts` 进一步把专家也放进可回收页缓存，代价是官方实测 mmap 速率依赖页缓存能否留住 34 GB（冷 71.97 vs 热 34.78 ms/token）。

### 6.2 那次宕机（必须记住）

`parallel=8` + 8 个 200K 并发请求 → 69 + 22 = 91 GB，叠加页缓存后进 swap，**系统假死约 50 分钟**：sshd 只有 TCP 握手、无 banner，服务无响应，无法自愈。

逐级测试里 `parallel=2`×200K（83 秒、2/2 成功）与 `parallel=4`×64K 都正常，问题出在 6/8 档 × 200K。

**结论：这台 94 GB 机器上，长上下文并发不能超过 4。** 且 `parallel` 必须按 §6.1 公式算，不能照搬短提示的经验值。

### 6.3 看门狗

`/root/offline_check/watchdog.sh` 每 15 秒检查，满足任一条件即杀掉压测并保留现场：

- `/health` 非 200
- 可用内存 < 6 GB
- swap 使用 > 1 GB
- load average(1m) > 80

**已知误报**：关 ESP 重启时 health 瞬时 000 会触发。正式压测前先暂停它，或把条件改成连续 3 次失败。

### 6.4 显存红线

当前 `--prefill auto:32768` 生效后，GPU0 从 28.9 GB 涨到 **37.8 GB（40 GB 的 92%，仅剩 3.2 GB）**，GPU1 从 35.0 GB 降到 31.2 GB。这是 chunk 缓冲变大导致层拆分重新平衡的结果。**长提示压测时要盯 GPU0 余量，小于 2 GB 就退回 `--prefill auto`。**

## 9. 最新配置实测（2026-11-02 20:20，8 槽 + batch-mtp）

### 9.1 该配置的实际组成

```
parallel=8（→ --batch 8，日志显示 pipelined 2 groups of 4）
```

### 9.2 A 轮：随机语料（与历史同口径）

`--dataset random`，in=2000 / out=100，`reasoning_effort=none`，`temperature=0`，`seed=1234`。

|---|---|---|---|
| 1 | 1501 | 9.25 | 41.4 |
| 2 | 2007 | 23.61 | 43.8 |
| 3 | 2820 | 34.10 | 48.3 |
| 4 | 3644 | 41.72 | 51.4 |
| 6 | 4869 | 63.16 | 53.8 |

与 14:34 单槽位基线对比：

| 并发 | TPOT 基线 | TPOT 现在 | 聚合 基线 | 聚合 现在 |
|---|---|---|---|---|

**读法**：单请求解码只慢了约 10%（108 vs 120 tok/s），但**每多一路并发，单流延迟按比例恶化**——并发 8 时 TPOT 94.7 ms，即每条流只剩 10.6 tok/s。聚合吞吐峰值 56.4，仅比单槽位的 51.7 高 **9%**。

### 9.3 关键发现：批量路径下 MTP 完全不运行

引擎在启动时自己打了这条警告：

```
strata generate: WARNING: --batch-mtp is off: a layer split with --batch pipelines the slots in groups
by default and the pipelined groups run no slot drafts (4 streams on 2 GPUs: 25-30% faster than the
serial MTP windows); --batch-groups 1 or STRATA_BATCH_MTP_SERIAL=1 keeps --batch-mtp with serial windows
(fewer streams, or when prompts arrive rarely, it can be the faster choice)
```

证据链：

- `--batch-mtp` 确实在 args 里（`--help` 与之对照无误）
- 但日志里**没有任何** `--batch-mtp: N slot drafters on CUDAk` 行
- 所有请求的草稿计数都是 `drafts accepted 0 of 0`

⇒ **`--spec 4` + `--mtp` 在当前 8 槽配置下完全空转。** 这不只是"随机语料接受率低"的问题，而是流水线批量路径根本不跑各槽的草稿。

引擎同时给出了取舍数据：**2 卡 4 路并发时，流水线比串行 MTP 窗口快 25–30%**。所以对 4 路以上并发，"保持流水线、放弃 batch-mtp"本来就是更优选择；batch-mtp 只在约 2 路并发、或提示稀疏到达时可能更快。

### 9.4 B 轮：自然中文语料

自建 48 条中文技术长文（in≈800 token），同样的并发梯度与采样设置。

| 并发 | TTFT avg (ms) | TPOT avg (ms) | 聚合输出 (tok/s) |
|---|---|---|---|
| 1 | 723 | 9.45 | 59.3 |
| 2 | 792 | 21.31 | 68.1 |
| 3 | 1404 | 28.08 | 70.7 |
| 4 | 1539 | 35.88 | 77.6 |
| 6 | 1937 | 51.97 | 83.7 |
| 8 | 1804 | **71.42** | **89.3** |

**不要把它读成"MTP 起作用了"。** 聚合吞吐比 A 轮高 58%，但原因是**提示只有 800 token（A 轮 2000）**，每请求的预填量只有 40%。证据：两轮 TPOT 在并发 1 时几乎相同（9.45 vs 9.25），而草稿接受计数是 `0 of 0`——自然文本也没有触发任何草稿。

所以自然文本这一轮的真正结论是：**换语料没有让解码变快，因为 MTP 压根没跑。**

### 9.5 结论

1. 8 槽位买到的是 **+9% 聚合吞吐**，代价是并发 8 时单流从 10.6 tok/s 起——对交互式业务几乎不可用。
2. **MTP/投机在当前配置下是零贡献**，`--spec 4` / `--spec-min-p 0.5` 两个参数白配。
3. 若目标是低延迟交互：回到 `parallel` 1–2。若目标是离线批量吞吐：可留 8 槽，但要接受单流延迟。
4. 若确实想要 MTP 收益：必须 `--batch-groups 1` 或 `STRATA_BATCH_MTP_SERIAL=1`，且只在约 2 路并发时才划算（引擎实测 25–30% 的反向差距）。

| 6 | **83.7** | 78.3 | 76.5 | 77.1 |
| 8 | **89.3** | 80.7 | 70.3 | 81.6 |

### 12.4 四条结论

**① 8 槽从来打不过 4 槽（长提示下）。** v6 在 A 轮每一个并发点都是最高的聚合，且 TPOT 只有 8 槽的一半（45.9 vs 94.7 ms）。槽位超过实际并行能力后，多出来的槽只是在争抢同一份专家缓存。

**② 槽位数要与提示长度匹配。** 短提示（B 轮）时 8 槽在并发 ≥6 反而最好（89.3 vs 80.7），因为每请求的预填占比低，多槽才真能换成吞吐。长提示则相反。

**③ `batch-mtp` 串行窗口（v7/v8）是最差的组合。** A 轮并发 8 聚合 49.9 / 47.9，比 v6 低 16–20%；TPOT 132–139 ms，是 v6 的 2.9–3.0 倍。这与引擎启动警告的 25–30% 方向一致，本机长提示实测为 16–20%。

**④ `--ple-io ram` 与 `mmap` 没有可测差异。** v9（ram）与 v5（mmap）在完全相同的槽位/分组下：并发 8 聚合 55.9 vs 56.4，TPOT 94.41 vs 94.71——都在噪声内。

> 这条**修正了本文档 §10 的一个推断**。当时用 v4（ram+4槽）对 v3w（mmap+4槽），得出"ram 快 14%"，但那两组同时有别的差异，且内存状态不同。现在用同槽位、同分组、空闲服务的严格对照，结论是 **PLE 表放 mlock 还是页缓存，对这组负载没有影响**。
>
> 但 `ram` 仍有一个真实代价：它把 26.8 GiB 变成**不可回收**内存。v8/v9 期间实测 `MemAvailable` 一度只剩 652 MiB，会话缓存开始拒绝停放（`skip parking (physical RAM admission ...)`）。**从稳定性角度，`mmap` 更安全。**

### 12.5 当前建议

| 场景 | 配置 |
|---|---|
| 长提示 / 文档分析（默认推荐） | **v6：`parallel=4` + 流水线，PLE 用 `mmap`** |
| 短提示 / 高并发问答 | `parallel=8` + 流水线 + `mmap`（v5） |
| 不要用 | 串行窗口 + `batch-mtp`（v7/v8），以及 `STRATA_ROUTE_TAIL_SKIP=0` 未验证的情况 |
