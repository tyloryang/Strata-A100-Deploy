## 1. 方法与口径

### 1.1 工具与环境

```bash
docker exec strata /data/tools/venv-evalscope/bin/evalscope perf \
  --model qwen3.8-flash-next-iq3_xxs \
  --url http://127.0.0.1:8080/v1/chat/completions \
  --api openai --api-key "$(cat /etc/strata/api_key)" \
  --tokenizer-path /data/Strata-data/tokenizer-qwen \
  --dataset random --min-prompt-length N --max-prompt-length N \
  --min-tokens M --max-tokens M \
  --parallel 2 4 6 8 -n 8 16 24 32 --stream \
  --outputs-dir /data/bench --name <name>
```

三个必须注意的环境事实：

- evalscope 的 venv **只能在容器内跑**（shebang 指向 `/data/tools/...`）。
- 随机文本生成要 `--tokenizer-path`，而 Strata 自带的 `tokenizer.json` 是自研格式（`{"model":"gpt2","pre":"qwen35",...}`），HF `AutoTokenizer` 会报 `KeyError: 'added_tokens'`。已另拉 `Qwen/Qwen3.8-Flash-Next` 的 HF tokenizer 到 `Strata-data/tokenizer-qwen`（23 MB）。
- `--stream` 必加，否则拿不到 TTFT / TPOT。

### 1.2 指标定义

| 指标 | 定义 | 主要受什么影响 |
|---|---|---|
| **TTFT** | 请求发出 → 第一个 token，含排队 + 预填 | prompt 长度、排队深度、前缀缓存是否命中 |
| **TPOT** | 总解码时长 ÷ 输出 token 数，倒数即 tok/s | 显存带宽、专家是否命中显存、KV 读取 |
| **ITL** | 相邻 token 的实际间隔（不是均值） | 调度抖动、被长预填抢占 |
| **E2EL** | 全流程 = TTFT + 输出 token × 平均 TPOT | 上述之和 |

**TPOT 是均值、看整体快慢；ITL 是单次、看稳不稳。** 只报 p50 不报 p99 的结论无效——p99 暴涨而 p50 正常，说明是排队/抢占，不是算力不足。

evalscope 的 `Req Throughput (req/s)` 在闭环模式下等于 `并发 ÷ 最慢请求耗时`，**不是饱和吞吐**；真正的成本指标是 `Output Throughput (tok/s)` 和 `Goodput`。

### 1.3 语料：这一节决定全部结论的可信度

**当前 62 个用例 100% 使用 `--dataset random`。** 这是一个必须修掉的方法学错误，原因有三层：

1. **投机采样会失效。** 随机 token 的 next-token 分布近似均匀，MTP 草稿几乎必被拒。实测 `Spec. Accept Rate = 2%–5%`、`Avg Decoded Tok/Iter = 1.01–1.05`——意味着每个验证窗口只产出约 1 个 token，`--spec 4` 完全没起作用。
2. **前缀缓存恒不命中。** 随机前缀不可能重复，实测 `KV Cache Hit Rate = 0.0%`，多轮/共享 system prompt 的场景完全没被覆盖。
3. **MoE 路由失真。** 随机 token 的专家选择不具代表性，EvalScope 结果对真实业务分布无预测力。

⇒ **`random` 只适合"容量/拐点扫描"**（长度可控、方差小）；**报吞吐、报 SLO、做交付基线，必须用自然中文。**

## 3. 结果

### 3.1 并发矩阵 `parallel=1`（单槽位）

|---|---|---|---|---|---|---|
| 512/512 | 2 | 0 | 34.4s | 4.26s | 8.05ms | 109.0 tok/s |
| | 4 | 0 | 72.3s | 12.57s | 8.51ms | 104.2 |
| | 6 | 0 | 106.1s | 20.32s | 8.34ms | 105.5 |
| | 8 | 0 | 145.6s | 27.99s | 8.69ms | 101.8 |
| 1024/256 | 2 | 0 | 23.9s | 3.44s | 8.86ms | 85.8 |
| | 8 | 0 | 99.3s | 19.77s | 9.47ms | 81.1 |
| 4096/256 | 2 | 0 | 33.4s | 5.31s | 10.04ms | 61.3 |
| | 8 | 0 | 131.8s | 26.85s | 9.75ms | 62.0 |
| 8192/256 | 2 | 0 | 42.7s | 7.39s | 10.31ms | 48.0 |

**读法：总输出吞吐是水平线（109→102、86→81、61→62、48→49），TTFT 随并发线性上涨。** 所有请求排一条队，一个槽位依次解码——这就是单槽位的指纹。

| 场景 | parallel=1 | parallel=4 | 吞吐提升 | TTFT@并发2 |
|---|---|---|---|---|
| 512/512 | 101.8 | 166.5 | **+63.6%** | 4.26s → 0.99s |

**收益随提示变长而衰减**：长提示的预填本身吃满槽位，4 个槽位也顶不住 8 个 8K 提示同时预填。代价是单流变慢：TPOT 从 8–10ms 涨到 13–54ms（单请求 100–125 → 18–75 tok/s），这是 4 个槽位分同一份算力的必然结果。显存代价很小：28.8/34.9 GB，专家缓存仍是 12288 个。

### 3.3 长上下文（真实中文，无缓存）

| 提示长度 | TTFT | 预填吞吐 | 解码 |
|---|---|---|---|
| 32K | 7.77s | 4,220 tok/s | 104.6 tok/s |
| 64K | 13.43s | 4,880 | 93.8 |
| 128K | 25.31s | 5,179 | 94.7 |
| 200K | 38.98s | 5,131 | **87.0** |

预填吞吐稳定在 4.2–5.2K tok/s；**解码从 104.6 掉到 87.0（−17% @200K）**——这是长上下文唯一明显的性能衰减。

多轮 A（4K/轮，12 轮）：

| 轮 | prompt_tokens | 新增 | TTFT | 解码 |
|---|---|---|---|---|
| 1 | 4,123 | 4,123 | 1.95s | 107.5 tok/s |
| 6 | 24,871 | 4,121 | 1.70s | 169.1 |

| 轮 | prompt_tokens | 新增 | TTFT | 解码 |
|---|---|---|---|---|
| 1 | 24,603 | 24,603 | 6.10s | 103.4 |

### 3.5 并发长请求（`parallel=1`）

| 场景 | 各请求 TTFT | 总墙钟 | 成功 |
|---|---|---|---|
| 4 × 64K | 14.4 / 28.8 / 42.9 / 57.2s | 57.8s | 4/4 |
| 4 × 200K | 41.3 / 81.1 / 121.0 / 160.9s | 161.9s | 4/4 |

严格串行：总墙钟 ≈ 4 × 单个耗时。**长上下文 + 并发 = 排队到分钟级。**

### 3.6 上下文超限行为

返回 **400**，53ms 内拒绝（不做任何计算），**不截断、不 OOM、不崩服务**：

```
request exceeds the context window: prompt (270017 tokens) + max tokens (32)
exceeds the context (262144); requests are never truncated.
Send a smaller max_tokens (at most 0 here), or add "fit_max_tokens": true ...
```

- 提示本身超窗 → 无论怎么配都 400，客户端必须自己裁历史
- 提示放得下但 `max_tokens` 过大 → `"fit_max_tokens": true` 可自动缩到剩余空间（**当前已开启**）

## 4. 三个方法学缺陷（必须修，否则后续数据同样不可信）

### 4.1 语料全是随机 token

见 §1.3。修法：换 `--dataset openqa` 或自建中文语料。

### 4.2 "并发"测的是排队，不是批处理

引擎**没有 `--parallel` 这个参数**（`strata --help` 里 0 处匹配）。真正的开关是 `--batch N / --slots N`，由 `server.py` 从配置的 `parallel` 键翻译：

```python
PARALLEL_MAX = 8
def parallel_args(cfg, args):
    if "--batch" in args or "--slots" in args: return []
    if n <= 1: return []                       # parallel=1 → 不传 --batch
    return ["--batch", str(n)]
```

所以 `parallel=1` 时所有"并发 2/4/6/8"的用例都在测**单槽位前的排队**。这正是 §3.1 吞吐呈水平线的原因。

**当前配置已是 `parallel=4`（4 个槽位）**，但这是 15:08 之后才改的，**尚无对应压测数据**。

### 4.3 ESP 的 A/B 可能测了个空

控制向量确实加载了，引擎日志有：

```
strata generate: control vector mode = project, dir = per-layer, layers 4..44 (41 steered)
```

但 `--serve` 模式下**是否对某个请求生效，由该请求的 `cvec` 决定**：

```python
# serve/server.py:1236
on = sampling.get("experimental_speed_projection")
return f" cvec={int(on)}" if isinstance(on, bool) else ""
```

配置里没有 `sampling.experimental_speed_projection`，所以请求**不带 `cvec` 参数**，走引擎默认值。两轮实测零差异，与"默认值 = 0（未应用）"一致，但也无法排除"应用了但确实没区别"。

⇒ **要判定 ESP 的真实效果，必须先在配置加 `"sampling": {"experimental_speed_projection": true}` 让请求带 `cvec=1`，再重跑 A/B。** 在那之前，这一节只能记为"未验证"。

### 4.4 其他口径问题

- **无预热**：evalscope 每次警告 "Warmup is disabled, so the first N requests are released at once" —— 第一个 case 的 TTFT 含着冷启动突发，会污染 p95/p99。ESP 矩阵里 512 那组的 −6% 就是这个原因。应加 `--warmup-num`。
- **单次测量**：每个配置只跑一遍，没有重复取中位，噪声（±5%）和真实差异分不开。
- **配置漂移**：62 个用例横跨 `parallel=1/4/6`、`ple-io ram/mmap`、chunk `8192/32768`、ESP 开/关等多种状态，**跨批次比较必须核对当时的配置**（见 §2 表）。

## 5. 结论与配置建议

| 场景 | 建议 | 依据 |
|---|---|---|
| 单人 / 长文档分析 | `parallel=1` | TPOT 8–10ms，单流最快 |
| 3–5 人同时用 | `parallel=4` | 吞吐 +19~64%，TTFT@2 从 4s 降到 1s |
| 长提示为主（>4K） | 优先看预填能力，槽位收益有限 | 8K 提示下 +19% 已接近上限 |
| 200K 长上下文 | 可用但并发要 ≤4 | 见 §6 内存公式 |
| 多轮对话 | 客户端裁历史到 ~10 万 token，或依赖 `fit_max_tokens` | 24K/轮只能 10 轮 |

## 6. 安全边界与事故复盘

### 6.1 内存预算公式

```
常驻 = 专家 arena 40 GB
     + PLE n-gram 表（模式相关，见下）
     + 引擎权重/缓冲 ~6 GB
每并发请求 KV ≈ 2.8 GB（200K 上下文、int8、--kv-resident 流式落内存）

--ple-io ram  ：表 26.8 GB 被 mlock 钉死，不可回收 → 常驻 ≈ 69 GB
--ple-io mmap ：表走页缓存，可回收              → 常驻 ≈ 42 GB + 页缓存（压力下可让出）
```

实测对照（同一台机器）：

| | `--ple-io ram` | `--ple-io mmap` |
|---|---|---|
| `Mlocked` | 28.1 GiB | **0** |
| `MemAvailable` | 18.5 GB | **32.4 GB** |
| 引擎 RSS | 76.8 GB | 65.2 GB |

⇒ **94 GB 的机器上 `ram` 是错误选择**（它是按 560 GB 内存的前提写的）。`mmap` 的代价是内存压力下页会被回收、退回 SSD 读，所以**每次重启后要先预热再压测**。

### 6.2 那次宕机（必须记住）

`parallel=8` + 8 个 200K 并发请求 → 69 + 22 = 91 GB，叠加页缓存后进 swap，**系统假死约 50 分钟**：sshd 只有 TCP 握手、无 banner，服务无响应，无法自愈。

逐级测试里 `parallel=2`×200K（83 秒、2/2 成功）与 `parallel=4`×64K 都正常，问题出在 6/8 档 × 200K。

**结论：这台 94 GB 机器上，长上下文并发不能超过 4。** 且 `parallel` 必须按 §6.1 公式算，不能照搬短提示的经验值。

### 6.3 看门狗

`/root/offline_check/watchdog.sh` 每 15 秒检查，满足任一条件即杀掉压测并保留现场：

- `/health` 非 200
- 可用内存 < 6 GB
- swap 使用 > 1 GB
- load average(1m) > 80

**已知误报**：关 ESP 重启时 health 瞬时 000 会触发。正式压测前先暂停它，或把条件改成连续 3 次失败。

### 6.4 显存红线

当前 `--prefill auto:32768` 生效后，GPU0 从 28.9 GB 涨到 **37.8 GB（40 GB 的 92%，仅剩 3.2 GB）**，GPU1 从 35.0 GB 降到 31.2 GB。这是 chunk 缓冲变大导致层拆分重新平衡的结果。**长提示压测时要盯 GPU0 余量，小于 2 GB 就退回 `--prefill auto`。**

### 7.3 矩阵设计

| 形态 | input | output | 场景 |
|---|---|---|---|
| 短问答 | 512 | 256 | 在线助手 |
| 典型运维 | 2000 | 100 | 与历史数据可比 |

| 长上下文 | 65536–200000 | 64 | 单独报 TTFT 与预填 tok/s |

并发梯度 `--parallel 1 2 4 6 8`，每组 `-n` 取 4×并发，**每档至少重复 3 次取中位**，并加 `--warmup-num`（取并发数）把冷启动排除在测量窗口外。

### 7.4 必须记录的字段

| 类别 | 字段 |
|---|---|
| 延迟 | TTFT p50/p95/p99、TPOT p50/p95/p99、ITL p99、E2EL p50/p95/p99 |

### 7.5 判读三条红线

- **p99 涨而 p50 正常** → 排队/抢占，不是算力不足
- **专家缓存 slots 下降** → VRAM 被 KV 或 prefill 缓冲挤掉，解码会变慢
- **swap used 上升** → 内存不够，立刻停

## 8. 下一轮实验计划

按"每组只改一项、重启一次跑完整矩阵"的顺序，避免配置漂移。

| 步骤 | 改动 | 目的 | 验收信号 |
|---|---|---|---|
| 0 | 换成自然中文语料 | 拿到可信基线 | `Spec. Accept Rate` 从 2–5% 升到正常水平 |
| 1 | 现状（`parallel=4` + mmap + chunk32768） | 基线 | 4 槽位吞吐 vs `parallel=1` 的真实差距 |
| 2 | 加 `"sampling": {"experimental_speed_projection": true}` | 让 ESP 真正生效 | 日志/请求确认 `cvec=1`；再判 A/B |
| 3 | `--prefill auto:32768` → `auto` 回退对比 | 量化 chunk 收益 | GPU0 余量 vs 预填 tok/s 的取舍 |
| 4 | `--kv k8v4` | 省 23% KV 显存 | 200K 解码速度、显存余量 |
| 5 | `--expert-cache-device1 auto` | 让第二张卡也装专家 | 专家 slots 是否从 12288 提升 |
| 6 | `--pipeline-windows 2` | 双卡 decode 重叠 | TPOT 是否下降 |
| 7 | `--expert-cache-per-layer` | 改善专家命中分布 | 命中率 / TPOT |
| 8 | `--calibrate` | 本机标定 `--spec-min-p` | 接受率 vs 预填开销 |

**注意**：步骤 5/6/7 目前**没有官方在本配置下的验证记录**（`--peer-device` 明确与 layer-split 互斥，`--expert-cache-device1..3` 未见限制但也未见组合实测），必须先在单变量下小流量验证，不要直接上生产。
