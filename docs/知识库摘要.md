## 2. 推理性能指标体系

### 2.1 四个延迟指标（见 7）

| 指标 | 定义 | 公式 | 覆盖阶段 | 瓶颈来源 |
|---|---|---|---|---|
| TTFT | 请求发出 → 第一个 token 返回（ms） | `TTFT ≈ 排队 + Prefill + 首个 decode step`（见 9） | 调度 + 完整 prefill | 长 prompt 的 prefill 算力、排队、prefix cache 未命中 |
| TPOT | 解码阶段每 token 平均耗时 | `TPOT = 总解码时长 ÷ 输出 token 数`，倒数即 tok/s | decode | 显存带宽 + KV Cache 读放大（见 7） |
| ITL | 相邻两 token 的实际间隔 | 逐次采样，非平均 | decode | 调度抖动、长 prefill 抢占、CUDA Graph 未覆盖的突刺 |
| E2EL | 端到端总耗时 | `E2EL = TTFT + 输出 token 数 × 平均 TPOT` | 全流程 | 上述之和 |

**公式可用真实数据校验**（见 24，qwen3.8-27B / 1×H20 / 输入 2000 输出 100）：BF16 qps=1 时 `812.48 + 100×30.76 = 3888ms ≈ mean_e2el 3858ms`；FP8 qps=1 时 `396 + 100×16 = 1996ms ≈ 1989ms`。误差 <1%，说明该 E2EL 公式可直接用于容量估算。

**TPOT 与 ITL 的区别是运维关键**（见 7）：TPOT 是全程平均（看整体快慢），ITL 是单次间隔（看输出稳不稳）。压测脚本对两者都取 p90/95/99（见 23）。

### 2.2 吞吐类指标

| 指标 | 定义 | 出处 |
|---|---|---|
| Request throughput (req/s) | 单位时间完成请求数 | 见 23（vLLM bench 输出） |
| Output token throughput (tok/s) | 单位时间输出 token 数，**最贴近成本** | 见 23 |
| Total token throughput (tok/s) | 输入+输出合计 | 见 23 |
| QPS / Per-GPU-QPS | 每秒请求数；**除以卡数**才是横向对比口径 | 见 25（tp2 → 5/2=2.5，tp4 → 8/4=2，tp8 → 24/8=3，取最高者做混部基线） |
| 并发（concurrency / 并发槽位） | 同时在跑的序列数，受 `max_num_seqs` 与 KV 显存双重约束 | 见 额外实战/推理优化、26 |
| Goodput | **SLO 约束下的有效吞吐**——超过延迟 SLO 的吞吐不计入 | 见 25：「PD 分离不会凭空多出吞吐，而是提高 SLO 内的吞吐（goodput）」 |

Goodput 是知识库里唯一把「延迟」和「吞吐」统一成一个数的指标，也是 PD 分离收益的唯一正当口径（见 25）。

### 2.3 prefill / decode 的算术强度差异

知识库给的结论是定性的（见 9 §2、18 背景、5 阶段 4 批注）：

| 维度 | Prefill | Decode |
|---|---|---|
| 单次处理 token | 整个 prompt（2048~8192+） | 1 个（每请求） |
| 计算形态 | `[batch_tokens, hidden] × [hidden, 3·hidden]`，M 维大，Tensor Core 喂得饱 | `[num_active_reqs, hidden] × [hidden, 3·hidden]`，M 维小，算力打不满 |
| 瓶颈 | **compute-bound**（算力） | **memory-bandwidth-bound**（显存带宽 + KV 读） |
| 批大小收益 | 吞吐随 batch 上升后**趋平**（DistServe 实验，见 9） | 吞吐随 batch **显著上升**（见 9） |
| 典型利用率 | 高 | 「传统自回归模式下 GPU 算力利用率普遍不足 30%」（见 额外实战/推理优化） |

注意 9 明确写了这句话「不是绝对定律」，瓶颈还取决于模型大小、batch、prompt/输出长度、GPU 型号、attention kernel、KV 精度、TP/PP、是否 GQA/MQA。

### 2.4 Roofline：知识库未做定量分析【未覆盖，补充推导】

知识库**没有**出现「算术强度 / roofline / ops:byte」字样，也没有给 GPU 的算力与带宽规格。用标准 roofline 把上面的定性结论量化（公式属通用知识，输入参数取自知识库）：

- 判据：`I = FLOPs / Bytes`（算术强度），若 `I < 峰值算力 / 峰值带宽` 则 memory-bound。
- **Decode（batch=1 视角）**：每 token 需读完全部权重，`FLOPs ≈ 2N`、`Bytes ≈ N·b`（N=参数量，b=权重字节数），故 `I ≈ 2/b`。FP8（b=1）时 `I ≈ 2 FLOP/byte`，FP16 时也是 2——**与模型大小无关**，远低于任何现代 GPU 的 ops:byte 比（H100 级 BF16 约 300），所以 decode 恒为 memory-bound；这解释了为什么「权重量化在 decode 几乎线性收益」（见 18、24 实测）。
- **Prefill**：一次读权重服务 P 个 token，`I ≈ 2P/b`。令 `2P/b = 峰值算力/峰值带宽` 得拐点 `P* ≈ b·(算力/带宽)/2`；以 BF16、比值 ≈300 计，`P* ≈ 150 token`。即**几百 token 以上的 prompt 就已经进入 compute-bound 区**，长 prompt 的 prefill 必然吃算力而不是带宽——与 9、25 的「长输入场景 PD 分离收益最大」自洽。
- 工程含义：decode 优化看「每 token 搬多少字节」（权重位宽、KV 位宽、专家是否在显存）；prefill 优化看「每焦耳多少 FLOP」（Tensor Core 占用、chunk 大小、并行切分）。

### 2.5 业界经验阈值

知识库给的是**具体项目口径**而非通用行业表（见 25）：`P95 TTFT < 700ms`、`P95 TPOT < 30ms`，在该 SLO 下 `2P(tp4) + 2D(dp1)`、输入 4500 共享前缀 + 1200 随机、输出 100，PD 分离相对混部吞吐 **1.7×**。25 还给了判据：**SLO 越严格、输入越长、P:D 比例越适中，PD 分离收益越大**。

24 的实测表则给出「延迟随负载非线性劣化」的锚点（1×H20，输入 2000/输出 100）：

| 档位 | 模型 | QPS | mean/p99 TTFT (ms) | mean/p99 TPOT (ms) | mean/p99 E2EL (ms) |
|---|---|---|---|---|---|
| qps=1 | BF16 | 0.98 | 812 / 2046 | 30.8 / 62.0 | 3858 / 6979 |
| qps=2 | BF16 | 1.77 | 2306 / 4493 | 144 / 303 | 16611 / 31690 |
| qps=3 | BF16 | 1.95 | 9291 / 15190 | 250 / 496 | 34079 / 49882 |
| qps=3 | FP8 | 2.85 | 1713 / 4064 | 123 / 224 | 13987 / 23218 |

读法：吞吐只从 0.98 涨到 1.95（+99%），p99 TTFT 却涨了 7.4 倍——**单卡在这个输入输出形态下的拐点在 qps≈2 附近，超过就是纯排队**。

## 3. KV Cache 相关

### 3.1 显存公式（见 6）

知识库给出的推导路径：单头 `2×[B,L,d_head]` → n_head 头 `2×[B,L,d_model]`（因为 `n_head·d_head = d_model`）→ 每层独立缓存 → 总元素 `2·B·L·d_model·n_layer`：

```
KV 显存 = 2 × B × L × d_model × n_layer × bytes      (bytes: FP16=2, FP8=1, FP32=4)
```

**这是 MHA 口径**（把 `n_head·d_head` 直接写成 `d_model`）。15_MHA/MQA/GQA 是空壳，知识库没有给 GQA 版公式，按同口径改写为【补充推导】：

```
KV 显存 = 2 × B × L × (n_kv_head × d_head) × n_layer × bytes
```

用知识库自己的例子校验（见 9）：32 层、GQA 后 8 个 KV heads、head_dim=128、FP16、prompt 8192 →
`2 × 8192 × 8×128 × 32 × 2B = 1.07 GB`，与原文「1GB 左右」一致 ✓。

工程速算（见 额外实战/推理优化）：`单序列 KV = 2 × num_layers × hidden × bytes × max_model_len`，`总 KV = 单序列 × max_num_seqs`，必须 ≤ 可用 KV 显存 —— 这就是 `max_num_seqs` 与 `max_model_len` 的硬约束关系。

### 3.2 PagedAttention：分页机制与碎片治理（见 8）

- 传统做法的两个病：**内部碎片**（按最大长度 4096 预留、实际 512 → 利用率 12.5%）与**外部碎片**（请求长短不一，释放的连续块塞不进新请求）。
- 机制对照 OS 分页：Block（常见 16 token）↔ Page(4KB)、Block Table ↔ Page Table、物理 Block 池 ↔ 物理页框。**逻辑连续、物理离散**；块内连续、块间跳跃，因此寻址开销可忽略，而省下的显存换成更大 batch，净收益为正。
- 三个工程红利：① **共享前缀缓存**（相同 system prompt / 长文档 / 多轮历史 / RAG 同一文档，多请求 Block Table 指向同一批物理块，只存一份）；② **连续批处理**（每 decode step 结束即释放完成请求的 Block 并从等待队列补新请求，增删只需改 Block Table）；③ **Chunked Prefill**（长 prompt 切块与 decode 交错，避免 200ms 级「霸屏」；它不让单次 prefill 更快，而是让 ITL 更平稳）。
- Block 大小是**权衡参数**：太大 → 尾部浪费（block=64 而只剩 3 token → 浪费 61 格）；太小 → Block Table 变长、寻址与调度开销上升。实践取 16（最多浪费 15 个 token）。知识库未讨论 8/32/64 的实测对比【未覆盖】。
- 23 的 Prometheus 指标里可见实际取值：`block_size`、`num_gpu_blocks=12759`、`kv_cache_size_tokens=6853883`、`kv_cache_max_concurrency=26.1` —— **这是判断「KV 还能撑多少并发」最直接的一手数据**。

### 3.3 KV 量化（见 额外实战/推理优化 §三、24）

- 背景量化：长上下文下 KV 可占**总显存 60% 以上**，是单卡并发数与最大上下文的头号约束。
- 选型逻辑：INT8 vs **FP8** —— FP8 浮点动态范围大，长序列数值稳定性更好、精度损失更小；Ada/Hopper 原生支持，**无反量化开销**；INT8 需整型缩放，长序列更易溢出/掉点。
- 两种 scale 来源：① 运行时动态自动算（`calculate_kv_scales=False`，部署最简）；② 业务校准集离线固化标度（`calculate_kv_scales=True` 或 llm-compressor 生成，精度更优）。
- 收益路径：显存不变的前提下「KV+权重+激活」都变小 → **调大 batch 或提高 `max-model-len`**（原文明确这一句），而不是直接变快。
- 精度风险与兜底：需联合算法侧评估「信息召回率、上下文一致性」，高精度场景保留 FP16 降级开关 + 上游 AB test。
- `q4_0` 等 4bit KV：**知识库未覆盖**【未覆盖】。

### 3.4 KV 池化（prefix cache / KV 复用）（见 10）

**要解决的问题**：vLLM 的 APC 只在**单实例内**生效，同一个 2K system prompt 在 N 个实例被各存一份（N 倍显存 + N 倍重算）；实例驱逐后冷启动要重算；新实例上线从零开始。成本本质：`KV 占显存 = 可用并发空间 = 吞吐 = 单请求成本`。

**收益量化（见 10，GQA + FP16 + 128K 上下文）**：

| 指标 | 不卸载 | 卸载后 | 节省 |
|---|---|---|---|
| 7B 单卡 128K 并发数 | ~1 | ~4 | 并发 3-4×，KV 显存省 100%（16GB） |
| 72B / 10 并发 128K 所需 GPU | ~40 卡 | ~16 卡 | 少 24 卡，硬件成本 -60% |

**两层架构**（LMCache MP 模式，见 10）：
- L1 = CPU DRAM 热数据；L2 = 19+ 可插拔后端（Mooncake Store / Redis / S3 / FS / NIXL / Aerospike / Bigtable…）。引擎侧通过 `LMCacheMPConnector` 走 ZMQ DEALER/ROUTER 对接独立 daemon。
- 三大控制器：`StoreController`（L1→L2 异步写，受 `--l2-store-policy` 控制：`default` 保留 L1 / `skip_l1` 纯写透）、`PrefetchController`（L2 未命中回填，`--l2-prefetch-max-in-flight` 限并发；留存策略 `default` 临时 / `retain` 永久）、`EvictionController`（**水位线默认 80%**，LRU / IsolatedLRU / noop）。
- 关键工程细节：**GPU 亲和性分发**——同一引擎实例的 STORE/RETRIEVE 固定给同一 GPU Worker 线程，独占 CUDA IPC 句柄，消除锁竞争（`--max-gpu-workers`），直接压低 P99；写锁 TTL 600s、读锁 TTL 300s。

**命中率的影响因素（知识库明确给出的）**：
1. **块对齐**：只有块对齐的前缀才能命中，命中 token 数是块大小整数倍（块=8 时，31 token 只能命中 24）。
2. **分块粒度**：`chunk-size` 默认 256 token，哈希用 blake3 + 模型/rank/租户盐。
3. **实例集中度**：TP8 单实例共享一份 cache 命中率最高，实例一多就被 `round_robin` 稀释（见 25 的平局决胜规则）。
4. **驱逐水位与 TTL**：水位到 80% 就 LRU 淘汰；`decoder_kv_blocks_ttl` 默认 480s 的 pin 会把 KV 池钉满 —— 见 26 的真实故障：开了 `bidirectional_kv_xfer: true` 后 D 端「钉住但没人回读」的块把 KV 用到 **98%**。
5. **租约**：Mooncake 读租约默认 5s、LMCache 写锁 600s，租约内的对象不参与驱逐。

**Mooncake Store（见 10）**：控制面/数据面分离；`PutStart → P2P 零拷贝（RDMA/TCP，经 Transfer Engine，不过 Master）→ PutEnd` 两阶段防脏读；`GetReplicaList` 授读租约；近似 LRU + 硬 pin / 软 pin / 活跃租约四级保护；内存→SSD→DFS 三级回退，水位触发默认释放 5% 总量；节点心跳 TTL 10s，副本 best-effort 不自动重建。

### 3.5 KV 卸载 / 分层（KV streaming、CPU offload）

- **池化的本质就是分层卸载**：GPU HBM → CPU DRAM（L1）→ SSD/DFS/远端池（L2），冷热由 LRU + 水位决定（见 10）。
- **模型架构层的天然分层**：DSA 把「每步全量读的小索引（128 维）」常驻 GPU，把「只读 Top-k 的大 Latent KV（576 维）」标为可部分 offload 的冷数据（见 17）——这是「单一存储模式无法同时满足两种访存」的正面解法。
- **vLLM 侧的 offload 开关**：23 的指标里出现 `kv_offloading_backend=native`、`kv_offloading_size=None`，但知识库**没有**展开这套参数怎么配、带宽/延迟代价如何【部分未覆盖】。
- **易混淆**：`--cpu-offload-gb n` 是**权重**卸载（每次前向要过 PCIe，性能下降，只用于显存不足且不追性能），不是 KV 卸载（见 排查故障）。

## 4. 投机采样（speculative decoding）

### 4.1 原理与四类方案（见 11）

「先猜再验证」：草稿生成 γ 个候选 → 目标模型**一次前向并行验证** → 接受最长匹配前缀，首个不匹配处用目标分布重采样。**只要拒绝采样逻辑正确，输出分布与原生解码数学等价（无损）**。

| 方案 | 核心机制 | 关键差异/代价 |
|---|---|---|
| Draft-Target | 小模型逐 token 猜，大模型验证 | 通用、无损；但要额外显存加载草稿模型，接受率不稳，长序列收益衰减（见 额外实战/推理优化） |
| N-gram / Prompt Lookup | 在上下文里匹配末尾 N 个 token，抄后面 K 个 | 零模型零显存零训练；只适合高重复内容（代码、客服话术） |
| Medusa | 目标模型末层挂多个并行解码头，树状验证 | 单模型自投机、只训新增头、主干冻结；**直接预测离散 token**，越远越不准，通常 3-5 步 |
| EAGLE-1 | 用**倒数第二层 hidden feature** 做特征级自回归 + 树状草稿 + Tree Attention | 预测连续语义而非门牌号；额外输入「提前一步 token embedding」抑制漂移 |
| EAGLE-2 | 动态树（价值 `v(u)=∏P(x|c)`，扩展 Top-M + 重排剪枝 Top-N，保连通性） | 同算力下平均接受长度 +20~40% |
| EAGLE-3 | 多层特征融合（低/中/高 3 层，`W∈R^{d×3d}`）+ **TTT**（训练时模拟自回归）+ 去掉特征回归损失、只留 token CE | 官方称最高 6.5×，比 v2 再 ~1.4×；无约束后倾向「token 对但特征不像」 |

EAGLE 比 Draft 接受率高的三条原因（见 11 §2.5）：hidden feature 连续可"接近"；出 token 仍走目标模型自己的 LM Head（词表与分布偏差小）；特征空间保留未定死的信息。

### 4.2 接受率如何决定加速比（见 11，本节公式全部来自原文）

记 α=单步接受概率、γ=每轮候选数、c=草稿单 token 耗时/目标单 token 耗时：

```
期望接受长度   E[K] = (1 - α^(γ+1)) / (1 - α)
实际加速比     S    = E[K] / (1 + γ·c) = (1 - α^(γ+1)) / [(1-α)(1+γc)]
理论上界       c→0, γ→∞ ⇒ S_max = 1 / (1 - α)
本质硬上限     α ≤ 1 - TV距离(草稿分布, 目标分布)
```

- α=0.8 → S_max=5；α=0.9 → 10；α=0.95 → 20。示例校验：α=0.8、γ=3 → E[K]=(1-0.4096)/0.2=2.95 token/轮 ✓。
- **三层天花板**：理想极限（α 决定，可通过算法逼近）→ 本质硬极限（模型分布差异/TV 距离，**不可突破**，两模型完全一样时 α=1 但等于没加速）→ 工程极限（α + 草稿开销 + γ，靠调参逼近）。
- 所以「提升接受率」是唯一主线：Medusa/EAGLE 全系列都在缩小 TV 距离。

### 4.3 参数取值：`--spec N` / `--spec-min-p`

**知识库没有这两个参数**【未覆盖】，它用的是 vLLM 口径的四参数（见 额外实战/推理优化）：

| 参数 | 作用 | 知识库给的取法 |
|---|---|---|
| `--speculative-algo EAGLE` | 选算法 | 选 EAGLE（复用主模型中间层隐状态，从根上解决分布对齐） |
| `--speculative-num-steps` | 草稿树深度（≈γ 的层数） | 短输出偏保守、长输出调高 |
| `--speculative-eagle-topk` | 每层分支数（树宽） | 同上 |
| `--speculative-num-draft-tokens` | 单轮草稿 token 总预算（≈γ 总量，即"一次猜几个"） | 短输出适中保守；长输出可调高 |

`--spec N` 对应「单轮草稿 token 数 / 树规模」，`--spec-min-p` 这类「接受概率阈值/最小草稿置信度」在知识库中完全没有对应讨论【未覆盖】。

### 4.4 什么场景会失效或变慢

1. **c 不够小**：草稿模型太大或跑在拥挤的 GPU 上，`γc` 吃掉全部收益（见 11 分母）。
2. **α 上不去**：高熵/创造性文本、长尾专业领域，草稿与目标分布差异大 → 逼近 TV 上限（见 11）。
3. **γ 过冲**：超过最优猜测长度后收益递减甚至转负（见 11）。
4. **长序列收益衰减**：见 额外实战/推理优化背景（独立 Draft 方案的已知痛点），这也是它转向 EAGLE 的原因。
5. **显存挤占**：独立 Draft 模型额外占显存，会挤掉 KV/并发（见 11、额外实战）。
6. **decode 被其他负载拖住**：投机收益全在 decode 侧（见 额外实战「延迟毛刺减少，归根于 decode」），若 prefill 长请求抢占，收益被 ITL 抖动掩盖。

**MTP（multi-token prediction）**：知识库**未覆盖**【未覆盖】。11 的四种方案里没有 MTP，26 的脚本注释里出现的 `mamba-cache-mode` 也与 MTP 无关。

## 5. 并行策略（见 19）

### 5.1 通信原语与每层通信量

19 先铺 NCCL 五类规约（Sum/Prod/Max/Min/Avg，大模型并行场景几乎只用 Sum）与六个原语（Reduce / Broadcast / AllReduce / ReduceScatter / AllGather / AllToAll，并特意提醒 ReduceScatter 不是维度切分、AllGather 不是维度合并）。

| 策略 | 切什么 | 一个 Transformer Layer 前向的全局通信 | 适用 |
|---|---|---|---|
| DP | 复制权重，切请求 batch | **0 次全局通信** | 提吞吐，不改单请求延迟 |
| TP | 切权重（Attention 按头、MLP 按列/行） | **2 次 All-Reduce** | 降单请求延迟；通信量大，需 NVLink，一般 ≤8 卡 |
| PP | 按层切（layer split） | **仅相邻 Stage 点对点（P2P）**，无全局 AllReduce | 跨机、超大模型；有气泡 |
| SP | 叠在 TP 上，沿**序列维**切 LayerNorm/Dropout/残差 | 1 次 ReduceScatter + 1 次 AllGather = **通信量等同 2 次 AllReduce（不增加）** | 修 TP 的激活显存非线性缩放 |

SP 的价值在原文有定量依据：纯 TP 下每层激活 `sbh×(10 + 24/t + 5as/(ht))`，其中 `10sbh` 不随 TP 缩小 → TP 越大占比越高；SP 让 LayerNorm/Dropout/残差沿 S 切分，激活降到 `(34/t)bsh`，**通信量不变**。

### 5.2 流水线气泡（19 的定量部分）

- 朴素 PP（p=4, 单 micro-batch）：前向 4 个有效单位 / 16 个 GPU 周期，反向同样 → **气泡率 24/32 = 75%**。
- GPipe（m 个 micro-batch，F-then-B）：总时长 `2(m+p-1)`，p=m=4 → 14 周期 / 56 格、有效 32 → **气泡率 42.8%**。

【补充推导】气泡率通式 `(p-1)/(m+p-1)`。**2 卡（p=2）时**：m=2 → 33%，m=4 → 20%，m=8 → 11%。即 2 卡 PP 想压到 10% 量级需要 ≥8 个 micro-batch，而 micro-batch 越小单次矩阵越瘦，GPU 效率越差——这是小规模 PP 的固有矛盾。

### 5.3 「层拆分流水线并行」在 2 卡场景的开销与气泡

19 全程以**训练**（F/B、Loss、梯度）为背景，**没有讨论推理/decode 下的 PP**【未覆盖】。以下为基于 19 通信模型的推理侧推导【补充推导】：

- **收益**：权重与 KV 都按层对半 → 单卡 KV 容量翻倍，`max_model_len` / 并发可提升，这是 2 卡上 PP 相对 TP 的唯一硬优势（TP 会把每层 KV 也切开，但每层都要 All-Reduce）。
- **代价（decode）**：每个 token 必须串行穿过 2 个 Stage，`TPOT ≈ Σ(单 stage 计算) + P2P 延迟`；`[1, hidden]` 的激活只有几十 KB，**带宽不是问题，延迟才是**（kernel launch + P2P 握手 ~10µs 量级，对 10-30ms 的 TPOT 是可感知的百分比）。且 decode 每步只算 1 token，**没有 micro-batch 可填气泡**——训练里那套 GPipe 调度在 decode 上不成立，任何"Stage 2 等 Stage 1"的空转都是纯损失。
- **结论**：2 卡场景优先 TP（NVLink 下 2 次 All-Reduce 很便宜、延迟最低）；只有「单卡装不下 / KV 容量不够」时才上 PP，并且要接受 TPOT 上升；TP+PP 混合（2×2）只在 4 卡以上才有意义。PP 与 PD 分离、KV 池化叠加时，P 端更适合 PP（大 batch、算力密集、气泡可被 chunk 填），D 端更适合 TP。

**EP（专家并行）**：19 **未覆盖**【未覆盖】；仅在 3模型架构演进 提到 MoE 跨卡调专家会产生大量 AllToAll 通信。

## 6. MoE 与专家

**知识库覆盖极少**，只有 3模型架构演进 的架构层面：

- Switch Transformer 用 **稀疏 Switch FFN** 替换稠密 FFN：多个专家 + Router 打分 + **Top-1 路由**（每个 token 只激活 1 个专家，其余闲置），输出按路由权重加权合并。
- 容量账：128 专家、每次只激活 2-4 个 → 总参数可到千亿/万亿，算力只随**激活专家数**线性增长；原文称同算力下比稠密模型快 7 倍达同等精度。
- 两个已知缺陷：**专家坍缩**（Router 反复选少数专家，其余退化，需辅助损失/负载均衡约束）；**AllToAll 通信**（专家分布在不同 GPU，跨设备调用产生全对-all 开销，规模越大越可能吃掉稀疏收益）。

**expert offload 到 CPU/内存、expert cache 命中率、专家亲和性/专家画像（expert profile）、专家缓存大小对解码速度的影响：知识库全部未覆盖**【未覆盖】。

只给一条从知识库前提推出的判断【补充推导】：按 §2.4，decode 是 memory-bound，每 token 的耗时 ≈ 需搬运的字节 / 有效带宽。专家若在 CPU，每次未命中就是一次 PCIe 传输（带宽比 HBM 低一个数量级以上，见 5 对 PCIe「门很窄」的描述），因此**TPOT ≈ 命中部分按 HBM 带宽计 + 未命中部分按 PCIe 带宽计**；命中率每下降一档，TPOT 近似按「未命中比例 × (HBM带宽/PCIe带宽)」放大。据此，expert cache 的容量策略应盯住「热专家覆盖率」而非「专家总数覆盖率」——但这属于推论，知识库无实测。

## 7. 量化

### 7.1 类型与数学（见 18）

- IEEE 754 三件套：`值 = (-1)^S × (1.M) × 2^(E-bias)`；FP16（1+5+10, bias 15）、FP32（1+8+23, bias 127）、**BF16 不是 IEEE 标准**（8 位指数 + 7 位尾数，牺牲精度保范围）、FP8 E4M3（1+4+3, bias 7, 原生最大 ±448）。
- 量化通用式：`q = clamp(round(x/scale + zp), qmin, qmax)`；反量化 `x̂ = (q - zp)·scale`。对称量化 zp≡0；非对称量化用满刻度（原文例子：只用 scale 时 255 格只用 113 格，加 zp 后铺满 −127~127）。
- 浮点→浮点（FP16→FP8）多一步：除以 scale 只做数值对齐，**还要按目标格式裁剪位宽**（尾数 10→3 位，银行家舍入）才真正省字节；原文用 80.75→80.0（相对误差 <1%）走完全流程。
- **量化粒度**（从粗到细，精度↔开销）：per-tensor（激活常用）< per-channel（INT8 权重默认，性价比最高）< per-group（INT4 常用）< per-token（LLM 激活、KV Cache 必用，因不同 token 注意力数值差异极大）。

### 7.2 减误差三法（见 18）

RTN（直接四舍五入，零成本但粗暴）→ **GPTQ**（按列量化，误差按 Hessian 权重分摊给未量化列）→ **AWQ**（激活感知：0.1%~1% 显著通道由**激活幅值**决定而非权重幅值，用 `Y = XW = (X·diag(s)⁻¹)(diag(s)·W)` 等价缩放把重要通道权重拉大，相对误差从 25% 降到 2.5%）。

### 7.3 生产选型：FP8（见 额外实战/推理优化、24）

- 选 FP8 而非 INT8/4bit 的三条理由：Ada/Hopper **张量核心原生支持**（计算时无需反量化，无额外开销）；浮点动态范围大于 INT8、精度损失更小；相对 FP16 权重显存减半。
- 「量化一定更快」是错的（见 18 明确的判断树）：带宽瓶颈 → 大概率提速；计算瓶颈 → 看硬件是否支持低精度计算，**不支持则要反量化，可能不升反降**。
- **实测反例（见 24）**：A100/3090（sm80/86）上 FP8 全部 kernel 不支持，回退 `MarlinFP8ScaledMMLinearKernel`（cc≥7.5），W8A16、激活不量化，反量化发生在 CUDA kernel 内 → 「权重带宽省一半，但无 FP8 算力收益，计算密集场景反而弱于原生 BF16」。
- **精度由粒度决定（见 24 kernel 表）**：官方 FP8 = block 128×128（FlashInfer DeepGEMM）> 自量化 FP8_DYNAMIC = per-channel（Cutlass scaled_mm）> 在线 `--quantization fp8` = per-tensor（Cutlass online）。实测在线量化比两条离线 FP8 低 5-6 个点，原因就是 per-tensor 粒度粗。
- **实测收益（见 24，27B / 1×H20 / 2000+100）**：饱和吞吐 qps 档 1.95→2.85（**+45%**），P99 TTFT 15190→4064（**−73%**），P99 E2EL 49882→23218（**−53%**），精度「几乎无损」。

### 7.4 GGUF 档位（Q4_K_M / IQ3_XXS / IQ2）

**知识库完全未覆盖**【未覆盖】：全文没有 GGUF / llama.cpp / K-quant / I-quant 字样，量化章节只讲 FP8/INT8/INT4 与 GPTQ/AWQ。因此无法给出这些档位在**本库口径下**的比特数与质量损失。

若需要该信息，属于 llama.cpp 生态的通用经验（**非知识库内容，需以实际文件元数据核对**）：K-quant 的 `Q4_K_M ≈ 4.5 bpw`、`Q3_K_M ≈ 3.9 bpw`，I-quant 的 `IQ3_XXS ≈ 3.1 bpw`、`IQ2_XXS ≈ 2.1 bpw`；同 bpw 下 I-quant 靠重要性矩阵（imatrix）校准，低 bpw 段质量优于纯 K-quant，但解码更慢。**本库唯一可迁移的判据**是 18 的瓶颈树：这些档位在 decode（memory-bound）几乎线性收益，在 prefill（compute-bound）取决于硬件是否支持对应低精度 GEMM，否则会因反量化而变慢。

### 7.5 decode 阶段是 memory-bound 还是 compute-bound

**memory-bound**，且这一点在知识库中有三重独立支撑：18 背景（「大模型推理属于内存绑定型负载」）、9（decode 更 memory-bandwidth-bound）、额外实战/推理优化（decode 为访存密集，算力利用率 <30%）。结合 §2.4 的 `I ≈ 2/b`：**权重位宽每减半，decode 的理论上限耗时也近似减半**——这就是 24 实测 TPOT 30.76→16ms（−48%）的机制解释，也解释了为什么量化在 decode 的收益远大于在 prefill。

### 8.1 效果评测：lm_eval（见 27、24）

```bash
# 关键三件套：vllm 后端 + 固定 fewshot + limit 冒烟
python -m lm_eval --model vllm \
  --model_args "pretrained=<path>,add_bos_token=True" \
  --tasks gsm8k --num_fewshot 5 --batch_size auto --limit 250
```

- **`add_bos_token=True` 是量化模型评测的必要项**（24 原注：量化模型对 bos token 敏感），否则掉点会被误判成量化损失。
- 国内必须 `export HF_ENDPOINT=https://hf-mirror.com`，否则数据集下载阻塞；离线场景写自定义 task yaml（`dataset_path` 指本地、`doc_to_text`/`doc_to_target`/`doc_to_choice`）并用 `--include_path` 引入（见 27）。
- 分数读法：`Num=5` 是冒烟、**无统计意义**，正式评测去掉 `--limit`（见 27）。

### 8.2 性能压测：EvalScope perf（见 27）

```bash
evalscope perf --model <name> --url http://127.0.0.1:8123/v1/chat/completions --api openai \
  --parallel 1 5 --number 20 20 \
  --dataset random --prefix-length 400 \
  --min-prompt-length 500 --max-prompt-length 500 \
  --min-tokens 50 --max-tokens 50 \
  --tokenizer-path <path> --stream
```
关键点：`--parallel` 是**并发梯度**，可一次传多个值做扫描；`--dataset openqa`（真实问答）vs `random`（长度可控）；`--prefix-length` 构造共享前缀以测 prefix cache；`--min/max-prompt-length` 相等即固定长度（消除分布方差）；**`--stream` 必须加，否则只有整请求延迟、拿不到 TTFT/TPOT**；服务端要开 `--enable-prompt-tokens-details` 才能统计 Cached Prompt tok/s。

### 8.3 压测：vLLM 原生 bench + 自动化矩阵（见 23）

```bash
vllm bench serve --host 127.0.0.1 --port 8000 --model <path> \
  --dataset-name random --random-prefix-len 1000 \
  --random-input-len 1200 --random-output-len 100
```
23 给的自动化脚本是**压测矩阵的标准范式**，值得直接复用：
- 矩阵：`product(input_lens, output_lens, request_rates)`，`request_rates=[3,4,5,6,8,10,inf,200]`（**用 `inf` 打饱和点、用有限值打 SLO 点**），`num_prompts=100`，每档间隔 `sleep 3` 稳定。
- 必带开关：`--percentile-metrics ttft,tpot,itl,e2el`、`--metric-percentiles 90,95,99`、`--ignore-eos`（否则模型提前 EOS 会让 output_len 失真）、`--seed`（可复现）。
- 数据集：`random`（可控长度）/ `sonnet`（`sonnet.txt` 自然文本，带 `--sonnet-prefix-len`）/ `sharegpt`（真实对话）。三种在同一脚本里通过 `build_dataset_params()` 切换。
- 落库字段（CSV）：timestamp/seed/机型/模型/总输入 token/input_len/output_len/request_rate/**throughput_rps / output_tok_s / total_tok_s**/mean,median,p90,p95,p99 × (ttft,tpot,itl,e2el)/total_generated_tokens/**success_rate**。这张表就是"压测矩阵 → 结论"的载体，缺 success_rate 的压测不可信。
- 服务端观测：23 附了完整 Prometheus 指标字典，压测同时要抓 `vllm:num_requests_running / num_requests_waiting(_by_reason) / kv_cache_usage_perc / prefix_cache_hits_total / num_preemptions_total / iteration_tokens_total / request_queue_time_seconds / request_prefill_time_seconds / request_decode_time_seconds`。**`num_preemptions_total` 上升 = KV 不够开始换出，是吞吐拐点的第一信号**。

### 8.4 为什么必须用自然文本而非随机 token

知识库**给出了自然文本数据集（sonnet/sharegpt）却没有解释原因**【未覆盖原理解释】。但它自己讲的三个机制决定了这件事【补充推导】：
1. **prefix cache 命中率**：`random` 前缀是随机 token，除人为 `--prefix-length` 外几乎不可能命中；真实业务（system prompt、多轮历史、RAG 文档）命中率很高（见 10、8.7.1）。
2. **投机采样接受率 α**：随机 token 的 next-token 分布近乎均匀，α→1/V，加速比趋近 1，会得出"投机采样无效"的错误结论（见 11 的 `S=1/(1-α)`）。
3. **MoE 路由/注意力稀疏性**（若目标模型是 MoE 或 DSA）：随机 token 的路由分布与真实文本完全不同（见 3、17）。
结论：**做 prefix cache、投机采样、KV 池化、MoE 的收益评估必须用自然文本**；纯容量/拐点扫描可以用 `random`（长度可控、方差小），两者不能互相替代。

### 8.5 如何设计压测矩阵（把知识库的做法合起来）

1. **先定 SLO**（如 P95 TTFT<700ms、P95 TPOT<30ms，见 25）——没有 SLO 的压测只能得到"最大吞吐"，不能选型。
2. **定输入输出形态**：按业务真实分布设 `(prefix_len, input_len, output_len)` 三组（短问答 / 长文档 / 长输出），不要只测一组。
3. **单变量扫描**：并发（`--parallel` / `max_num_seqs`）从低到高、`request_rate` 从低到 `inf`，每次只动一个参数（见 额外实战「定初值，每次上调 25%」）。
4. **找三条红线**（见 额外实战/推理优化）：显存红线（峰值 >90% / OOM / KV 分配失败）、延迟红线（p99 E2EL 或 TPOT 超阈值、毛刺变多）、吞吐天花板（再调不涨甚至下降）。回退一档 + 预留 5%~10% 冗余 = 生产值。
5. **每组至少跑 3 次**取中位（知识库未强调，但 23 的脚本用 `--seed` + 间隔已在向可复现靠）【未覆盖重复性要求】。

### 8.6 p50 / p95 / p99 怎么读

- **p50（median）** 反映"典型用户"，与 mean 差距大说明分布右偏；23 的 CSV 同时存 mean 与 median，就是用来判断偏斜的。
- **p95/p99 才是 SLO 的载体**：25 的 SLO 全部写成 P95；额外实战的 CUDA Graph 实验「主要看 p99/95/90 的 e2el、ttft，看突刺现象是否改善」。
- **p99 暴涨但 p50 正常 = 排队/抢占**，不是算力不够：24 的 qps=1→3，mean TTFT 812→9291（11×），p99 2046→15190（7.4×），而吞吐只翻倍；排查故障一文列的四类根因正是这种形态（长输出占用 decode、异常重复生成、超长 prompt 独占 prefill、突发流量排队）。
- **ITL 的 p99 比 TPOT 的 p99 更敏感**：TPOT 是均值口径，会把个别 200ms 停顿摊平；长 prefill 插队造成的卡顿只有 ITL p99 能暴露（见 8 的 Chunked Prefill 时间线、7 的 ITL 定义）。
- **吞吐与延迟必须成对看**：只报 tok/s 不报 p99 的压测结论无效（goodput 才是可比数，见 25）。

## 9. 可复用的调优清单（参数 → 作用 → 影响 → 风险）

### 9.1 并发与显存预算

| 参数 | 作用 | 影响 | 风险 | 出处 |
|---|---|---|---|---|
| `gpu_memory_utilization` | 显存预算比例，剩余全部给 KV | 调大 → KV↑ → 并发/吞吐↑ | **CUDA Graph 显存独立于该参数管控**（1-5GB），调太高会隐性 OOM；小卡（5090/L20）建议 0.80-0.85，大卡（H20/H100）0.90-0.92 | 额外实战/推理优化、排查故障 |
| `max_num_seqs` | 单步并发序列上限（并发槽位） | 并发↑ → decode batch↑ → 吞吐↑（memory-bound 阶段收益明显） | 上限受 `可用KV ÷ (max_model_len × 单token KV)` 硬约束；过大 → p99 劣化、毛刺、preemption | 额外实战/推理优化 |
| `max_model_len` | 单请求最大总 token（context length） | 调小 → 同显存装更多请求 → 吞吐↑ | 直接砍业务能力（长文档/多轮）；与 `max_num_seqs` 是乘关系，二者一起定 KV 总量 | 额外实战/推理优化 |
| `--kv-cache-dtype fp8` | KV 存 FP8 | KV 显存减半 → 并发↑ 或 `max_model_len`↑ | 精度轻微损失，需业务校准；高精度场景留 FP16 开关 | 额外实战/推理优化、26 |
| `calculate_kv_scales` | 动态算 vs 离线标度 | 离线标度精度更优、启动更慢 | 动态版在长序列上数值稳定性略差 | 额外实战/推理优化 |

### 9.2 prefill 与调度

| 参数 | 作用 | 影响 | 风险 | 出处 |
|---|---|---|---|---|
| `max_num_batched_tokens` | 单次前向的 token 总预算（决定 chunk 粒度） | 调小 → prefill 分块细 → ITL 平稳、p99 毛刺少，但 TTFT↑；调大 → TTFT↓，但长 prefill 霸屏、ITL 飙升 | **下限必须 > `max_num_seqs`**，否则并发被卡死；高吞吐场景可设到 `max_num_seqs × max_model_len` | 额外实战/推理优化 |
| `--enable-chunked-prefill` | 长 prompt 切块与 decode 交错 | ITL 平稳 | 多一步调度开销 | 8、26 |
| block size（16） | KV 分页粒度 | 16 是碎片与寻址的折中 | 未实测 8/32/64；MoE/mamba 混合模型会被框架改写（23 中 block_size=544） | 8、23 |
| `--enable-prefix-caching` | 共享前缀跳过 prefill | TTFT 大幅下降 | 命中依赖块对齐与实例集中度；TP 实例越多越易被 round_robin 稀释 | 8、25、26 |

### 9.3 KV 复用 / 卸载 / 池化

| 参数 | 作用 | 影响 | 风险 | 出处 |
|---|---|---|---|---|
| `chunk-size`（256） | KV 池化分块与哈希粒度 | 越小命中越细，但元数据/传输开销↑ | 命中 token 数只能是块大小整数倍 | 10 |
| `--l1-size-gb` / `--eviction-policy LRU` / 水位 80% | CPU 热缓存容量与淘汰 | L1 越大命中越高，P99 越好 | 与主机内存、NUMA 抢资源；驱逐抖动会传到 P99 | 10 |
| `--l2-store-policy default/skip_l1` | 写 L2 后是否留 L1 | default 热数据留 L1（低延迟）；skip_l1 纯写透省内存 | skip_l1 会牺牲热数据命中 | 10 |
| `--l2-prefetch-max-in-flight` / `default`\|`retain` | L2 回填并发与留存 | retain 提升后续命中 | 并发过高打满 L1 | 10 |
| `kv_lease_duration`（300s） | P 端 KV 租期 | 需 > decode 时长 | 到期释放会触发**重传/重算** | 26 |
| `bidirectional_kv_xfer` + `decoder_kv_blocks_ttl`（480s） | D 端 KV 回传/钉住 | 支持 turn-2 回读 | **钉住但无人回读会把 KV 池填到 98%**（26 的真实故障） | 26 |
| `kv_recompute_threshold`（64） | 可复用 token < 阈值就本地重算 | 省一次远程拉取 | 阈值过高会反复重算长前缀 | 26 |
| `--cpu-offload-gb` | 把权重放 CPU | 显存不够时能起服务 | **每次前向过 PCIe，性能显著下降**；这是权重不是 KV | 排查故障 |

### 9.4 并行 / 拓扑

| 参数 | 作用 | 影响 | 风险 | 出处 |
|---|---|---|---|---|

### 9.5 算法层

| 参数 | 作用 | 影响 | 风险 | 出处 |
|---|---|---|---|---|
| `--speculative-algo EAGLE` + `num-steps` / `eagle-topk` / `num-draft-tokens` | 投机解码（≈γ 与树形） | α 高则 TPOT 近似按 `1/(1-α)` 上限下降 | γ 过大反而变慢；短输出保守、长输出调高；必须做参数梯度实验 | 11、额外实战/推理优化 |

### 9.6 稳定性兜底（来自真实事故，见 排查故障）

| 手段 | 作用 | 风险 |
|---|---|---|
| 输入侧限流 + prompt 长度阈值（超长截断/分流长文本集群） | 防超长 prompt 独占 prefill | 截断会损失业务完整性 |
| `repetition_penalty=1.1` 全局默认 | 抑制微调模型的异常重复生成 | 过高会伤多样性 |
| `max_tokens` 硬上限 | 防单请求无限 decode | 长文场景需单独放宽 |
| 网关突发限流 + 自动降级到小 bot | 保业务链路可用 | 降级=能力损失，需上游 AB |
| 调小 `max_num_batched_tokens` | 削峰、保 ITL | TTFT 上升 |
| 启动阶段 OOM：FP8/INT4 量化、加 TP、调低 `gpu_memory_utilization`、`--cpu-offload-gb` | 先能起服务 | 后两者牺牲性能 |

### 一句话结论

这个库的**强项**是「vLLM 生产调优的实操链条」——从 KV/分页原理 → PD 分离与 KV 池化 → 量化与投机 → 压测矩阵与故障处置，且带真实机型实测数字（24 的量化表、25 的 1.7×、26 的 98% KV 故障）；**弱项**是「硬件层定量分析」（无 roofline、无带宽/算力规格）、「MoE 工程」（只有架构层）、「GGUF 生态」以及三个空壳章节（15、nano-vllm、小部分 17 之外的注意力变体细节）。
