# 引擎参数速查

> 所有含义均取自 `strata --help` 原文与实跑启动日志，不是推测。
> 适用引擎版本：**0.1.45**（`/data/Strata/engine-cuda12/strata`）
> “当前值”对应 2026-11-02 **16:42** 的配置（args 43 项）：`parallel=4`、`--resident-experts`、`--ple-io mmap`、`--prefill auto:32768`、会话缓存 12 GiB、ESP 已加载、`reasoning_effort=medium`、`temperature=1.0`

## 0. 参数分三层，改之前先确认它在哪一层

| 层 | 位置 | 例子 | 改动方式 |
|---|---|---|---|
| **容器层** | `/data/compose/strata/docker-compose.yml` + `.env` | 端口、显存设备、shm、ulimit | 改 YAML，`docker-compose up -d` |
| **服务层** | `serve/server.py` 启动参数 | `--engine`、`--config`、`--port` | 在 `run-iq3_xxs.sh` 里 |
| **引擎层** | 配置 JSON 的 `exe` / `args` / 顶层键 | 几乎所有性能参数 | 改 JSON，重启容器 |

**改引擎参数有两条路**：重跑 `setup.sh`（会重新生成整个 JSON，最稳）或手工改 `args` 数组（快，但要自己保证 JSON 合法）。

## 1. ⚠️ 最容易踩的两个坑

### 1.1 引擎没有 `--parallel`

```bash
$ strata --help | grep -c parallel
0
```

真正的开关是 `--batch N` / `--slots N`。配置 JSON 里的顶层键 `parallel` 由 `server.py` 翻译：

```python
PARALLEL_MAX = 8      # 引擎的 batch window 最多 8 行
def parallel_args(cfg, args):
    if "--batch" in args or "--slots" in args: return []
    if n <= 1: return []                    # parallel=1 → 不传 --batch，单槽位
    return ["--batch", str(n)]
```

- `parallel` 合法范围 **2..8**；写 1 等于关闭批处理
- 写 `>8` 会被压到 8（除非同时加 `--batch-mtp`）
- **验证槽位真的生效**：`curl -s -H "Authorization: Bearer $KEY" http://127.0.0.1:8800/slots | python3 -c "import json,sys;print(len(json.load(sys.stdin)))"`
- 启动日志也会出现 `[strata] "parallel": N - the engine runs at most 8 requests together`

### 1.2 `--ple-gguf` 不给会静默降级

```
--ple-gguf PATH   the n-gram/PLE shard.  WITHOUT IT LAYER 1's PLE IS SILENTLY SKIPPED
```

不报错、不影响启动，但第 1 层 PLE 直接不生效——模型能力受损而你不会发现。`--ple-gguf` 是**必需**项。

## 3. 显存与上下文

| 参数 | 当前值 | 含义 | 取舍 |
|---|---|---|---|
| `--max-context` | `262144` | KV/state 容量（**默认只有 4096**） | 越长，pinned RAM 里的 KV 越大；超限请求返回 400，不截断 |
| `--kv` | `int8` | `fp16`(默认,1056 B/cell 的两倍) / `int8`(1056 B) / `q4_0`(528 B, 精度略降) / `k8v4`(816 B，K 精确 + V 4bit) | 长上下文省显存的首选是 `k8v4`，质量损失小于 `q4_0` |
| `--kv-resident` | `32768` | KV 流式：每 QSA 层留 N 格在显存，**整份 K/V 放 pinned RAM**；腾出的显存给专家。最小 20480；`0`=全放显存；**上下文 ≤ N 时不触发流式** | 这是 256K 上下文能进 40 GB 卡的关键。实测只占 1.55 GiB pinned RAM，代价极低 |
| `--kv-grow` | 未设 | KV 只按请求实际达到的格数占显存，专家缓存吃剩下的（单卡 + `--expert-profile`） | 默认是"整份 max-context 都占" |
| `--vram-elastic` | 未设 | 专家缓存分 512 MiB 段，支持运行时 `POST /v1/vram` 热调 | 需要动态让显存给别的程序时用 |
| `--trim-stage-weights` | 未设 | 显式 `--layer-split` 时每卡只加载自己那几层的稠密权重 | 能省显存，但改变行为，要先验 |

**显存账本（实测，chunk=8192、batch=4 时）**

```
CUDA0  ≈ 28.9 GB：层 0-23 的权重 + KV 显存窗 + 2 个 slot session(0.51 GB each)
CUDA1  ≈ 35.0 GB：层 24-47 + head + 专家缓存 22.24 GB + 2 个 slot session
专家缓存 = 12288 / 24576 个（50%）
CUDA1 可供专家 ≈ 31–33 GB，而 24576 个需要约 40 GB  → 装不下，所以停在 12288
```

> 改成 `--prefill auto:32768` 后层拆分重新平衡：**CUDA0 涨到 37.8 GB（仅剩 3.2 GB）**，CUDA1 降到 31.2 GB。长提示时要盯 CUDA0 余量。

## 4. 专家缓存（决定解码速度的核心）

| 参数 | 当前值 | 含义 |
|---|---|---|
| `--expert-cache` | `auto` | 放进显存的专家块数；`0` = 关闭（纯 CPU 池，最慢的地板）。`auto` 会算"空闲显存 − 700 MiB 储备"能装多少，**向下取到 2 的倍数档** |
| `--expert-cache-device1/2/3` | 未设 | `N` 或 `auto`：把 CUDA1/2/3 也填上专家。**与 layer-split 的组合未见官方实测** |
| `--expert-cache-per-layer` | 未设 | 每层独立分槽，而不是共享计数器。官方实测：默认策略 256 槽只覆盖 ~26 层的 position 0，命中 **2.97%**；per-layer 同样路由下 **21.4%** |
| `--peer-device N` | 未设 | 第二张卡当"自适应专家缓存层"（走 P2P）。**明确与 `--layer-split` 互斥** |
| `--expert-cache-remote-placement` | — | `stripe`（默认）或 `layer`，多卡专家放置方式 |
| `--mmap-experts` | （由 `--resident-experts` 带入） | 退出常驻 arena，回到 `MapViewOfFile`。官方给的代价：**mmap 速率取决于页缓存能否留住 34 GB，实测冷 71.97 vs 热 34.78 ms/token** |
| `--resident-cpu-experts` | （同上） | 与 mmap + 静态 profile 配合：GPU 缓存装不下的专家**常驻普通内存**，自适应交换只在内存之间换，**不再回文件读** |
| `--resident-experts` | **已启用** | 低内存机型模式 = `--mmap-experts` + `--resident-cpu-experts`，尽量钉页 + 4 GiB 余量；装不下就退回纯 mmap。**同一放置下答案与 `--mmap-experts` 相同** |
| `--shared-expert-arena FILE` | 未设 | 用一个 `MAP_SHARED` 文件承载常驻 arena；**文件要放 `/dev/shm`，不要放普通 SSD** |
| `--adapt-min-gain F` | 1.5（默认） | 自适应层换入专家的门槛：衰减路由计数要比被替换者高出 F 以上。调大 = 换得更少更准 |
| `--adapt-async 1` | 0（默认） | 换入在验证窗口之间推进，而不是整轮阻塞。**注意：帮助写明 "one GPU"**，且"Not bit-exact run to run" |

**`--resident-experts` 的效果（本机实测）**

它把 40 GiB 专家从"常驻匿名内存"改成"文件映射 + 局部钉页"，于是：

| | 关 | 开 |
|---|---|---|
| 引擎 RSS | 61.7 GiB | **39.3 GiB** |
| `MemAvailable` | 30.6 GB | **57.1 GB** |
| 显存 / 专家缓存 | 37.8+31.2 GB / 12288 | 完全不变 |

日志会多出这两行，可据此确认生效：

```
layer split: 100% of the experts resident, the prompt path's streamed ring 96 slots
FileExpertSource: mapped pinned cache complement ready: resident 12.65 GiB, pinned 12.65 GiB
```

⚠️ **"100% resident" 是"全部在主机 RAM"，不是"全部进显存"**——GPU 缓存仍是 12288（一半），另外一半由 CPU 池从 RAM 算，只是不再回文件读。

**为什么只有 50%：** CUDA1（末级）可供专家 ≈ 31–33 GB，24576 个需要约 40 GB，差 7–11 GB。CUDA0 跑完前 24 层后还有相当余量，但默认不给专家用。`--expert-cache-device1 auto` 是唯一可能把它利用起来的手柄——**需要实验验证**。

## 5. 预填（prompt 读取）

| 参数 | 当前值 | 含义 |
|---|---|---|
| `--prefill` | `auto:32768` | `CHUNK` = 每块多少 token。`auto` = **上限 8192** 内取"专家缓存借得出缓冲"的最大值；`auto:16384` / `auto:32768` 放宽上限（也可用 `STRATA_PREFILL_AUTO_MAX`） |
| `--prefill-pipe R` | 未设（0=关） | 层拆分专用：块大小按两卡的 b/a 调成同时读。`1` 只均衡缓冲块数 |
| `--prefill-head-alias` | 未设 | 读 prompt 时把输出头卸下，读完再装回，省峰值显存 |
| `--prompt-cache-every N` | 16384 | 每 N 个新 prompt token 存一个检查点；0 = 关 |
| `--prompt-cache-tail` | 未设 | 单卡时在 prompt 末尾附近多存一个检查点 |
| `--prompt-cache-spread` | 未设 | 检查点从会话末尾往回铺（近密远疏），适合客户端回改历史 |

**实测 chunk 解析值**（看日志 `prompt chunk auto: N tokens, a 96-slot ring`）：

| 配置 | 解析结果 |
|---|---|
| `--prefill auto` | **8192**（顶到上限，说明没有余量可涨） |
| `--prefill auto:32768` | **32768**（生效） |

**`auto:32768` 的官方依据**（`setup.py` 内注释）：

```python
PREFILL_BIG_RAM_GB  = 96   # --prefill auto:32768 在 96 GB 上 +21-35%，在 32 GB 上约 3 倍慢
PREFILL_RISK_RAM_GB = 64   # 低于此值显式设 auto:32768 会告警
```

代价：缓冲足迹按块大小线性增长，并且会挤占 VRAM 导致层拆分重新平衡（见 §3 的账本变化）。**本机 96 GB 正好在推荐档，+21~35% 目前尚未实测验证。**

## 6. PLE / n-gram 表读取（`--ple-io`）

表大小：**320001536 行 × 90 B = 26.8 GiB**，每个位置取 **16 行**（一次 `PrefetchVirtualMemory` 发出）。

| 模式 | 含义（引擎原文） | 内存 | 内存压力下 |
|---|---|---|---|
| `direct`（**引擎默认**） | 无缓冲 SSD 读，**表永不进入内存或页缓存** | ≈0 | 无影响 |
| `mmap` | 映射文件，按需进页缓存（原文标注 "A/B arm"） | 最多 26.8 GiB，**可回收** | 页被丢弃 → 退回 SSD 读 |
| `ram` | 启动时整表锁进内存（`mlock`），**prompt/token 路径上永不读盘** | 26.8 GiB，**不可回收** | 挤占其他内存，极端时 OOM |

| 配套参数 | 默认值 | 含义 |
|---|---|---|
| `--ple-row-cache N` | 1048576（约 90 MiB） | 已取行的有界缓存，三种模式都生效 |
| `--ple-inflight N` | 256 | 在途 SSD 读上限 |
| `--ple-sync-submit` | 关 | A/B：在 token 线程上提交读（默认走 I/O 线程） |

**实测对照（同机）**

| | `ram` | `mmap` |
|---|---|---|
| `Mlocked` | 28.1 GiB | **0** |
| `MemAvailable` | 18.5 GB | 32.4 GB |
| 引擎 RSS | 76.8 GB | 65.2 GB |
| 启动额外耗时 | +2.5~6 s | 0（懒加载） |

> **94 GB 机器上应该用 `mmap`**（`ram` 是按 560 GB 前提写的）。`mmap` 的唯一风险是页颠簸，此时反而不如 `direct` 可预测。`direct` 值得单独测一次做对照。

## 7. 投机解码（MTP）

| 参数 | 当前值 | 含义 |
|---|---|---|
| `--spec N` | `4` | MTP 草稿层**每个验证窗口提议几个 token**。`--suffix-draft` 命中重复时窗口可再涨 2，上限 8 |
| `--spec-min-p P` | `0.5` | 草稿层多有把握才继续外扩窗口。`--calibrate` 会为本机实测这个值 |
| `--suffix-draft N` | 3（默认） | prompt 查找：从上下文里上一次重复的末尾 N+ token 之后抄；`0` = 只用 MTP |
| `--lookup-chain K` | 0（关） | 在 MTP 草稿之后再追加最多 K 个查找草稿（窗口仍 ≤8） |
| `--lookup-chain-min M` | 3 | `--lookup-chain` 生效所需的最短上下文匹配 |
| `--mtp-max-t M` | 0（= `--spec`） | 限制 MTP 窗口 token 数 |
| `--mtp-q4 all\|proj\|head` | 未设 | 草稿层投影/头用 4bit 副本，省显存 |
| `--mtp-draft-vocab FILE` | 默认 | 草稿头的词表子集（`cjk` 默认 / `en` 省约 110 MiB） |
| `--mtp-hnorm pooled\|stream` | pooled | 草稿层隐状态归一化方式 |

**接受率是所有投机收益的分子**：加速比上界 ≈ `1/(1-α)`。当前随机语料下 α 只有 2–5%，等于没开投机。**换自然文本后必须重新测 α。**

## 8. 双卡与批处理

| 参数 | 当前值 | 含义 |
|---|---|---|
| `--layer-split` | `auto` | `auto` 按各卡空闲显存 + 每层成本自动分层；也可以给"后一张卡的起始层号"（48 层均分就是 `24`） |
| `--batch N` / `--slots N` | `4`（由 `parallel: 4` 生成） | 最多 N 个请求一起解码，每槽独立 session，**每槽都吃 VRAM** |
| `--batch-groups G` | `auto`（日志显示 `2 groups of 2 slots`） | 层拆分时把槽位分成 G 组在卡间流水 |
| `--batch-mtp` | 未设 | 每个槽额外验证一个 MTP 提议；需要 `--mtp` + `--spec`；每槽额外吃显存 |
| `--pipeline-windows N` | 未设 | 层拆分下把两卡的**验证窗口重叠**：`1` = 只重叠 prompt 短读，`2` = decode 也重叠。**仅 AMD gfx12 默认开**；`0` 关闭 |
| `--conversation-cache-*` | 见 §12 | 会话停放缓存，独立一节 |
| `--memory-limit-mib N` | 未设 | 容器看不到真实 cgroup 上限时告诉引擎 |

**批处理的收益与代价（实测）**：`parallel=4` 比 `1` 吞吐 +19~64%，但单请求 TPOT 从 8–10ms 涨到 13–54ms。收益随提示变长而衰减。

## 9. 控制向量 / ESP

| 参数 | 当前值 | 含义 |
|---|---|---|
| `--control-vector-scaled FILE:SCALE` | `…-speed-projection.gguf:1.0` | 残差流上的控制向量，`--ctrl-vector` 的缩放版 |
| `--control-vector-layer-range A B` | `4 44` | 作用层（含端点），默认 1..最后一层 |
| `--cvec-mode add\|project` | `project` | `add`：`h += s·v`；`project`：`h -= s(h·v)v`（v 单位化） |
| `--cvec-dir per-layer\|single:L` | `per-layer` | 每层各用自己方向，或全用第 L 层的 |

**关键机制**：`--serve` 模式下**每个请求用 `cvec=0|1` 自己开关**。`server.py` 只在配置里有 `"sampling": {"experimental_speed_projection": true/false}` 时才把 `cvec` 带给引擎；**没设就不带，走引擎默认值**。

> ⇒ 当前配置已加载控制向量（日志有 `control vector mode = project, dir = per-layer, layers 4..44 (41 steered)`），但没有 `sampling` 键，所以**无法确认 ESP 对请求真的生效**。之前的 A/B 零差异，要判定真实效果必须先加 `sampling.experimental_speed_projection`。

## 12. 会话与提示缓存

两块不同的东西：**prompt-cache** 是"请求之间保留的检查点"，**conversation-cache** 是"会话停放的 RAM 预算"。

| 参数 | 当前值 | 引擎原文 | 说明 |
|---|---|---|---|
| `--prompt-cache N` | 6（默认） | `--serve: keep N conversation checkpoints between requests (default 6, ~118 MB of RAM each; 0 = read every prompt from the start)` | 每个检查点约 118 MB，默认 6 个 ≈ 700 MB |
| `--prompt-cache-every N` | 16384（默认） | 每 N 个新 prompt token 存一个检查点 | 0 = 关 |
| `--prompt-cache-tail` | **已启用** | `--serve, single GPU: one extra checkpoint near the prompt's end, at an existing chunk boundary (default off; requires --prompt-cache and --prompt-cache-every > 0)` | ⚠️ 帮助注明 **single GPU**；本机是双卡层拆分，是否生效需 A/B 验证 |
| `--prompt-cache-spread` | 未设 | 检查点从会话末尾往回铺（近密远疏） | 适合客户端会回改历史的场景 |
| `--conversation-cache-mib N` | **12288** | `--serve: RAM budget for parked conversations (default 0 = off)` | 停放会话的 RAM 预算，12 GiB |
| `--conversation-cache-slots N` | **4** | `at most N parked conversations (default 4)` | 和 `parallel=4` 一一对应，配对正确 |
| `--conversation-cache-min-tokens N` | **4096** | `park only conversations of at least N tokens, so short side requests do not take the slots a long one needs` | 防止一句"你好"占掉会话槽 |
| `--conversation-cache-min-free-mib N` | 2560（默认） | 停放/保存/恢复时的 RAM 下限（在 MemAvailable、cgroup 限制和 `--memory-limit-mib` 之下） | 内存安全阀 |
| `--conversation-cache-park-gain N` | 0（默认） | 会话比将被取代的副本多推进 N token 才停放 | 避免"每轮写一次快照、下一轮就丢" |
| `--session-min-free-mib N` | 4096（默认） | 一次 SAVE 之后必须留出的磁盘空间 | |
| `--memory-limit-mib N` | 未设 | 容器看不到真实 cgroup 上限时告诉引擎总 RAM（也认 `STRATA_MEMORY_LIMIT_MIB`；flag 优先） | |

**预算怎么估**：KV 实测 262144 格只占 **1.55 GiB** pinned RAM，所以 4 个满长会话 ≈ 6.2 GiB，`12288` MiB 的预算相当宽裕。真正吃内存的是专家（40 GiB）和 PLE 表（26.8 GiB），会话缓存不是大头。

## 13. 推理预算与采样（配置 JSON 顶层，不是引擎 flag）

| 键 | 当前值 | 作用 | 对压测的影响 |
|---|---|---|---|
| `reasoning_effort` | `medium` | 思考强度默认值 | **决定性**：模型会先输出思考 token 再给答案 |
| `reasoning_budget_tokens` | 4096 | 思考预算上限 | `--max-tokens` 小于它时，输出会被思考全部吃掉，`finish_reason=length` 且没有答案 |
| `reasoning_close_retry` | `true` | 思考未闭合时重试收尾 | 可能增加一次内部重算 |
| `sampling` | `temperature 1.0` / `top_p 0.95` / `top_k 20` | 采样默认值 | temp 1.0 偏高：**结果不可复现**，且**压低 MTP 接受率**（输出越随机，草稿越难对齐），投机加速比下降 |

`reasoning_effort` 可以按请求覆盖（body 里带 `reasoning_effort`）：做纯性能基线时传 `"none"`，做业务 SLO 时保持 `medium`。**两种口径不能混着报。**

## 14. 环境变量（配置 JSON 的 `env`）

| 变量 | 当前值 | 作用 | 判断 |
|---|---|---|---|
| `STRATA_ROUTE_TAIL_SKIP` | **0** | CUDA 上默认 7，官方 changelog 记为 **+13-16% decode**。`setup.py` 的注释：`=0 where every expert is in RAM (the skip costs KL there)` | **拿速度换质量**。当前"全部专家在 RAM"正属于该分支，所以 0 与 setup 的自动判断一致。但这是本配置里最贵的一个开关，值得单独 A/B |
| `STRATA_RESIDENT_HEADROOM_GIB` | **6** | 常驻模式留的余量（`--resident-experts` 自带 4 GiB，这里覆盖成 6） | 保守，合理 |
| `MALLOC_MMAP_THRESHOLD_` | **16777216** | glibc：≥16 MiB 的分配走 `mmap`，`free` 后立刻还给 OS | 配合大块缓冲进出（prefill 块、会话快照）压住堆碎片；代价是更多 page fault 与 syscall |
| `STRATA_ADAPT_OVERLAP` | **1** | 自适应层换入在验证窗口之间推进 | ⚠️ 对应 `--adapt-async`，帮助注明 **one GPU**；双卡层拆分下是否生效需验证 |
| `STRATA_ADAPT_OVERLAP_RESIDENT` | **1** | 上面那项的常驻内存变体 | 同上 |

⚠️ **`STRATA_ADAPT_OVERLAP*` 与 "Not bit-exact run to run" 有关**：开启后同一请求两次运行的输出可能不同，压测必须重复多次取中位，不能单次定论。
