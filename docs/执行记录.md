## 8bis. 阶段 H：docker-compose 启动方式（2026-11-02 06:49–07:07 实测）

### 8bis.1 前置：本机原本没有 compose

```
docker compose version   → 'compose' is not a docker command.
docker-compose version   → command not found
```

手册 5.5.1 的规则是"两个都不存在时继续用 docker run，不要在离线机上另装"。本机是有外网的跳板机（非内网目标机），为了把 compose 配置验成"已验证"而不是"未验证"，**只装了官方 v2 独立二进制，没有装任何系统包**：

```bash
curl -fL -o /usr/local/bin/docker-compose \
  https://github.com/docker/compose/releases/download/v2.29.7/docker-compose-linux-x86_64
chmod +x /usr/local/bin/docker-compose
# Docker Compose version v2.29.7（60.8 MB，用时 14 秒）
```

> **内网目标机必须事先把这个二进制放进交付包**（或 `~/.docker/cli-plugins/docker-compose` 走 `docker compose` 调用），否则只能用 docker run。

### 8bis.2 文件

`/data/compose/strata/docker-compose.yml`（`.env` 同目录，必须）：

```yaml
services:
  strata:
    image: strata-qwen38:cuda12-1.0
    container_name: strata
    restart: unless-stopped
    init: true                      # 补充项，见 8bis.5
    command: ['/data/Strata/run-iq3_xxs.sh']
    ports:
      - '${BIND_IP}:8800:8080'
    volumes:
      - '${BASE}:/data'
    shm_size: 2g
    ulimits:
      memlock: {soft: -1, hard: -1}
    stop_grace_period: 120s
    security_opt: [label=disable]
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              device_ids: ['0', '1']
              capabilities: [gpu]
    healthcheck:
      test: ['CMD-SHELL', 'curl -fsS http://127.0.0.1:8080/health | grep -Eq loaded.:.true']
      interval: 30s
      timeout: 10s
      retries: 5
      start_period: 300s
```


| 06:54 | 容器自行变成 `Exited (137)` | 才能 `docker rm` + `up -d` |
| 07:01 | 加了 `init: true` 后再 `docker rm -f`（运行中） | 仍然失败：`tried to kill container, but did not receive an exit event`（12 秒后放弃） |

**根因**：引擎进程占着两张卡的 CUDA 上下文，收到 SIGKILL 后要先把 GPU 上下文拆掉，这段时间进程处于不可中断状态；docker 20.10 的 kill 只等 10 秒，等不到退出事件就报错，容器留在不一致状态。`init: true` 只解决"孤儿进程回收"，**不解决 CUDA 收尾**，所以两种写法都会失败。

**正确做法**（已验证）：

```bash
docker-compose stop      # 13 秒，SIGTERM，python 自己收掉引擎
docker-compose down      # 或直接 down（内部先 stop 再 rm），13 秒，干净
docker-compose up -d     # 65 秒 healthy
```

**不要**对运行中的 strata 直接 `docker rm -f` / `docker kill`。真遇到卡死：等它自己退到 `Exited (137)`（本次约 5 分钟），或 `systemctl restart docker`（会中断所有容器）。

### 8bis.6 与 docker run 的差异

| 项 | docker run（首次部署用的） | docker-compose（现在在用的） |
| --- | --- | --- |

### 8bis.7 端口调整与访问路径（07:15–07:26）

**发生了什么**

| 时间 | 事件 |

**三层地址，别再混**

```
容器内服务监听 : 0.0.0.0:8080         ← config 的 "host": "0.0.0.0"、"port": 8080
宿主发布映射   : 0.0.0.0:8800->8080  ← compose 的 '${BIND_IP}:8800:8080'（本节 07:24 时还是 8080，见 8bis.8 的最终方案）
```

## 9. 与手册不一致的地方（需要更新文档）

1. **容器内 Python 是 3.10.12，不是 3.12.16**。`pyvenv.cfg` 写的也是 3.10.12；手册 5.3 的"Python 为 3.12.16"这条门禁应改为 3.10.12。不影响运行。
2. **`/health` 不能从 `127.0.0.1` 访问**。手册 5.6 第一条 `curl -s http://127.0.0.1:8080/health` 在本机返回空，因为容器端口只绑了 `-p 192.168.122.4:8080:8080`，宿主 127.0.0.1 并不监听。要用 `http://<内网IP>:8080/health`，或在容器内 `docker exec strata curl 127.0.0.1:8080/health`（容器内正常）。手册 5.5.1 的 compose healthcheck 在容器内执行，所以没问题。
3. **驱动/机型与手册不同**：手册写 A100-PCIE-40GB + 535.104.12，本机是 A100-SXM4-40GB + 550.78。手册第 10 节"驱动 535 能否跑 CUDA 12.4"的风险在本机**不存在**（550.78 原生支持 12.4），但 SXM4 的 NVLink 在虚拟机里不可用，双卡只能走 PCIe——本模型是层拆分流水线，实测不影响速度。
4. **内存 94GB 够用但需注意**：setup 选择 `--ple-io ram`（29GB n-gram 表进内存）+ 专家 39.97 GiB 载入 + KV 流式，稳定态 44G 已用。手册按 560GB 写的"专家全部放内存"策略在本机应改成"专家进显存缓存"（实际就是这样：12288 个专家、17.72 GiB 显存）。
5. **局域网可达性**：本机唯一网口是 `192.168.122.4/24`（libvirt NAT）。手册要求的"局域网另一台电脑访问"在这台机器上需要宿主机做端口转发/NAT 映射，否则外部访问不到；这属于网络配置，不是离线包问题。已按默认绑定该地址，未做外部可达验证。

## 11. 复现同一份离线包到另一台新机器的结论

按《离线环境部署手册》+ 本次实测，**可以按同一流程复现**，要点：

- 只需 6 个动作：传包 → `sha256sum -c` → 解包 → `docker load` → `setup.sh --setup --no-start` → `docker run`。
- 断网完全没问题：setup 没有发起任何网络请求，引擎为预编译（arch 80），模型/MTP 都在包里。
- 换机器的变量只有三个：GPU 是否 sm80、显存总量（决定 `--context` 与 `--gpus`）、内存（决定 `--ple-io`）。
- 必须保证容器挂载点仍是 `/data`（配置里全是 `/data/...` 绝对路径）。
- 本次在 94GB 内存、40GB×2、无 NVLink 的机器上跑通，说明这套包对"比云主机更小的机器"是安全的；反向（更大显存的单卡 80GB）只需 `--gpu 0`。

详细步骤与门禁见 `plan-新内网机器复现.md`。
